# 详细设计写作骨架

本文件供作者选取结构，不整份复制到产物。新文档可合并、调整顺序、按设计问题命名章节，不要求十一章、固定编号或每个模块相同的小节。已有文档优先保留被引用的章节与 D-* 锚点；移动前核对覆盖，移动后修复引用并记录修订。

目标是让实现者和测试人员找到明确的契约、理由、边界和验证依据。图、表、正文各自补充信息；读者不应反复核对三份相同算法。按[图示规范](references/design-diagrams.md)选择必要视图，按[设计质量检查](references/design-quality.md)检查产物。

## 必须能找到的信息

以下是内容要求，不是待填写的章节清单。没有涉及的风险或技术面不用占位。

| 信息 | 写在哪里 |
|---|---|
| 来源、目标、范围、非目标、接受状态、修订原因 | 开头简述并链接来源；已有概要时不复写业务背景 |
| 设计决定及其理由、关键取舍 | 决定所在的机制或契约章节；沿用已接受提案，不重复论证 |
| 现有能力、复用判断、所有权与依赖、状态/故障边界、维护代价 | 就近附在决定旁，或合为简短“架构适配”；引用真实路径/符号/契约，证据缺失时说明 |
| 精确行为及受保护的旧契约 | 机制、接口或数据章节；边界只写一份，其他位置链接 |
| 实际验证证据、源场景覆盖、未解决问题及其影响 | QA / Verification Strategy |
| 实施相关决定的唯一位置 | Design Contract Index；锚点位于正文，不把完整决定都塞进索引 |
| 哪些决定已固定、哪些仍由下游决定、哪些阻塞交接 | Planning Handoff；没有规划需求时简述当前交付状态即可 |

`Support lenses` 记录实际采用的 lens 及结论，未触发时用一处 `none`；无需每种 lens 各开一表。每个设计只记录一次完整的架构依据，具体契约用链接回指。

## 推荐起点

下面是一个可调整的短骨架。小设计可以合并为几个章节；复杂设计按真实决策拆分，不能靠填更多栏目替代设计。

```markdown
# <项目/功能>设计

状态：<proposed / accepted / 待评审；明确已有批准与本次交付状态>
来源：<需求、已有合同及必要的概要/提案链接>
修订：<版本、变更、原因；多次修订可用表>

## 范围与设计依据
<本次详细设计补充什么；现有 owner、复用点和边界的证据>

## <关键机制或决策>
<决定及其来源、理由、边界、状态与下游约束；选择主要表达>

## <本次需要精确定义的接口或数据合同>
<只展开本次变更的契约；不复写机制>

## 验证与交接
### Verification Strategy
<源 TC 的文档推演结果与后续实现验证；实际呈现检查及限制>
### Design Contract Index
<每个 D-* 的唯一链接及 AC/边界/下游关系>
### Planning Handoff
<固定约束、下游可决定的事项、未决问题及交付影响>
```

只有“记录已接受的局部选择”的请求不需要这个骨架，按 skill 的简短记录规则处理。

## 按设计问题展开

### 行为与处理机制

对需要详细说明的机制，交代入口、输入、前置条件、转换/决策和调用方结果。选择流程图、时序图、表格或文字作为主要表达，再补主要表达不能承载的精确规则。业务主流程由概要拥有时，本节直接链接，只补实现所需细节。

涉及跳过、空成功、整体失败等不同出口时按图示规范表达关键分支。多个输出路径共用输入时解释共同阶段和分叉，不让比较图暗示它们必然在同一请求执行。已有机制足够解释顺序时，不再另列“流程步骤”。迁移、发布等独立操作顺序只在影响合同且未在别处定义时展开。

合并简单协议映射、字段注入和生成支持说明，不要求它们各自重复入口、机制、边界和不变行为。关键复杂模块可以独立成章，但不强制统一子章节格式。

### 接口合同

按 [api-designer 的按需响应规则](../api-designer/SKILL.md#return-only-what-callers-need)确定字段：逐字段说明调用方用途与需求依据，区分列表、详情等场景；不直接透传存储对象，不用 JSON 字符串代替调用方需要的结构化合同。存量删字段或改类型须核实消费者与兼容性。

新增或修改的范围内接口须明确请求/响应形状、字段来源、必填/默认值/枚举、校验及客户端可见的成功与失败语义。读者须能区分空成功、部分成功（仅限已要求）和错误。内部错误与 wire 输出分别表述；未经证据确认的映射保留为缺口。

接口路径、方法或 RPC、鉴权边界和兼容性按实际协议说明。完整字段表和一段 proto/OpenAPI 示例若表达相同内容，保留最清楚的一种，另一种只补必要差异。沿用已有合同的部分直接引用。禁止从模板推导限流、熔断、日志、重试等未要求机制。

### 数据、状态与并发

实际修改数据模型时定义实体关系、字段、唯一性、索引或查询访问路径及其理由；图不代替必要字段含义，字段表也不代替关系语义。只改局部字段不必画全库 ER 图。

改变生命周期时提供状态图或完整转换表，状态、事件、守卫、效果及非法转换处置须可恢复。涉及并发持久化状态时按共享并发合同保留不变量、CAS 条件、冲突/回滚与 ABA 判断。纯读场景无需填“状态/写入/补偿：无”；但必须明确影响验收的读取一致性和数据变化边界。

### 运行与兼容性

仅在实际涉及时展开消息交付、缓存、配置、任务、部署、迁移重叠、回滚、权限、性能或可靠性合同，优先就近放在所属机制。无状态变更的小接口可以用一段发布顺序与旧契约保护说明，不需独立“系统发布/监控/容量”章。

保留非显然排除及代价。没有需求或既有约束支持的建议应标为建议，不能变成新的验收或发布阻塞项。缺少负载证据不能写成性能已经达标；反过来也不能自动要求开展未授权的压测、建设监控或增加基础设施。

## 决定与验证的写法

决定旁使用唯一显式 D-* 锚点，并交代来源 AC（如有）、合同类型、接受状态、规则、边界和下游预期。这些信息可以在连贯正文中，不必逐决定填写一组加粗字段。已有相同全局状态可以引用；某项待决时必须单独标明。

索引链接唯一维护位置。例如写 `[D-001](概要设计.md#D-001)`，不能只写“D-001 见概要与详细设计”。精确锚点示例见设计质量检查引用。不要把模板链接复制进生成文档，改为实际来源、决定或证据链接。

Verification Strategy 保留源 TC 覆盖，能恢复 AC → D → TC；允许合并推演结果和验证策略，不另建一份重复用例表。正常与关键异常的文档推演写明具体结果；自动化/人工实现检查标记待执行、已执行或有理由延后，不能混淆。

最后分别记录语义检查与呈现检查的实际结果。渲染工具不可用时明确视觉验证限制，仍需完成语义、链接和锚点检查。记录真正发生的评审、问题与结论；准备或发送材料不能写成评审通过。
