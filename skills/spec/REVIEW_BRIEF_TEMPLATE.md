# 概要设计写作骨架

概要设计供产品、测试和工程师共同评审：说明要解决什么、方案如何运作、改变什么、必要时简述为何这样选择。按 spec 的概要设计适用范围使用；不要求固定七章、每模块三段或每项都填表。

新文档可按业务链路或关键决定组织、合并相邻主题；章节名使用清楚的工程/业务名称。已有文档须保留独有决定、D-* 锚点、评审问题和修订历史，不能为了换版式覆盖它们。引用过的章节移动后修复入链。

## 内容与读者

主体应让读者理解输入如何成为结果、哪些异常改变结果、方案理由和代价。保留理解决定所必需的领域词和技术名词；不要将不同事件或状态翻译为同一泛称。函数签名、文件路径、字段级错误映射和生成器版本放详细设计，通过真实链接定位。

已有概要拥有其中的架构、核心流程和模块边界；详细设计拥有字段级和实现所需的精确合同。同一决定只在所属位置完整维护，另一份文档可以概括并链接。使用[图示规范](references/design-diagrams.md)选图，不把“一张总图”视为已经解释了所有业务分支。

## 可调整的起点

以下只是常见组织方式；项目简单时可合并，复杂时按关键机制拆分，不将每个技术组件提升成独立模块章。

```markdown
# <项目/功能> · 概要设计

状态：<版本、接受/待评审状态；实现是否已发生>
来源与详细设计：<实际链接>
修订：<变更与原因；保留后续评审修订>

## 背景与范围
<业务目标、本次范围和容易误解的排除>

## 核心方案
<系统边界、职责、运行机制、关键分支；必要的理由与代价>

## 变更与影响
<接口/存储/模块变化，调用方或运维需要配合什么，哪些旧行为受保护>

## 风险、验证与待决事项
<实际风险、未决选择及影响，关键验收结果，链接详细 QA；真实评审状态>
```

## 写作取舍

- 背景写有证据的痛点或新业务目标，不给新业务编造旧系统缺陷。范围写清非显然排除，不按模板枚举所有“不做”。
- 核心方案选最清楚的主要表达。架构图讲职责和依赖，流程图讲分支和出口；图中节点使用短职责名，必要时就近映射到模块。图已经表达的步骤不再用列表复写。
- 与业务结果相关的规则在机制旁说明理由。表格只用于值得比较的并列信息；一两句能说明的内容直接写段落，不强制“诉求/设计/规则与理由”三个标签。
- 同一组数据导出不同结果且容易混淆时，概要解释业务区别和代价，详细设计拥有精确投影对比。避免维护两份同内容表格。
- 变更影响聚焦实际改变的表面。已有核心路径保护写成可验证约束，未实施时不能写成已验证“零改动”。无变更的技术组件不需逐项列空值。
- 方案比较和被否决选项不是必填项；只解释影响读者理解或判断的选择。
- 决定旁保留唯一 D-* 锚点及状态，完整索引在详细设计链接回来。待确认只记录真实未决选择，不把已接受方向重新交给评审点头。
- 冲突、数据/兼容性代价和非显然的故障后果保持可见。待决项可以独立成表，也可留在所属机制旁并被交接摘要引用；不能在两处维护完整问题表。

## 验证与评审记录

挑出评审人需要判断的验收要点，链接详细设计中的源 TC 覆盖、文档推演和呈现检查结果。不要在概要重新维护完整测试矩阵。仅交付概要时按[设计质量检查](references/design-quality.md)就近记录实际结果与限制。

已有或明确要求的评审记录中，保留提出者、处理结论及依据；不默认新建讨论记录。采纳的修改直接更新对应设计，必要时简述契约变更原因。材料发出、聊天沉默、等待超时均不是评审通过；不为本文新增审批门或重新索取已有明确批准。
