# Examples：前后改写对照

按 SKILL.md 的硬规则组织（Rule 编号对应正文 Hard Rules；Addendum 指 Engineering-Design Addendum）。每个模式先给通用示例，再给真实项目案例（来自证券行情同步项目的实际改稿，Symbol、RIC、OCC、T-1、清算切日等为该项目领域专名，按 Rule 1 保留原样）。**模式可迁移到任何领域；案例里的业务细节不要照搬。**

## 1. 软建议 → 定案（Rule 2）

**通用**

> 建议审批通过后再发起扣款，重试次数可以设为 3 次。

→

> 审批通过后发起扣款；失败重试 3 次，仍失败转人工。

**真实案例**

> 建议每日定时跑一轮，分为两阶段。T-1 路由可并入日批第二阶段。

→

> 每天定时跑一轮，固定两阶段：先同步落标准事件，成功后再路由。T-1 路由放在每日同步的第二阶段。

## 2. 抽象包装名 → 写实际规则（Rule 1 + Rule 5）

**通用**

> 采用滑动窗口机制拉取增量数据，窗口大小可配置。

→

> 每次拉取以当天为基准、往前 N 天（默认 7，可配置）到当天为止的增量数据，含起止两端。

**真实案例**

> 一次同步拉这一窗，在窗内做配对。产品确认按同步日拉，而不是按每个事件的生效日分别扩窗。

→

> 以当天业务日为基准：起点是往前第 3 个美股交易日，终点是往后第 5 个美股交易日；拉起点到终点之间每个自然日的原始行。配对只在这一批数据里做。起止按同步日算一次，不按每个事件的生效日分别拉。

区间类规则最好配公式和日期例子，放进「关键决策」一节。

## 3. 自造夹杂要改，领域专名要留（Rule 1）

**自造夹杂（要改）**

> 日批作业加锁后 sync；管理端不露 raw 全文。

→

> 每天定时同步先加锁再拉取；管理端展示结论、变更前后、证据摘要、关联。

**误伤专名（不要这样改）**

> 「主板换所且 Symbol 不变」被改成「代码不变」；trade status 被硬翻成生造中文。

→ 专名保留：

> 主板换所且 Symbol 不变；交易查行情 trade status。T-1、RIC、ISIN、change_scope、action_type 等同理，首次出现加一句中文旁注即可。

判别方法：这个词是否出现在协议、接口、上游文档或团队既有文档里？有出处就是专名，保留；没有就是自造，改掉。

## 4. 模糊指代 → 点名（Rule 1）

**通用**

> 那边负责校验，这边只做转发。

→

> 风控服务负责校验，本模块只做转发。

**真实案例**

> 那边读 OCC / 市场事件，这边读 RIC Change。

→

> 分红拆合股链路读取 OCC / 市场事件，本模块读取 RIC Change。

## 5. 臆造能力 → 核实后删或改写（Rule 3 + Rule 7）

**真实案例**

> 改代码确认后，走既有「通知清算更新映射」能力，本模块不另开平行通道。

核实后发现协作方没有这条出口 →

> 删掉整句（列入 deletion ledger）。若只需表达和清算切日的关系，写：
> 消费到当日清算切日消息后，按改代码任务调用行情改库接口。

要点：产品文案里有、实现里没有的能力，不能写成「走既有能力」。先核实；删除时留痕。

## 6. 辩解旁白 → 决策表一行（Rule 4）

**真实案例**

> 通知渠道为服务间调用。
> 说明：飞书里写过「通知清算更新映射」。本模块不负责通知清算；和清算的关系是收清算切日消息……

→

> 行情改库：调用行情正股事件接口。
> | 改代码 | 消费到当日清算切日消息后，按改代码任务调用 |

对账过程、免责声明放评审口头说明；正文只留定案。

## 7. 臆造量级 / 臆造下游故障 → 删除留痕（Rule 3 + Rule 7）

**真实案例**

> 规模预期：日增量原始行大约千到万级；单次拉取控制在分钟级。
> 风险：通知到了但 trade status 未更新 | 联调时把行情状态单独验收

→

> 无量测依据的量级整段删除，列入 deletion ledger（作者若有依据可补出处恢复）。
> 本系统看不见的下游状态不写成己方风险；边界写成：职责止于改库通知。

## 8. 实现笔记 → 设计视角（Engineering-Design Addendum）

**真实案例**

> 代码锚点：`ric_change_sync.go`、`handler_delisting.go`。
> 建议回归：`go test ./internal/biz/... -run RICChange`

→

> 用职责描述：每日同步、退市任务执行、生效日行情通知。
> 验收写成场景表，不绑具体测试命令。

例外：用户要的是实现说明或改造方案时，代码路径与命令可以保留，但单独成节，不混进设计正文。

## 9. 表格装逻辑 → 判定条件显式（Rule 11）

删噪声删过头的典型产物：把分支逻辑压进表格单元格，"看起来定案了"，实际把未定案藏起来了。

**Before（详设真实案例）**

> | 非主板 DEL | `observation` 或 `otc_change_row` | ... |

「或」的判定条件全文没有出现——实现的人只能猜。

**After**

> 有判定条件就写条件；没有就把缺口亮出来：
> 「待确认（研发定案）：非主板 DEL 在 observation 与 otc_change_row 之间的判定条件。」
> 单元格里无条件的「或」要么是隐藏的未决策，要么是可读性缺陷，二者都不允许留在表里。

## 10. 电报体 → 完整句子（Rule 12）

**Before（详设真实案例）**

> change_scope 取值：任务/明细载荷 → 扩展字段 → 标准事件。
> 消息失败走明细失败或差异。

箭头链要读者猜是优先级还是数据流；第二句没有主语，"走"字承担全部语义。

**After**

> 发消息时 change_scope 按优先级取值：先用任务与明细载荷里的值；载荷缺失时用扩展字段；仍缺失时回退到标准事件。
> 消息发送失败时，按明细失败或差异流程处理。

## 11. 只有公式、没有算例（Rule 10）

**Before**

> 起点=`RelativeTradingDay(D,-3)`，终点=`RelativeTradingDay(D,+5)`；闭区间每个自然日。

**After（公式旁边紧跟算例）**

> 同上，并紧跟：
> 例：同步日 `2026-07-20`（周一），无额外休市：start=`2026-07-15`，end=`2026-07-27`，实际拉取 `7/15`～`7/27` 每一天（含 `7/18`、`7/19` 周六日）。
>
> 文末验收用例不能替代算例——读者需要在读到规则的那一刻验证自己的理解。

## 12. 流程图与决策不一致 → 对齐（Rule 6）

**通用**

> 决策写「支付成功回调后才发货」，图里却画成「下单 → 发货」。
> → 图改为：下单 → 支付 → 支付成功回调 → 发货；并补支付失败出口。

**真实案例（图）**

> 建改代码任务 → 立刻行情改库

→ 与决策对齐：

> 生效日建改代码任务 → 执行时发交易消息；**清算切日之后**再发行情改库。
> 转板 / 仅改名走生效日行情通知，不经正式任务。
