## 二、需求信息

### 2.1 需求背景

为集群内调用方提供按业务日期查询受限标的的 RPC。原始需求、AC-001 至 AC-008、TC-001 至 TC-007 由同目录 [source.md](source.md) 唯一维护；该文件是 fixture 的原样副本，不是实际项目的已批准需求文档。

### 2.2 需求范围

本期定义既有内部服务的新 RPC、既有交易限制用例的查询方法、字段投影、错误传递以及 proto 生成和部署边界。业务与模块边界见[概要设计](概要设计.md)。不增加 schema、作业、分页、日历校验、重试、补偿、日志基础设施或出站调用审计；不改 Redis 和候选/策略契约。

Support lenses: `architecture-designer`、`go-style`。前者核对复用及所有权，后者约束小接口与生成产物。输入未确认 Kratos 框架，不据命名推断框架；没有 SQL 改动，也不另行设计查询语句。

#### 3.6.3 边界与隔离

架构所有权由 [D-001](概要设计.md#D-001) 维护；数据读取与错误只影响本次请求，汇总集合为请求局部数据，不能存入共享缓存。仓储原有状态由既有工作流更新，查询不增加写路径。集群内认证边界沿用；没有 HTTP 映射。仓储或策略返回错误（包括由既有路径返回的超时错误）沿 [D-007](#D-007) 转换，不引入重试或替代数据源。

#### 3.6.4 可维护性

维护成本集中在新增查询方法、小接口/注入、proto 和生成入口。候选与策略继续由既有所有者维护；RPC 与 Redis 的投影各自绑定其输出语义。后续扩展或移除 RPC 必须同时核对调用方和协议兼容性，不顺带移动限制策略。测试边界分为 biz 输入/选择、service 转换、生成与旧行为回归；诊断依赖已有返回错误路径，不增加日志系统。确切源码位置与现有测试命令是 [Q-002](#questions) 的待补证项。

## 四、详细设计

### 4.1 TradingRestrictionUsecase

#### 4.1.1 需求内容

在既有 owner 上增加 `ListTradingRestrictedSymbols` 查询能力，由服务的小查询接口消费。逻辑输入为业务日期字符串，逻辑输出为字符串列表或错误；实际 Go 参数及 context 形式沿现有接口模式确认，不猜仓库签名。核心分支见 [D-002](概要设计.md#D-002)。

#### 4.1.2 设计机制

<a id="D-003"></a>
**D-003 · Behavior Contract · 已接受（演练）**：biz 首先使用现有 `validateRequiredDateLayout` 校验 `YYYY-MM-DD`，失败前不得调用仓储；成功后只调用一次既有 `ListTradingRestrictionCandidates(businessDate)`。其候选条件为：美国市场、日期匹配、`delete_time` 为 null/zero、状态既不是 `completed` 也不是 `no_action`、`restriction_released_at` 为零；record-only RIC 不属于任务源。每个候选使用 `tradingRestrictionDecisionForTask` 完成注册解析和策略结果校验，任何错误整次失败，校验成功后才按 `Restricted` 决定保留或跳过。来源：AC-001、AC-002、AC-005、AC-007、AC-008。边界：仓储查询和处理器规则不改，不增类型白名单；下游用候选排除矩阵与日期提前失败用例验证。

<a id="D-004"></a>
**D-004 · Data Contract · 已接受（演练）**：仅对策略成功且 `Restricted=true` 的候选选择 `task.Symbol` 原始字符串；空字符串使整次请求失败。按精确字符串相等去重，再按字符串升序排列。不得 trim、大小写折叠、加减后缀、读取替代字段或做键规范化；`AAPL` 与 `AAPL.US` 分别保留。来源：AC-003、AC-004、AC-006、AC-007、AC-008。边界：不为非空空白串新增清理规则；不受限任务的 symbol 不进入该空值检查。下游以原始字段与策略字段不同的输入验证选择来源，并覆盖单项、重复项及空集合。

两个路径独立执行，下表是语义比较，不表示一个 RPC 先后执行两条路径。

| 阶段 | 新 RPC | 既有 Redis 写入 |
|---|---|---|
| 共同来源 | 既有任务候选查询 | 同一候选阶段 |
| 共同策略 | 既有处理器决策及校验 | 同一策略阶段 |
| 分叉字段 | `task.Symbol` | `decision.Symbol` |
| 转换与去重 | 不改字符串；精确去重；升序排序 | 经既有 key 契约规范化；去重；首次出现顺序 |
| 输出去向 | RPC `symbols` | 既有 Redis 写入路径 |
| 示例 | 保存值 `AAPL.US`、`AAPL`、`AAPL.US`，均受限，返回 `["AAPL", "AAPL.US"]` | 输入不是保存值列表；具体值由各任务的 decision 与已有 key 规则决定，fixture 未提供，不猜规范化结果 |

#### 4.1.4 关键规则与边界

<a id="D-005"></a>
**D-005 · Behavior Contract · 已接受（演练）**：确定性只针对相同候选数据和策略结果；其他工作流可改变任务状态，下次查询可能减少或改变标的。只读不意味着跨请求结果稳定，也不增加本次请求的快照、锁、缓存或隔离级别承诺。来源：AC-004、TC-007。边界：无查询写入、跨请求状态或一致性机制；下游验证“同数据同输出”和“状态变更后可变输出”两类断言，不能把后者当违约。

排序发生在全部候选成功处理之后；末项策略错误也不能返回已收集列表。单个不受限项跳过并继续下一项；零候选或只有不受限候选返回成功空列表。字符串排序按 Go 字符串字典序表达升序，不引入区域化排序或证券主代码排序。

#### 4.1.5 不变行为与验证

必须保持仓储单查询、原候选条件、处理器注册与策略校验、Redis 投影/写入/释放/闸门语义；差异检查对应源码路径后，运行既有回归测试并新增源场景映射中的行为测试，见 [Verification Strategy](#verification)。本次未执行这些实现检查。

### 4.2 内部 Service 与装配

服务只把 `business_date` 交给 biz，把成功列表映射到 `symbols`，把错误沿现有 inner 转换返回。增加的小查询能力经 `Service` 和 `InnerUsecases` 注入；不将校验、策略、排序挪入服务层。精确协议与错误分别由 [D-006](#D-006)、[D-007](#D-007) 维护。

`HasPendingExecutionToday` 与 `ListClearingReconciliationDetails` 的 RPC 注册、请求、回复及错误契约保留。后续测试需要用已有 mock/fake 边界验证 service 委派及错误返回，并检查既有 RPC 注册仍可用，不能只测试新方法。

### 4.3 Proto 与生成入口

<a id="D-008"></a>
**D-008 · Operational Contract · 已接受（演练）**：增加 inner proto 生成脚本，使用 `protoc 34.1`、`protoc-gen-go v1.31.0`、`protoc-gen-go-grpc 1.3.0`，与现有 admin 脚本版本一致；inner 不生成 go-http。修改 proto 源并由工具生成代码，禁止手工编辑生成代码。来源：source.md 的生成选择及 AC-008。边界：不改 admin 契约，不猜包路径、include 参数或生成目录；下游必须核对实际 admin 脚本、生成输入与产物差异，版本和生成命令验证尚未执行。

## 七、接口设计

### 7.1 接口设计原则

继续使用既有集群内 unary gRPC 与 inner 错误转换。字段业务校验在 biz；不增加错误规范化中间件。请求重复调用没有新增写效果，但响应稳定性仅按 [D-005](#D-005) 判断。

### 7.2 接口清单

| 接口 | 调用方 | 服务方 | 权限边界 |
|---|---|---|---|
| `ListTradingRestrictedSymbols` | 集群内调用方，具体身份未提供 | `CorporateActionInnerService` | 既有集群内 gRPC；无 HTTP/Gateway 或认证变更 |

### 7.3 接口明细

<a id="D-006"></a>
**D-006 · Interface Contract · 已接受（演练）**：新增 `CorporateActionInnerService.ListTradingRestrictedSymbols`；请求包含 `string business_date`，回复包含 `repeated string symbols`。成功空结果是零个元素的列表；失败无回复消息，不得发送部分成功列表。来源：AC-002、AC-003、AC-004、AC-006、AC-007、AC-008。边界：不修改既有 RPC 定义，不承诺 JSON 或 HTTP 表示；下游核对字段映射、生成注册和旧方法兼容性。

| 字段 | 类型 | 约束、缺省及来源 |
|---|---|---|
| 请求 `business_date` | string | 业务必填；缺省空字符串进入既有缺失日期错误；格式 `YYYY-MM-DD` |
| 回复 `symbols` | repeated string | 成功时的精确唯一升序列表；无匹配时零元素；值来自 [D-004](#D-004) |

fixture 未给出 proto package、请求/回复 message 名称和字段编号；此处不伪造完整 gRPC 路径或已批准的编号。依据真实 proto 确认局部命名与未占用编号，不得改旧编号；见 [Q-002](#questions)。

<a id="D-007"></a>
**D-007 · Interface Contract · 部分已接受、错误细节待补证**：日期错误精确沿用下表；其他错误沿既有 inner 转换传播，整次失败，无回复。来源：AC-002、AC-007。边界：不能把内部 detail 宣称为线路 message，不新造业务错误码或中间件；下游需验证 service 实际转换，并补齐 [Q-001](#questions) 后再宣称完整错误契约就绪。

| 触发 | biz 内部错误 | 调用方线路结果 |
|---|---|---|
| 空日期 | CodeError `427012`，detail `business_date_required` | gRPC `Internal`；message `error_code=427012`；无回复 |
| 非法日期，如 `2026/09/07` | CodeError `427012`，detail `business_date_invalid` | gRPC `Internal`；message `error_code=427012`；无回复 |
| 仓储、注册解析或策略校验返回错误 | 保留原有错误及既有传播方式 | 由既有转换决定；fixture 未给出各错误的具体 status/message；无回复 |
| 受限任务保存的 symbol 为空 | 必须返回错误；具体错误类型、编码未提供 | 必须失败且无回复；具体 status/message 待补证 |

日期的内部 detail 不在 wire 上，调用方不能根据线路文案区分缺失与格式错误。对未提供映射的错误，不将其统称为 `Internal`、`InvalidArgument` 或其他新约定。
