## 二、需求信息

### 2.1 需求背景

为集群内部调用方增加按业务日期返回交易受限标的的只读 RPC。唯一需求及仓库事实来源为 [read-only-rpc.md](source.md) 的 Request、Repository facts and accepted choices、Acceptance、Scenarios。本次没有 intake package；夹具的 AC/TC 即本次覆盖基线，不代表真实 corporate-action 项目已批准需求。

现有符号名和行为均来自夹具，本文没有获得文件路径、实际调用方名称、Go 版本、测试结果或运行负载。

### 2.2 需求范围

| AC | 必须满足的行为 |
|---|---|
| AC-001 | 按业务日期复用候选任务和 handler 策略 |
| AC-002 | 缺失/非法日期沿既有校验错误失败 |
| AC-003 | 无符合限制条件的任务时成功空列表 |
| AC-004 | 原始字符串去重、升序；相同输入与策略结果确定，不冻结后续请求 |
| AC-005 | 排除删除、终态、已释放、非 US、record-only 记录 |
| AC-006 | 仅输出 task.Symbol，不取 decision.Symbol 或 normalized_underlying_symbol |
| AC-007 | 仓库、注册表、策略或受限空标的失败则整次失败；非限制结果跳过 |
| AC-008 | 保护已有 RPC、Redis、候选查询和 handler 契约 |

范围和非目标由 [概要设计 §1](概要设计.md#1-背景与范围) 维护。辅助 lenses：`architecture-designer`、`go-style`。`kratos` 的检测规则已阅读，但夹具未确认框架，不套用其框架约定；不因 proto/biz 命名推定 Kratos。没有 SQL 或持久化变更，不制定新查询、索引或并发控制方案。

## 三、概要设计

### 3.1 方案总述

在既有 `TradingRestrictionUsecase` 新增查询能力，用当前候选查询与策略函数判断资格，再按原始任务标的构造结果。架构、主流程和模块边界的唯一完整位置为 [概要设计 §2～3](概要设计.md#2-总体设计)；本章不复制 3.2～3.5。

夹具未提供容量或性能验收数值。可以从处理过程推导：若有 n 个候选、k 个不同受限标的，新增投影包含 n 次遍历和 k 个字符串排序，内存容纳候选及唯一标的集合；这不是已测性能结论，也不包含既有仓库或策略的成本保证。

### 3.6 专项设计与架构一致性检查

## 四、详细设计

### 4.1 TradingRestrictionUsecase 查询

#### 4.1.1 需求内容

入口为新增 biz 查询方法（拟与 RPC 同名 `ListTradingRestrictedSymbols`；最终签名沿真实仓库风格核实）。接受业务日期字符串，输出标的字符串集合或错误。协议类型留在 service，biz 不需要依赖 proto 回复类型。

#### 4.1.2 方案设计

<a id="D-003"></a>
**D-003 · Behavior Contract**

- 来源：AC-002。
- 决策：复用 `validateRequiredDateLayout` 校验必填及 `YYYY-MM-DD` 格式；日期缺失或非法在仓库调用之前失败。分别沿用 CodeError 427012 的 `business_date_required` 与 `business_date_invalid` 内部 detail。
- 边界：不增加日历、交易日或日期区间规则，不新增 trim/宽松解析行为；其他输入细节遵守既有 validator。
- 下游要求：TC-002 断言仓库调用次数为 0，并分别验证内部错误和 wire 契约。

<a id="D-004"></a>
**D-004 · Data Contract**

- 来源：AC-001、AC-005、AC-008。
- 决策：日期有效后，仅调用一次 `TradingRestrictionRepository.ListTradingRestrictionCandidates(businessDate)`；该既有查询选取日期匹配的 US 任务，`delete_time` 为 null/zero，状态既不是 `completed` 也不是 `no_action`，且 `restriction_released_at` 为 zero。record-only RIC 不属于任务数据源。
- 边界：不修改既有查询，不新增二次查询、SQL、事件类型过滤、数据源或迁移。上述资格由仓库负责，新 biz 方法不重新实现候选筛选。
- 下游要求：复核真实仓库契约与夹具一致；TC-004 验证排除项并覆盖 no_action；TC-006 防止仓库查询行为变化。

<a id="D-005"></a>
**D-005 · Behavior Contract**

- 来源：AC-001、AC-007、AC-008。
- 决策：对每个候选调用 `tradingRestrictionDecisionForTask`，使用既有 registry 和对 `TradingRestriction` 结果的验证。返回 `Restricted=false` 时跳过该任务。股息、市场转移策略返回 false；拆股、合股、退市、改名策略限制。注册表或策略错误立即返回。
- 边界：这些事件是既有策略证据，不构成 RPC 的类型白名单；不改变 handler，不忽略错误，不改 Redis 调用策略方式。
- 下游要求：验证 false 跳过和错误终止；新增事件策略将由既有 registry 路径自然决定，不得额外维护 RPC 类型清单。

<a id="D-006"></a>
**D-006 · Data Contract / Behavior Contract**

- 来源：AC-003、AC-004、AC-006、AC-007、AC-008。
- 决策：仅在策略确认 Restricted 后读取 `task.Symbol`。若精确等于空字符串，整次查询失败；其余按字符串精确值去重，使用 Go 常规字符串升序排序。AAPL 与 AAPL.US 是不同值。不做大小写、后缀、空白或 Unicode 归一化。零候选或全 false 成功返回空列表。
- 边界：不选 `decision.Symbol`，不选 `normalized_underlying_symbol`，不调用 Redis 的 `restrictedSymbolsFromTasks` 投影。后者继续归一化 decision.Symbol 并保留首次出现顺序。false 任务不会进入 RPC 的空标的校验，但既有策略函数自身的验证仍先执行。
- 下游要求：验证精确去重和乱序输入排序、单元素、全重复、AAPL/AAPL.US 区分及受限空字符串失败。空标的错误具体类型待 §11.2 核实，不发明新错误码。

#### 4.1.3 流程步骤

1. 校验日期；失败直接返回错误。
2. 调用一次既有仓库方法；失败直接返回错误。
3. 遍历候选，调用既有策略函数；失败丢弃请求内已积累的结果。
4. false 跳过；true 检查任务原始标的非空，加入精确字符串集合。
5. 将集合转换为升序列表，成功返回。内部使用 nil 或空 slice 不影响 protobuf repeated 的零元素语义，不增加 JSON 契约。

#### 4.1.4 边界条件

| 场景 | 处理与调用方感知 |
|---|---|
| 缺失或无效日期 | 校验先行；仓库调用为 0；wire 错误见 D-008 |
| 零候选、全 false、单元素、全重复 | 分别为空列表、空列表、一个值、一个值；均成功 |
| 合法候选之后出现坏 handler/策略/受限空标的 | 整次失败，没有部分列表 |
| 非限制任务的空标的 | 既有策略成功返回 false 后跳过，不应用受限标的校验 |
| 重复或并发请求、外部任务状态变化 | 按 D-002 每次计算；无持久化副作用，无跨请求固定结果承诺 |
| 仓库或策略错误、依赖超时 | 返回既有错误转换结果；不新增超时值、重试或兜底；实际 context/超时契约待核实 |
| 存量受限任务的 symbol 为空 | 采用已接受 corruption rule 整次失败，不跳过、不回填、不取替代字段 |

这些分支利用既有返回错误诊断，不增加日志、告警或补偿系统。

#### 4.1.5 不变行为

| 行为 | 原因 | 验证方式 |
|---|---|---|
| 仓库候选条件和查询次数 | 既有候选来源为权威 | 对照仓库契约和差异；查询调用计数 |
| handler 注册及结果验证 | 限制策略继续只有既有所有者 | 回归已有 handler 契约，检查没有类型白名单 |
| Redis 写入、释放和 gate | 新 RPC 不承担执行限制的控制流程 | TC-006 回归及最终调用依赖检查 |

### 4.2 内部 service 与依赖注入

#### 4.2.1 需求内容

在 `CorporateActionInnerService` 接收新一元 RPC，通过小型查询接口调用现有 biz owner，兼容已有两个 RPC。

#### 4.2.2 方案设计

接口字段归 §7 的 D-007 所有；错误归 D-008 所有。沿已有 `Service` 和 `InnerUsecases` 注入现有 `TradingRestrictionUsecase`，具体构造函数及字段名待核实。service 不筛选任务、不校验日期、不排序，不依赖 Redis。

#### 4.2.3 流程步骤

1. 将 request 的业务日期传给 biz 查询，沿既有模式传递调用方 context。
2. biz 出错则沿既有错误转换返回错误，不创建成功 reply。
3. 成功则把 strings 映射到 reply 的 repeated 字段。

#### 4.2.4 边界条件

空列表是成功；错误是失败且无 reply。权限沿既有 inner 边界，未提供具体鉴权机制，不臆造角色或 token 要求。proto 元数据和已有生成器对新增方法的注册方式须在落地时核实。nil request 的现有处理习惯未提供，本文不另建与既有服务不一致的规则。

#### 4.2.5 不变行为

`HasPendingExecutionToday`、`ListClearingReconciliationDetails` 的签名、注册与行为应保持；验证方式为既有契约回归和 proto/生成差异审查。错误转换、鉴权及 HTTP/Gateway 配置保持；检查新字段映射之外没有 middleware 或暴露面变化。

### 4.3 inner proto 生成

#### 4.3.1 需求内容

增加可复现的 inner 生成脚本，版本与夹具给出的现有 admin 脚本一致。

#### 4.3.2 方案设计

<a id="D-009"></a>
**D-009 · Operational Contract**

- 来源：AC-008，以及夹具的生成工具选择。
- 决策：inner 脚本使用 protoc 34.1、protoc-gen-go v1.31.0、protoc-gen-go-grpc 1.3.0；省略 go-http。proto 和脚本是输入，生成 Go 文件从工具产生，禁止手改。
- 边界：不升级 admin 工具、不凭空指定 proto package/go_package 或生成路径；不编造生成命令已经成功。
- 下游要求：真实仓库确认脚本调用约定与输出范围，验证版本及可重复生成，复核旧 RPC 和新增 gRPC 注册，排除新增 HTTP 产物。

#### 4.3.3 流程步骤

在真实项目中应核对现有 inner proto 元数据和 admin 脚本调用约定，扩展 proto 输入后用上述版本生成，并检查差异。这是生成契约说明；本演练没有执行生成或安装工具。

#### 4.3.4 边界条件

工具缺失或版本不匹配应作为生成检查失败报告，不能手改生成结果绕过。旧服务实现是否需要新增 stub 由实际生成结果验证，不能仅凭接口增量假定编译通过。

#### 4.3.5 不变行为

admin 生成行为和版本、既有 RPC 及 HTTP 暴露面保持；通过脚本/生成结果 diff 和已有契约测试确认。

## 七、接口设计

### 7.1 接口设计原则

仅集群内 unary gRPC，复用当前权限与错误转换。注释应说明日期必填、原始标的口径、成功空列表和失败无回复。没有 HTTP、分页、交易日规则或请求写入语义。

### 7.2 接口清单

| 接口 | 调用方 | 服务方 | 权限/幂等 |
|---|---|---|---|
| ListTradingRestrictedSymbols | 集群内调用方，具体服务待核实 | CorporateActionInnerService | 既有 inner 权限；只读无副作用，相邻结果可变化 |

### 7.3 接口明细

#### 7.3.1 ListTradingRestrictedSymbols

<a id="D-007"></a>
**D-007 · Interface Contract**

- 来源：AC-001～AC-008，以及夹具的 RPC 形状选择。
- 决策：新增 `CorporateActionInnerService.ListTradingRestrictedSymbols`，请求为 `business_date` string，回复为 `symbols` repeated string。字段语义如下。成功返回 reply；失败没有 reply。
- 边界：不新增 HTTP annotation、分页字段或额外数据；完整 gRPC 路径中的 proto package、消息名和字段编号未提供，不将推测写成已确认 wire 定义。
- 下游要求：核实真实 proto 元数据，保持旧方法和字段编号；验证 wire 状态、零结果以及 service/biz 映射。

| 方向 | 字段 | 类型 | 必填/默认 | 语义 |
|---|---|---|---|---|
| 请求 | business_date | string | 业务必填；未提供时为空字符串并校验失败 | YYYY-MM-DD，经既有 validator 校验 |
| 回复 | symbols | repeated string | 成功时可为零元素 | 精确 task.Symbol 去重升序集合；不是 Redis key，也不是归一化值 |

示例：`business_date="2026-09-07"`，夹具 TC-001 数据下返回 `symbols=["AAPL", "AAPL.US"]`。本例是设计期预期，不是执行结果。

<a id="D-008"></a>
**D-008 · Interface Contract / Behavior Contract**

- 来源：AC-002、AC-007，以及夹具的 inner 错误转换约定。
- 决策：缺失/非法日期是内部 CodeError 427012，detail 分别为 business_date_required / business_date_invalid；现有 inner wire 转换为 gRPC `Internal`，message 为 `error_code=427012`，内部 detail 不出现在 wire。其余错误沿既有转换传播。任何仓库、注册表、策略或受限空标的失败，都使请求失败且无回复，无部分 symbols。
- 边界：不改成 InvalidArgument，不新加错误归一化 middleware，不把失败变成 OK 空列表，不虚构非日期错误的 code/message。
- 下游要求：分层测试校验业务错误和实际 wire 错误；对未知的空标的错误类型先补证据再固定精确断言。

| 条件 | biz 结果 | wire 结果 |
|---|---|---|
| 空日期 | CodeError 427012 / business_date_required | Internal；error_code=427012；无 reply |
| 非法日期 | CodeError 427012 / business_date_invalid | Internal；error_code=427012；无 reply |
| 仓库/注册表/策略失败 | 返回既有错误 | 现有 inner 转换；具体状态随既有错误，不新指定 |
| Restricted 且 task.Symbol 为空 | 整次失败；具体错误构造待核实 | 现有 inner 转换；无 reply，不承诺未提供的 code |
| 无受限标的 | 成功空集合 | OK，symbols 零元素 |

## 八、系统发布

### 8.3 关联系统/功能影响

<a id="D-010"></a>
**D-010 · Operational Contract**

- 来源：AC-008，以及夹具接受的发布与回滚规则。
- 决策：先发布支持新 RPC 的服务，再发布调用方。服务回滚到不含新方法的版本后，调用方可能收到 `Unimplemented`，必须按请求失败处理。
- 边界：不加兼容 shim、重试、Redis 兜底或假空列表；查询无数据写入，不需要本功能的数据迁移/回滚。
- 下游要求：联调覆盖新调用方遇旧服务/回滚服务的失败状态。具体发布系统、维护者和回滚触发标准由真实项目约束核实。

### 8.4 回滚方案
