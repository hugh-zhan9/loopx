# plan runtime 按 ralplan 模式落地的架构文档

## 目标

将 `loopx plan` 从当前的轻量产物生成阶段，升级为真实的规划运行时闭环：

- Planner 起草
- Architect 评审
- Critic 把关
- 在批准后停止

该闭环只覆盖规划阶段，不负责执行阶段调度。

## 当前问题

- skill 文档已经声明 `plan` 默认是共识规划
- runtime 仍然只生成计划产物并直接标记完成
- status 无法显示规划评审进度
- `docs/` 中文文档没有进入完成判定

## 目标架构

### 运行时分层

1. `plan` 入口层
   - 解析 slug / spec path
   - 加载 clarify 或 deep-interview 产物
   - 初始化或恢复 plan 状态

2. 规划闭环层
   - Planner 生成 draft
   - Architect 审查 draft
   - Critic 给出 verdict
   - 非 approve 时进入下一轮修订

3. 产物层
   - canonical:
     - `.LoopX/plans/prd-<slug>.md`
     - `.LoopX/plans/test-spec-<slug>.md`
   - 中文 docs:
     - `docs/<slug>/架构文档.md`
     - `docs/<slug>/设计文档.md`
     - `docs/<slug>/测试计划.md`
   - review evidence:
     - planner draft evidence
     - architect review evidence
     - critic verdict evidence

4. 状态与展示层
   - `state.json` 保存 iteration / architect / critic / artifact gate
   - `loopx status` 展示规划阶段进度

5. 适配层
   - production adapter：负责真实 Planner / Architect / Critic 编排
   - test adapter：负责 deterministic fixture 结果

## 关键架构约束

- Architect 和 Critic 必须串行，不能并行
- `plan` 不得自动进入 `build` 或 `autopilot`
- `docs/<slug>/` 下三份中文文档是阻塞产物
- approved plan 仍以 `.LoopX/plans/prd-<slug>.md` 为 canonical

## 状态机建议

- `plan_current_iteration`
- `plan_max_iterations`
- `plan_consensus_mode`
- `plan_architect_review_status`
- `plan_critic_verdict`
- `plan_package_status`
- `plan_docs_status`
- `plan_acceptance_criteria_testable`
- `plan_verification_steps_resolved`
- `plan_review_artifact_paths`

## 完成判定

只有满足以下条件时，`plan` 才能算完成：

- Planner draft 已生成
- Architect review 完成
- Critic verdict = `approve`
- `.LoopX/plans/prd-<slug>.md` 存在
- `.LoopX/plans/test-spec-<slug>.md` 存在
- `docs/<slug>/架构文档.md` 存在
- `docs/<slug>/设计文档.md` 存在
- `docs/<slug>/测试计划.md` 存在
- 三份 docs 内容为中文

## 非目标

- 不做执行阶段编排
- 不引入 `team` 作为公开 LoopX surface
- 不把 approved plan 移到 `docs/`
