## 二、需求信息

### 2.1 需求背景

- 背景：当前 `clarify` 输出单文件 `.loopx/intake/clarify-<slug>-YYYY-MM-DD.md`，需求契约、澄清过程、测试口径混在一起。用户希望吸收 Harness Engineering 中 “`requirements.md` 与 `test-cases.md` 同源” 的做法，让需求阶段就固定验收/集成测试场景。
- 需求目的：把 `clarify` 升级为 P1 intake package 生成器，明确需求、澄清记录和测试场景三类产物的边界。
- 目标用户/使用方：使用 loopx skills 的 Codex/Claude 风格 coding agent，维护 loopx workflow 的开发者，以及后续执行 `spec`、`plan-to-exec`、`final-review` 的 agent。
- 需求链接：当前对话；[Harness Engineering 对 loopx 的可吸收点](../../../articles/harness-engineering-loopx-takeaways.md)。
- 关联原始材料：
  - [设计提案](./设计提案.md)
  - `skills/clarify/SKILL.md`
  - `skills/spec/SKILL.md`
  - `skills/plan-to-exec/SKILL.md`
  - `src/workflow.mjs`
  - `src/cli.mjs`
  - `docs/loopx/specs/installation.md`
  - `docs/loopx/design/loopx-skill-suite-v1-design.md`

### 2.2 需求范围

- 本期范围：
  - 新 `clarify` 输出目录式 intake package。
  - 固定 `clarification.md`、`requirements.md`、`test-cases.md` 三个 artifact 的职责和模板。
  - `spec` 与 `plan-to-exec` 支持 intake package 目录输入。
  - CLI state 增加 intake package 字段，并保留 `spec_artifact_path` 兼容字段。
  - 更新 skill 文档、resolver/docs/README 里涉及 clarify source 和 handoff 的描述。
  - 更新治理测试和 workflow tests。
- 非目标：
  - 不新增 `acceptance-testcase-generator` skill。
  - 不生成可执行测试脚本。
  - 不迁移历史 `.loopx/intake/clarify-*.md`。
  - 不改变主流程顺序。
  - 不新增 mandatory CLI state machine。
- 决策边界：
  - `clarify` 负责 P1 intake package，不写实施计划，不改代码。
  - `requirements.md` 是确认后的需求契约。
  - `test-cases.md` 是黑盒验收/集成测试场景，不是单元测试文件。
  - `clarification.md` 是追溯和 resume 文件，不覆盖 `requirements.md`。
- 依赖方：
  - `spec` 读取 intake package 做设计。
  - `plan-to-exec` 读取 intake package 做实施计划。
  - CLI `status`/`clarify` 输出展示 intake paths。
  - tests 验证 skill governance 和 runtime 状态。
- 约束条件：
  - 保持 public CLI command signatures 不变。
  - JSON mode 新增字段，不删除旧字段。
  - `.loopx/` runtime state 不默认提交。
  - 支持旧单文件 clarify source 的读兼容。
- 触发的辅助 skills：`cli-developer`、`architecture-designer`

### 2.3 可行性分析

- 业务可行性：需求已澄清；用户明确选择目录格式，并要求 `test-cases.md` 成为独立测试场景文件。
- 技术可行性：当前 `workflow.mjs` 已集中处理 intake path 生成；skill docs 明确下游 source 规则；变更可以局部落在 workflow runtime、CLI output、skills 和测试。
- 团队接受能力：目录式 artifact 更符合 skill-first 和 Harness 文章的 P1 语义，维护成本可控。
- 时间成本：中等。涉及多个 skill 文档和 runtime/test，但不需要新依赖。
- 资源成本：极低。新增本地 markdown 文件。
- 替代方案：保留单文件加 section、先加 `Test Case Seeds`、新增 generator skill。均在提案中拒绝。
- 关键风险：
  - 下游 skills 没有同步读取 `test-cases.md`，导致测试场景仍被忽略。
  - `spec_artifact_path` 命名与新语义不一致，可能继续误导维护者。
  - 目录命名冲突处理不清导致重复 clarify 覆盖旧产物。

## 三、概要设计

### 3.1 方案总述

- 设计目标：让 `clarify` 产出结构化 P1 intake package，使需求契约和验收/集成测试场景同源。
- 总体思路：把旧单文件 artifact 替换为目录；以 `requirements.md` 为 source of truth，以 `test-cases.md` 为测试场景 source，以 `clarification.md` 为追溯和 resume source。
- 核心模块：
  - `skills/clarify/SKILL.md`
  - `skills/spec/SKILL.md`
  - `skills/plan-to-exec/SKILL.md`
  - `src/workflow.mjs`
  - `src/cli.mjs`
  - `test/skill-governance.test.mjs`
  - `test/workflow.test.mjs`
- 主要难点：
  - 新目录格式与旧单文件格式的兼容边界。
  - `AC-*` 与 `TC-*` 的同源约束。
  - CLI JSON 字段稳定性。
- 技术指标：
  - 新 `clarify` workflow 创建三份 intake artifact。
  - `status --json` 返回 package 和三份 child artifact path。
  - `spec`/`plan-to-exec` 文档明确目录输入和必读文件。
  - 治理测试覆盖 skill 文档契约。

### 3.2 整体架构设计

- 业务模式：用户从 `$clarify <feature>` 开始，agent 逐步澄清并更新 intake package；完成后按 route 交给 `$spec <package>` 或 `$plan-to-exec <package>`。
- 系统边界：
  - CLI/runtime 只创建和展示本地 artifact。
  - skills 决定如何填写和消费 artifact。
  - 下游执行仍由 `plan-to-exec`、`exec`、`subagent-exec` 完成。
- 上下游系统：
  - 上游：用户输入、PRD、issue、repo evidence。
  - 下游：`spec`、`plan-to-exec`、`final-review`。
- 应用架构：
  - `workflow.mjs` 生成 intake package path 和 state fields。
  - `cli.mjs` 渲染 human/JSON output。
  - bundled skills 约束 agent 行为。
- 技术架构：Node.js ESM，无新增依赖。
- 数据流转：

```text
user request / source docs
  -> clarify Q&A
  -> .loopx/intake/YYYY-MM-DD-<slug>/
       clarification.md
       requirements.md
       test-cases.md
  -> spec? or plan-to-exec
  -> implementation plan
```

### 3.3 核心流程设计

| 流程 | 触发条件 | 参与系统/模块 | 主流程 | 异常/补偿 | 输出 |
|---|---|---|---|---|---|
| 初始化 clarify intake package | 用户运行 `loopx clarify <slug>` 或 skill 创建 clarify artifact | `workflow.mjs`、`clarify` skill | 生成 package 目录和三份 markdown 模板，state 记录路径 | 目录冲突时生成唯一目录名 | intake package |
| 增量澄清 | 每轮 Q&A 后 | `clarify` skill | 更新 `clarification.md`、同步 `requirements.md` 和 `test-cases.md` 中已确认内容 | 未决项标 `[PENDING]`，Resume State 指向下一问 | 可恢复澄清状态 |
| handoff 到 spec | route 为 `needs_spec` | `clarify`、`spec` | 输出 `$spec .loopx/intake/YYYY-MM-DD-<slug>/` | 如果 package 缺文件，回到 clarify | 设计包 |
| handoff 到 plan | route 为 `direct_to_plan` | `clarify`、`plan-to-exec` | 输出 `$plan-to-exec .loopx/intake/YYYY-MM-DD-<slug>/` | 如果 AC/TC 不完整，blocked | 实施计划 |
| status 展示 | 用户运行 `loopx status` | `cli.mjs`、`workflow.mjs` | 展示 package 和 child paths | 旧 workflow 无 package 时展示旧 intake path | human/JSON status |

### 3.4 功能模块

| 模块 | 职责 | 关键功能 | 依赖 | 备注 |
|---|---|---|---|---|
| `clarify` skill | 定义 intake package 填写规则 | 三件套模板、AC/TC 规则、handoff gate | 用户回答、repo evidence | 不写计划 |
| `workflow.mjs` | 生成 runtime artifact 和 state | 目录命名、文件初始化、状态字段 | `.loopx/` runtime | 保留旧字段 |
| `cli.mjs` | 输出 human/JSON 状态 | `intake`、`requirements`、`test cases` path | workflow state | 不改命令签名 |
| `spec` skill | 消费 intake package | 必读 requirements/test-cases | intake package | 设计不能悄悄改 AC |
| `plan-to-exec` skill | 消费 intake package | 任务覆盖 AC，验证覆盖 TC | intake package | 不重新解释需求 |
| tests | 固化行为 | governance/runtime assertions | Node test | 更新旧断言 |

### 3.5 新增/调整功能说明

- `clarify` 输出目录：

```text
.loopx/intake/YYYY-MM-DD-<slug>/
```

- 固定文件：

```text
clarification.md
requirements.md
test-cases.md
```

- 新 state 字段：

```json
{
  "intake_package_path": "<absolute path>",
  "clarification_path": "<absolute path>",
  "requirements_path": "<absolute path>",
  "test_cases_path": "<absolute path>"
}
```

- 兼容字段：

```json
{
  "spec_artifact_path": "<absolute path to requirements.md>"
}
```

### 3.6 专项设计检查

| 辅助 skill | 触发原因 | 检查内容 | 设计结论 |
|---|---|---|---|
| `cli-developer` | CLI human/JSON output 会新增 artifact paths | 命令签名、stdout/JSON 稳定性、非交互行为 | 不新增命令；JSON 只增字段；human output 保持简洁 |
| `architecture-designer` | 跨 skill artifact contract 和兼容策略 | 边界、迁移、失败模式、长期维护 | 目录式 package 是长期契约；旧单文件只做读兼容 |

## 四、详细设计

### 4.1 clarify intake package 详细设计

#### 4.1.1 需求内容

- 入口：`$clarify <feature-or-problem>` 或 `loopx clarify <slug>` 初始化的 workflow。
- 操作人/调用方：用户、Codex/Claude style agent、loopx CLI。
- 前置条件：有明确 slug；`.loopx/` 可写。
- 输出结果：`.loopx/intake/YYYY-MM-DD-<slug>/` 下三份 markdown。

#### 4.1.2 方案设计

- 核心逻辑：
  - `clarify` 初始化时创建 package 目录。
  - 三个文件都从模板开始，未确认项标 `[PENDING]`。
  - 每轮 Q&A 后，`clarification.md` 记录问题和回答，`requirements.md` 更新确认后的需求契约，`test-cases.md` 更新可验证场景。
- 状态流转：
  - `blocked`：仍有 material question 或 AC/TC 不完整。
  - `needs_spec`：需求明确，但设计/API/数据/兼容等决策需要 spec。
  - `direct_to_plan`：需求、非目标、约束、AC、TC 都足够明确。
- 数据变更：只写 `.loopx/` runtime markdown 和 state JSON。
- 计算公式：无。
- 幂等设计：
  - 同 slug 重复运行不覆盖旧 package。
  - state 指向最新 package。
- 权限/越权控制：不涉及外部权限；遵守本地文件写权限。
- 异常处理：
  - 无法写目录时报错。
  - package 缺文件时 status 标明缺失。
- 补偿/重试：
  - 用户可重新运行 clarify 生成新 package。
  - 旧 package 保留，便于追溯。
- 日志与审计：state JSON 记录 artifact paths；markdown 保留过程证据。

#### 4.1.3 流程步骤

1. normalize slug。
2. 计算 package directory：`.loopx/intake/YYYY-MM-DD-<slug>/`。
3. 如果目录存在，生成唯一目录名，例如 `.loopx/intake/YYYY-MM-DD-<slug>-HHMMSS/`。
4. 创建 `clarification.md`、`requirements.md`、`test-cases.md`。
5. 写入 state 字段。
6. human output 展示 intake package 和 child paths。
7. 后续 Q&A 由 `clarify` skill 增量更新三份文件。

#### 4.1.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| slug 为空或不可规范化 | 抛 `workflow_slug_required` | CLI 报错 | 无 |
| 同日同 slug 已有 package | 追加短时间戳或序号 | status 指向新 package | 无 |
| `.loopx/intake/` 不可写 | 写入失败，非零退出 | 用户看到文件系统错误 | 无 |
| `requirements.md` 无 AC | 不能 handoff ready | `blocked` 或继续提问 | 无 |
| `test-cases.md` 无 TC | 不能 handoff ready，除非明确无可测场景并 blocked | `blocked` | 无 |
| 旧 workflow 只有 `spec_artifact_path` | 保持 status 可读 | 显示旧 intake path | 无 |

#### 4.1.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `loopx clarify <slug>` 命令签名 | public CLI surface | `node src/cli.mjs clarify sample --json` |
| 主流程 `clarify -> spec? -> plan-to-exec` | v1 skill-suite contract | README/docs governance tests |
| `.loopx/` 存放 runtime state | v1 artifact boundary | status/workflow tests |
| 旧 clarify source 可被 spec/plan 读取 | 兼容历史文档 | skill governance tests |

### 4.2 requirements.md 详细设计

#### 4.2.1 需求内容

- 入口：`clarify` 产出和每轮更新。
- 操作人/调用方：`clarify` skill、`spec`、`plan-to-exec`。
- 前置条件：至少有一个已确认 intent/scope/decision 后开始写。
- 输出结果：确认后的需求契约。

#### 4.2.2 方案设计

`requirements.md` 固定结构：

```markdown
# Requirements

## Source Facts
## Intent And Outcome
## Scope
## Non-goals
## Decisions
## Constraints
## Acceptance Criteria
## Open Questions
## Handoff Recommendation
```

AC 格式：

```markdown
### AC-001

WHEN <condition or user action>
THEN <observable system behavior>
AND <additional constraint>

Evidence target: integration | e2e | api | cli | unit | manual
Risk: high | medium | low
Status: confirmed | pending
```

规则：

- `Source Facts` 保留用户原话、PRD、issue 或 repo evidence，不混入 agent 推断。
- `Decisions` 只放已确认决策。
- `Open Questions` 中任意 blocking 问题存在时，不能 `direct_to_plan`。
- `Acceptance Criteria` 必须可测；不可测描述必须继续澄清或拆分。

#### 4.2.3 流程步骤

1. 从用户输入和 source docs 提取 source facts。
2. 逐轮确认 scope、non-goals、constraints。
3. 为每条验收标准生成稳定 `AC-*`。
4. 对不可测 AC 继续提问。
5. 选择 handoff route。

#### 4.2.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| 用户回答含糊 | 保持 `[PENDING]`，继续问 | 不能 ready | 无 |
| source doc 与用户回答冲突 | 标记 conflict，要求用户决策 | blocked | 无 |
| AC 描述不可测 | 改写或拆分 | 继续 clarify | 无 |
| API/data/security 等决策未定 | route `needs_spec` 或 blocked | 不进入 direct plan | 无 |

#### 4.2.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `clarify` 不写 implementation plan | skill boundary | skill governance |
| `plan-to-exec` 不发明产品行为 | downstream boundary | plan governance |

### 4.3 test-cases.md 详细设计

#### 4.3.1 需求内容

- 入口：`requirements.md` 中已确认或待确认的 AC。
- 操作人/调用方：`clarify` skill、`spec`、`plan-to-exec`、未来 `final-review`。
- 前置条件：存在至少一个 `AC-*`。
- 输出结果：需求阶段确定的黑盒验收/集成测试场景。

#### 4.3.2 方案设计

`test-cases.md` 固定结构：

```markdown
# Test Cases

## Coverage Summary

| AC | Test Cases | Coverage | Notes |
|---|---|---|---|
| AC-001 | TC-001, TC-002 | positive + boundary | |

## Cases
```

Case 格式：

```markdown
### TC-001

Source AC: AC-001
Type: integration | e2e | api | cli | manual
Priority: P0 | P1 | P2
Preconditions:
- ...
Steps:
1. ...
Expected:
- ...
Automation target: TBD | <command> | manual
Notes:
- ...
```

规则：

- `test-cases.md` 不写内部函数级单元测试。
- `Type: unit` 不作为推荐类型；只有需求明确要求单元级验证时才允许。
- 高风险 AC 至少有正向和失败/边界 case。
- 无法自动化必须写 manual reason。
- `Coverage Summary` 中出现未覆盖 AC 时，handoff 不能 ready，除非有明确 deferred rationale。

#### 4.3.3 流程步骤

1. 遍历 `requirements.md` 中 `AC-*`。
2. 为每条 AC 生成至少一个业务可观察测试场景。
3. 为高风险 AC 增加失败/边界场景。
4. 填写 Coverage Summary。
5. 对不可测或需要人工环境的场景标 manual。

#### 4.3.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| AC 没有任何 TC | 标记未覆盖，不能 ready | blocked 或 pending | 无 |
| TC 引用不存在的 AC | 文件不一致，下游停止 | 返回 clarify | 无 |
| TC 依赖尚未设计的内部实现 | 改写为外部可观察行为 | 不提前绑定实现 | 无 |
| 测试只能人工执行 | `Type: manual` 并写原因 | plan/final-review 可识别风险 | 无 |

#### 4.3.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `tdd` 仍负责实现阶段单元/回归测试纪律 | 职责清晰 | skill docs |
| `test-cases.md` 不生成测试脚本 | 避免扩大范围 | docs/governance |

### 4.4 downstream skill 消费详细设计

#### 4.4.1 需求内容

- 入口：`$spec .loopx/intake/YYYY-MM-DD-<slug>/` 或 `$plan-to-exec .loopx/intake/YYYY-MM-DD-<slug>/`。
- 操作人/调用方：agent。
- 前置条件：intake package 存在。
- 输出结果：设计文档或实施计划。

#### 4.4.2 方案设计

`spec` 更新：

- 在 Inputs 增加 intake package directory。
- 接收目录时，必读 `requirements.md` 和 `test-cases.md`。
- 按需读 `clarification.md`。
- 设计文档的需求信息引用 intake package。
- 测试和验证策略必须引用 `test-cases.md`。
- 如果设计发现需求/AC/TC 冲突，返回 `clarify`。

`plan-to-exec` 更新：

- 在 source list 增加 intake package directory。
- 接收目录时，必读 `requirements.md` 和 `test-cases.md`。
- 每个 task 绑定 `AC-*`。
- 验证步骤引用 `TC-*` 或说明 deferred rationale。
- Self-review 增加 AC/TC coverage 检查。

#### 4.4.3 流程步骤

1. 判断 source 是目录还是文件。
2. 如果是目录，检查三份固定文件。
3. 必读 `requirements.md` 与 `test-cases.md`。
4. 使用 `clarification.md` 解释历史问题和用户原话。
5. 生成设计或计划。

#### 4.4.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| source 是旧单文件 | 继续按旧 clarify output 读取 | 兼容 | 无 |
| source 是目录但缺 `test-cases.md` | 停止并要求回到 clarify | 明确缺失文件 | 无 |
| `test-cases.md` 与 `requirements.md` 冲突 | 停止并返回 clarify | 不自行调和 | 无 |
| plan 需要新增无 AC 支撑行为 | 禁止，返回 clarify/spec | 防止 scope creep | 无 |

#### 4.4.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `spec` 默认产出 `设计提案.md` 和 `需求设计文档.md` | existing spec contract | skill governance |
| `plan-to-exec` 输出位置不变 | existing plan contract | skill governance |

### 4.5 CLI runtime 详细设计

#### 4.5.1 需求内容

- 入口：`loopx clarify/status/next`。
- 操作人/调用方：用户和自动化脚本。
- 前置条件：workspace 初始化。
- 输出结果：runtime state 和 human/JSON 状态。

#### 4.5.2 方案设计

`workflow.mjs`：

- 新增 `canonicalIntakePackagePath(cwd, slug, stamp)`。
- 新增 child path helpers。
- `clarifyStage` 创建 package 目录和三份文件。
- state 增加:

```json
{
  "intake_package_path": "...",
  "clarification_path": "...",
  "requirements_path": "...",
  "test_cases_path": "..."
}
```

- `spec_artifact_path` 指向 `requirements_path`。

`cli.mjs`：

- human output:

```text
intake: .loopx/intake/YYYY-MM-DD-<slug>/
requirements: .loopx/intake/YYYY-MM-DD-<slug>/requirements.md
test cases: .loopx/intake/YYYY-MM-DD-<slug>/test-cases.md
```

- JSON output includes all state fields through existing payload.
- `next` command continues returning skill handoff, but should prefer package path once available.

#### 4.5.3 流程步骤

1. `loopx clarify <slug>` normalizes slug.
2. `workflow.mjs` creates package and state.
3. CLI prints concise human output.
4. `loopx status --json` includes package fields.
5. `nextSkillCommand` uses package path for `spec`/`plan-to-exec` when route is ready.

#### 4.5.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| old state lacks package fields | fallback to `spec_artifact_path` | status still works | 无 |
| JSON consumer expects `spec_artifact_path` | field remains | no break | 无 |
| human output path too long | display relative path when under cwd | readable | 无 |

#### 4.5.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `--json` required for complete payload | installation spec | CLI tests |
| `loopx next` returns skill handoff | installation spec | workflow tests |

## 七、接口设计

### 7.1 接口设计原则

- CLI 命令签名保持不变。
- JSON 字段新增不删除。
- human output 保持简洁，避免把完整 state 打到默认 stdout。
- path 使用 Node path API，展示时使用现有 relative-or-absolute 逻辑。

### 7.2 接口清单

| 接口 | 调用方 | 服务方 | 权限/认证 | 幂等 | 文档地址 | 备注 |
|---|---|---|---|---|---|---|
| `loopx clarify <slug> [--json]` | 用户/agent | `src/cli.mjs` | 本地文件权限 | 重复运行生成新 package，不覆盖旧 package | README / CLI docs | 输出 intake package |
| `loopx status [slug] [--json]` | 用户/automation | `src/cli.mjs` | 本地文件权限 | 只读 | README / CLI docs | 展示 package fields |
| `loopx next <slug> [--json]` | 用户/automation | `src/cli.mjs` | 本地文件权限 | 只读 | README / CLI docs | handoff 使用 package path |

### 7.3 接口明细

#### 7.3.1 `loopx clarify <slug> [--json]`

- 路径/方法：CLI command。
- 请求头：不涉及。
- 请求参数：
  - `slug`：必填，feature/workflow slug。
  - `--standard|--deep`：保持现有行为。
  - `--json`：输出完整 JSON payload。
- 响应参数：
  - human: workflow, stage, profile, blockers, open questions, round, intake, requirements, test cases, next skill/next action。
  - JSON: existing state plus `intake_package_path`、`clarification_path`、`requirements_path`、`test_cases_path`。
- 错误码：现有 CLI error handling。
- 业务校验：slug required。
- 数据变更：写 `.loopx/intake/YYYY-MM-DD-<slug>/` 和 workflow state。
- 日志字段：不新增。

#### 7.3.2 `loopx status [slug] [--json]`

- 路径/方法：CLI command。
- 请求参数：`slug` 可选，`--json` 可选。
- 响应参数：
  - human: package paths if workflow exists。
  - JSON: artifacts and state include package fields。
- 业务校验：旧 state fallback。
- 数据变更：无。

#### 7.3.3 `loopx next <slug> [--json]`

- 路径/方法：CLI command。
- 请求参数：`slug` 必填，`--json` 可选。
- 响应参数：next skill command。
- 业务校验：
  - 当 route ready 且 `intake_package_path` 存在时，handoff args 使用 package directory。
  - old state fallback 使用 existing slug/path behavior。
- 数据变更：无。
