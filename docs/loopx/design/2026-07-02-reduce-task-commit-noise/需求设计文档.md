## 二、需求信息

### 2.1 需求背景

- 背景：深度使用 loopx 后发现 `plan-to-exec` 生成的计划包含大量 per-task commit 步骤，`exec/subagent-exec` 忠实执行后导致 git history 噪声过多。
- 需求目的：让 plan 更轻量，集中描述逻辑、接口、测试和 review，而不是被 commit 指令填满。
- 目标用户/使用方：使用 loopx 主链路 `clarify -> spec -> plan-to-exec -> exec/subagent-exec -> final-review -> finish` 的 agent 和用户。
- 需求链接：`.loopx/intake/2026-07-02-reduce-task-commit-noise/`
- 关联原始材料：
  - `.loopx/intake/2026-07-02-reduce-task-commit-noise/requirements.md`
  - `.loopx/intake/2026-07-02-reduce-task-commit-noise/test-cases.md`
  - `.loopx/intake/2026-07-02-reduce-task-commit-noise/clarification.md`

### 2.2 需求范围

- 本期范围：
  - 修改 `plan-to-exec` 的任务模板和规划纪律，禁止新 plan 默认在每个 task 内写 `git commit`。
  - 修改 `subagent-exec` implementer 和 task reviewer 契约，task review 不再依赖 task commit 或 staging。
  - 修改 task review package 机制，使它能基于当前代码/工作区变更生成 review evidence。
  - 修改 `exec` 的提交策略说明，使 single-plan 默认最后一个 commit，multi-plan 默认每个 child plan 完成后一个 commit。
  - 更新治理测试和技能验证，锁定新契约。
- 非目标：
  - 不为历史 plan 的 per-task commit 指令保留兼容分支。
  - 不重写历史 plan 文档。
  - 不重新设计 `final-review` 或 `finish`，只保持它们对最终 `HEAD` 和 requirement start commit 的审计能力。
- 决策边界：
  - task review 是“当前代码是否满足 task contract”的门禁，不是“task commit 是否正确”的门禁。
  - Git 提交只发生在 plan 边界：single plan 完成后一次；multi-plan 每个 child plan 完成后一次。
  - 不用 per-task `git add` 替代 per-task commit。
- 依赖方：`skills/plan-to-exec`、`skills/subagent-exec`、`skills/exec`、`skills/review`、`skills/final-review`、`skills/finish`、`test/skill-governance.test.mjs`、`scripts/verify-skills.mjs`。
- 约束条件：项目尚未上线，可接受破坏性更新；canonical skill source 在 `skills/`，插件安装脚本从 canonical source 复制。
- 触发的辅助 skills：cli-developer。

### 2.3 可行性分析

- 业务可行性：提交历史减少，plan 可读性提高，符合深度使用反馈。
- 技术可行性：现有 `final-review` 已支持 `git diff` 和 `git diff --cached` 作为最终审计补充；task review package 可以从 commit range 扩展为 current worktree evidence。
- 团队接受能力：破坏性更新无需历史兼容，降低实现复杂度。
- 时间成本：中等，主要是多份技能文档、helper script、治理测试同步。
- 资源成本：无新增依赖。
- 替代方案：
  - 保持 per-task commit：拒绝，继续污染 git history。
  - 改为 per-task staging：拒绝，本质上仍把 Git 操作塞进 task 流程。
  - 只改 `plan-to-exec` 文案：拒绝，`subagent-exec` 和 review package 仍会把执行拉回 commit range。
- 关键风险：task review 失去 commit range 后，如果 review package 不清楚，reviewer 可能无法区分本 task 与前序 task 变化；需通过 task brief、progress ledger、working diff/context 和 implementer report 共同约束。

## 三、概要设计

### 3.1 方案总述

- 设计目标：减少自动化执行产生的 commit 数量，同时保留 task-level review 严格性和 finish 审计能力。
- 总体思路：把 task completion evidence 与 git commit 解耦；task review 消费当前代码和变更证据，git commit 延后到 plan/child-plan 边界。
- 核心模块：
  - `plan-to-exec`：生成不含 per-task commit 的 plan。
  - `subagent-exec`：implementer 不提交；reviewer 不要求 commit range。
  - `exec`：inline 执行同样遵守 plan 边界提交。
  - `review-package`：从 commit range package 改为支持 current worktree/task evidence package。
  - governance tests：阻止旧 per-task commit 契约回归。
- 主要难点：review evidence 要足够精确，避免 reviewer 只能看到累计 diff 时误判 task 范围。
- 技术指标：single-plan 执行默认只产生 1 个 implementation commit；multi-plan 默认每个 child plan 产生 1 个 implementation commit；task review 不需要 `git commit` 或 `git add`。

### 3.2 整体架构设计

- 业务模式：计划生成、执行、task review、final-review、finish 保持主链路不变，只调整提交边界和 review evidence。
- 系统边界：本设计只改变 loopx workflow skill contracts 和本仓库 helper scripts/tests，不改变用户项目代码行为。
- 上下游系统：上游是 clarified intake/spec；下游是 `plan-to-exec` 生成计划、`exec/subagent-exec` 执行、`review/final-review/finish` 审计。
- 应用架构：无运行服务；Node.js ESM CLI 和 Markdown skill contracts。
- 技术架构：shell helper scripts 继续放在 `skills/subagent-exec/scripts/`，skill governance 继续用 Node test。
- 数据流转：`plan-to-exec` 产出 plan -> executor 逐 task 修改工作区 -> task reviewer 读取 task brief/report/review package/current code -> plan/child-plan 结束统一 commit -> final-review/finish 审计 committed result。

### 3.3 核心流程设计

| 流程 | 触发条件 | 参与系统/模块 | 主流程 | 异常/补偿 | 输出 |
|---|---|---|---|---|---|
| Single-plan execution | 用户执行单文件 plan | `exec/subagent-exec`、task reviewer、final-review、finish | 启动 execution/finish baseline；逐 task 实现和 review；全部通过后统一 commit；final-review；finish | task review blocking 则 fix-review 后重审；最终 commit 失败则停止并报告 | 一个 implementation commit，完整 finish evidence |
| Multi-plan package execution | 用户执行 `00-overview.md` 或 package 目录 | package mode、child plan、task reviewer、final-review、finish | 按 child plan 顺序执行；每个 child plan 内不按 task commit；child plan 完成后 commit 一次并更新 state；全部 child 完成后 spec-level final-review；finish | child review blocking 则不进入下一 child；commit 失败则停止 | 每个 child plan 一个 implementation commit |
| Task review | task implementer 报告 DONE | `task-brief`、implementer report、review package、task reviewer | reviewer 检查 task brief、current code/evidence、测试结果和变更证据 | evidence 不足返回 NEEDS_CONTEXT；发现 Critical/Important 则 fix-review | task review verdict，不产生 Git commit/staging |

### 3.4 功能模块

| 模块 | 职责 | 关键功能 | 依赖 | 备注 |

| `exec` skill | inline 执行 | 遵守边界提交；checkpoint review 不要求 task commit | plan | final checkpoint 仍看 tracked changes |

### 3.5 新增/调整功能说明

#### Workflow Contract

- `D-001` / Source AC: `AC-001`, `AC-005` / workflow contract：新生成 single-plan 的默认 commit policy 是所有 tasks 和 required reviews 通过后，在 plan 边界创建一个 implementation commit。task steps 不得默认包含 `git commit` 或 `git add`。下游 `plan-to-exec` 必须把 commit guidance 放入 execution handoff 或 plan completion section，而不是每个 task。
- `D-002` / Source AC: `AC-006` / workflow contract：multi-plan package 的默认 commit policy 是每个 child plan 完成并通过 plan-level review 后创建一个 implementation commit；child plan 内 task 不提交。package-level final-review/finish 仍在所有 child plan 完成后运行。
- `D-003` / Source AC: `AC-002`, `AC-007` / workflow contract：`subagent-exec` implementer contract 不得要求 "Commit your work" 或返回 "Commits created" 作为成功条件。task success evidence 是 report fields、commands_run、evidence_summary、changed files 和 review package。
- `D-004` / Source AC: `AC-003`, `AC-007` / workflow contract：task review package 必须支持未提交、未暂存的 current worktree evidence。它可以包含 status、changed files、diff stat、full diff、task brief path、report path 和 optional base marker，但不得要求 task commit range 或 per-task staging。
- `D-005` / Source AC: `AC-004` / workflow contract：`final-review` 和 `finish` 的整体审计仍以 `execution-start` 的 requirement start commit、最终 `HEAD`、commit list、changed files、tracked status 为准。task review 去 commit 化不得削弱最终审计。
- `D-006` / Source AC: `AC-008` / compatibility contract：不实现历史 plan 兼容逻辑，不保留“历史 per-task commit 指令必须执行”的分支。旧计划若继续执行，按当前 workflow contract 处理。

## 四、详细设计

### 4.1 `plan-to-exec` 详细设计

#### 4.1.1 需求内容

- 入口：用户调用 `$plan-to-exec <source>`。
- 操作人/调用方：主 agent。
- 前置条件：requirements/spec 已明确。
- 输出结果：不包含 per-task commit 默认步骤的 implementation plan。

#### 4.1.2 方案设计

- 核心逻辑：删除或替换 `Frequent commits`、`"Commit" is a step`、task template 中的 `Step 5: Commit` 示例。任务步骤仍保持小粒度和 TDD，但把提交说明移到 plan completion policy。
- 状态流转：无运行时状态变化。
- 数据变更：仅修改 skill Markdown。
- 计算公式：不涉及。
- 幂等设计：重复生成 plan 应遵守同一 commit policy。
- 权限/越权控制：不涉及。
- 异常处理：source 不清仍返回 `clarify/spec`，不因 commit policy 填补需求缺口。
- 补偿/重试：不涉及。
- 日志与审计：plan 内保留 Expected execution evidence 和 review focus。

#### 4.1.3 流程步骤

1. 读取 source requirements/spec。
2. 生成 task steps，禁止默认 `git add`/`git commit`。
3. 在 plan header 或 execution handoff 中声明 commit policy：single-plan 最后一次 commit；multi-plan 每 child plan 一次 commit。
4. 保留 task evidence、review focus、commands_run 等非 Git 提交证据。

#### 4.1.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| 正常 single-plan | plan tasks 不含 commit step，completion policy 说明最终 commit | plan 更短，commit 集中 | governance test |
| 正常 multi-plan | child plan 内 tasks 不含 commit step，overview/child completion 说明 child 边界 commit | 每个 child plan 一个 commit | governance test |
| 非法输入/source 不完整 | 仍返回 clarify/spec | 不生成错误 plan | 不涉及 |
| 重复生成 | 输出遵守同一策略 | 无重复 commit 指令 | test |
| 并发 | 不涉及；plan generation 不并发写同一文件 | 不涉及 | 不涉及 |
| 遗留数据/历史计划 | 不迁移、不兼容保留 | 旧契约不再是当前行为 | governance scan |
| 回滚 | 回退 skill 文档即可 | 恢复旧策略会被测试暴露 | test failure |

#### 4.1.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `T-*` task anchors | 下游 traceability 依赖 | governance test |
| `Expected execution evidence` 和 `Review focus` | task review 仍需要严格证据 | governance test |
| plan save path | 用户工作流不变 | existing tests |

### 4.2 `subagent-exec` 和 task review 详细设计

#### 4.2.1 需求内容

- 入口：用户调用 `$subagent-exec <approved-plan>`。
- 操作人/调用方：controller agent、implementer subagent、task reviewer subagent。
- 前置条件：plan 已批准。
- 输出结果：task-level review 通过，工作区保留未提交改动，直到 plan/child-plan 边界 commit。

#### 4.2.2 方案设计

- 核心逻辑：implementer 执行 task、测试并写 report，但不 commit、不 staging。controller 生成 review package，task reviewer 读取 task brief、report、review package 和必要代码文件。
- 状态流转：progress ledger 记录 task complete、review clean、brief/report/review package path，不再记录 `commits <base7>..<head7>` 作为 task completion 证据。
- 数据变更：`.loopx/subagent-exec/` scratch reports 和 review packages 继续作为本地 workflow state。
- 计算公式：不涉及。
- 幂等设计：progress ledger 仍防止重复派发已完成 task。
- 权限/越权控制：reviewer read-only，不 mutate working tree/index/HEAD。
- 异常处理：review package 缺失或 evidence 不足时，reviewer 返回 `NEEDS_CONTEXT`；Critical/Important 通过 `fix-review` 处理。
- 补偿/重试：fix-review 后重建 review package 并重审。
- 日志与审计：report fields 继续记录 `task_anchor`、`source_ac`、`design_anchors`、`test_cases`、`commands_run`、`evidence_summary`、`remaining_risk`。

#### 4.2.3 流程步骤

1. `subagent-exec` 启动 `execution-start` 和 `finish-start`。
2. 对每个 task 生成 brief。
3. implementer 修改代码、运行测试、写 report，不提交。
4. controller 生成 current worktree review package。
5. reviewer 按 task contract 审查当前代码和 evidence。
6. review 通过后更新 progress ledger。
7. single-plan 所有 tasks 完成后统一 commit；multi-plan child 完成后统一 commit。

#### 4.2.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| task 完成但未提交 | 正常 review current worktree evidence | 不产生 commit | progress ledger |
| task 完成但未 staging | 正常；不要求 `git add` | 不污染 index | governance test |
| 多个 task 累计 diff | reviewer 用 task brief/report/evidence 判断当前 task；必要时查看命名文件 | 可能看到累计上下文，但 review 目标仍 task-scoped | reviewer self-check |
| implementer 意外 commit | controller 应报告 contract violation；plan 边界前不应接受为正常 task evidence | 用户看到异常 | governance / review finding |
| reviewer 需要更多上下文 | 返回 NEEDS_CONTEXT | 不继续下一 task | progress ledger |
| fix-review 后 | 重建 review package，重审 | task gate 保持严格 | review report |

#### 4.2.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| fresh implementer per task | 降低上下文污染 | skill governance |
| combined task review gate | 防止问题级联 | skill governance |
| `.loopx/subagent-exec/` scratch state | 不提交本地运行态 | git status / AGENTS.md |

### 4.3 `exec`、`final-review`、`finish` 详细设计

#### 4.3.1 需求内容

- 入口：`$exec <approved-plan>`、`$final-review`、`$finish`。
- 操作人/调用方：主 agent。
- 前置条件：plan 已批准，execution-start/finish-start 记录 baseline。
- 输出结果：边界 commit 后的最终审计仍完整。

#### 4.3.2 方案设计

- 核心逻辑：`exec` 和 `subagent-exec` 使用同一 commit policy。checkpoint review 可在未提交工作区上运行；final-review/finish 只要求最终 tracked changes 在 done 前进入 final `HEAD`。
- 状态流转：`execution-start` 记录 requirement start commit；`finish-start` 记录 finish baseline；final-review/finish 不保存 child task commit metadata。
- 数据变更：无新持久数据模型。
- 计算公式：不涉及。
- 幂等设计：finish-record 继续阻止 tracked dirty 状态标记 done。
- 权限/越权控制：不涉及。
- 异常处理：最终 commit 前 tests/reviews 未通过则不进入 finish。
- 补偿/重试：修复后重新 review 和 commit。
- 日志与审计：finish summary 保留 requirement start commit、final HEAD、commit list、changed files、tracked status。

#### 4.3.3 流程步骤

1. 执行开始记录 baseline。
2. task/checkpoint review 可基于未提交 diff。
3. single-plan 在所有 task 和 required review 通过后 commit 一次。
4. multi-plan 每个 child plan 通过 plan-level review 后 commit 一次。
5. final-review 读取 start commit、current HEAD 和必要 tracked diff。
6. finish-audit/finish-record 保持现有 done gate。

#### 4.3.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| final-review 前仍有 tracked changes | 允许 final-review 包含 tracked diff；finish done 前必须进入 HEAD | 审计不丢失 | final-review report |
| finish-record 时 tracked dirty | 继续阻止 done | 明确错误 | existing tests |
| untracked files | 保持现有“untracked clean/report-only”规则 | 不阻塞 done | existing tests |
| multi-plan child state | 不记录 child start/current/end commit metadata | state 更简单 | existing tests |
| 回滚 | 使用最终 commit 或 child commit 回滚 | history 粒度是 plan/child-plan | git log |

#### 4.3.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `execution-start` requirement identity | final audit 依赖 | workflow tests |
| `finish-start` baseline | finish-audit 依赖 | workflow tests |
| tracked dirty blocks finish done | 防止未提交变更漏审 | workflow tests |

## 七、接口设计

### 7.1 接口设计原则

- 本设计不新增 public CLI command。
- `skills/subagent-exec/scripts/review-package` 是内部 helper，但仍需保持脚本化：成功时 stdout 只输出 review package path；错误和 usage 输出 stderr；失败返回非零 exit code。
- 不引入交互式 prompt。
- 不要求 per-task staging 或 commit 作为参数前置条件。

### 7.2 接口清单

| 接口 | 调用方 | 服务方 | 权限/认证 | 幂等 | 文档地址 | 备注 |
|---|---|---|---|---|---|---|
| `scripts/review-package` | `subagent-exec` controller | shell helper | local git repo | 重复运行生成新的或覆盖指定 package 均可，由计划决定 | `skills/subagent-exec/references/task-handoff-and-review.md` | 需支持 current worktree evidence |
| skill Markdown contracts | Codex/Claude/Cursor agents | loopx skill files | local filesystem | 文档读取幂等 | `skills/*/SKILL.md` | canonical source |

### 7.3 接口明细

#### 7.3.1 `scripts/review-package`

- 路径/方法：`skills/subagent-exec/scripts/review-package`
- 请求头：不涉及。
- 请求参数：
  - 设计允许实现阶段选择一个破坏性新签名，例如 `review-package --worktree TASK_ANCHOR [OUTFILE]`，或保留 positional 但让 `BASE HEAD` 可选。
  - 无论具体签名如何，不能要求 task commit range。
- 响应参数：stdout 输出生成的 review package 绝对路径。
- 错误码：参数非法、非 git repo、diff 生成失败时返回非零。
- 业务校验：不得因存在 unstaged changes 而失败；不得要求 `git add`。
- 数据变更：只写 `.loopx/subagent-exec/` scratch package 或调用方指定 outfile。
- 日志字段：package 内至少包含 status、changed files、diff stat、full diff、task/report references。

## 八、系统发布

### 8.1 灰度方案

- 降级行为：回退本次 skill/helper/test 变更。
- 用户影响：短期恢复多 commit 旧行为。

- 配置回滚：不涉及。
