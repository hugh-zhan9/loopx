# 主链路 workflow completion 设计提案

Author(s): loopx maintainers
Last updated: 2026-06-30
Status: Draft
Discussion: 不涉及
Source requirements: `.loopx/intake/2026-06-30-main-chain-workflow-completion/`
Support lenses: architecture-designer

## Abstract / 摘要

本提案建议把 `docs/articles/harness-engineering-loopx-takeaways.md` 中仍未完成、且属于主链路的改造收敛到一条端到端 workflow contract：

```text
clarify AC/TC
-> spec D
-> plan-to-exec T
-> exec/subagent-exec verification evidence
-> review AC/D/T coverage or findings
-> final-review requirements coverage + Test Trust
-> finish final-review gate + learning/spec/delta candidates
```

本次只更新主链路 skill 合约和必要治理测试，不实现本地 metrics、不实现通用 artifact validator、不改 `plan-to-exec` multi-plan 语义，也不迁移历史 workflow artifact。

## Background / 背景与动机

`docs/articles/harness-engineering-loopx-takeaways.md` 已经把 Harness Engineering 中可吸收的工程纪律映射到 loopx skill 链路。多项能力已经落地：`clarify` intake package、`spec` `D-*` anchors、`plan-to-exec` `T-*` anchors、`review` spec compliance、`finish` audit-first learning extraction。

剩余风险不是单个 skill 缺字段，而是主链路可能在上下游交接时断开：

- `spec` 已有 `D-*`，但分类型 contract blocks 仍可细化。
- `plan-to-exec` 已有 `T-*`，但 `exec` / `subagent-exec` 的验证证据交接需要统一。
- `review` 已消费 `AC-*` / `D-*` / `T-*`，但需要与执行证据和 final-review 形成一致闭环。
- `final-review` 已有 requirements coverage、runtime validation、regression checklist，但缺少独立 `Test Trust`。
- `finish` 已有 spec candidates，但 delta-spec candidate 的 `ADDED/MODIFIED/REMOVED/RENAMED` 命名结构仍待细化。

用户明确要求完成文章里关于 `clarify`、`spec`、`plan-to-exec`、`exec`、`review`、`final-review`、`finish` 的未完成部分，并检查链路完整程度；同时补充 `subagent-exec` 必须纳入 `plan-to-exec` 的执行链路。

## Goals And Non-Goals / 目标与非目标

目标：

- 完成文章中七个主链路 skill 相关的剩余项。
- 把 `subagent-exec` 纳入 `plan-to-exec` 的执行证据链路。
- 明确新 artifact 的主链路 contract，并用治理测试防止链路重新断开。
- 更新文章，把本次完成或部分完成的项回标。
- 保持后续 `plan-to-exec` 可以生成一个普通单 plan，不生成 multi-plan package。

非目标：

- 不实现本地 metrics JSONL。
- 不实现通用 workflow artifact validator 框架。
- 不实现 `codebase-spec` repo specs 初始化模式。
- 不新增独立 `acceptance-testcase-generator` support skill。
- 不改 `plan-to-exec` multi-plan 语义。
- 不迁移、不回写、不强兼容历史 workflow artifact。
- 不实现 deploy、UI calibration、ops diagnose 等插件型能力。

## Proposal / 设计方案

### 1. 采用一条新 artifact contract，而不是回改旧文件

新生成的主链路 artifact 必须遵守完整 contract。历史计划、历史 review、旧 final-review、旧 finish audit 不迁移、不回写、不作为本次执行对象。

这避免把范围扩展成历史数据兼容项目，也符合用户确认的“旧的文件不会再修改或者执行，可以忽略，不做强兼容”。

### 2. `clarify` 继续作为 AC/TC 源头

`clarify` 已经输出 `requirements.md`、`test-cases.md`、`clarification.md`。本次设计要求下游继续把 intake package 当作需求源，不重新解释需求，不新增第二套验收编号。

### 3. `spec` 补充分类型 workflow contract blocks

`spec` 已有 inline `D-*` 和 `Design Contract Index / D-*`。本次不替代既有设计模板，而是在 detailed design guidance 中明确按需使用这些 contract block 类型：

- `Behavior Contract`
- `API Contract`
- `Data Contract`
- `Permission Contract`
- `State Contract`
- `CLI Contract`
- `Operational Contract`
- `Workflow Contract`

对于纯 workflow skill 合约，本次主要使用 `Workflow Contract`，并把它映射到 `D-*` anchor。

### 4. `plan-to-exec` 到 `exec` / `subagent-exec` 的执行证据链统一

`plan-to-exec` 产生 `T-*` 任务后，`exec` 和 `subagent-exec` 都必须保留：

- `Source AC`
- `Design anchors`
- `Test cases`
- `Task anchor`
- verification command
- expected evidence
- review focus

`exec` 的 checkpoint/self-check 和 `subagent-exec` 的 task brief / report / review package 都应该能带出同一组 anchor 与验证证据。

### 5. `review` 和 `final-review` 分别承担局部与全局检查

`review` 保持 task 或 checkpoint 粒度，检查 `AC-*` / `D-*` / `T-*` 的 spec compliance 和代码质量。

`final-review` 保持 whole-feature 粒度，新增独立 `Test Trust` 小节，用 High / Medium / Low 判断测试证据是否足以支撑需求覆盖。它不替代 `review` 的任务级检查，也不变成通用 artifact validator。

### 6. `finish` 细化 delta-spec candidate 命名

`finish` 已有 audit extraction candidates、accepted/rejected candidates、memory/spec candidates。本次只补充 candidate 表达结构，让 spec candidate 能按 `ADDED` / `MODIFIED` / `REMOVED` / `RENAMED` 分类呈现。是否真正写入 `docs/loopx/specs/` 仍由 finish audit 和用户确认控制。

## Support Lens Checks / 专项设计检查

| Support lens | Trigger | Design checks applied | Result |
|---|---|---|---|
| `architecture-designer` | 本次改变多个 workflow skill 的边界、所有权和下游消费关系 | 检查系统边界、失败模式、可运维性、迁移范围、长期契约 | 采用“新 artifact contract + 不迁移旧 artifact + 单 plan”的低迁移方案 |

## Boundary Scenarios / 边界场景

| 场景 | 处理方式 |
|---|---|
| 输入是 intake package | 读取 `requirements.md` 和 `test-cases.md`，`clarification.md` 只作过程证据。 |
| 输入是设计文档 | `plan-to-exec` 读取 `D-*` 和 `TC-*` 映射，缺关键设计决策则回到 `spec`。 |
| 新 plan 缺 `T-*` | 新产物不满足 contract，治理测试或 plan 自检应失败。 |
| `exec` 或 `subagent-exec` 未保留验证证据 | 不能声明任务完成；必须补充命令、结果、剩余风险。 |
| review 发现 anchor 覆盖缺口 | Critical/Important 处理后才能继续后续阶段。 |
| final-review 无法判断 Test Trust | 标为 Medium/Low，并说明哪些 AC 只由 smoke/manual confidence 支撑。 |
| finish 找不到 final-review artifact | 保持现有行为：不生成 final-review，询问或要求先跑 final-review。 |
| 历史 artifact 缺新增字段 | 不迁移、不回写、不作为本次执行对象。 |
| 重复执行新流程 | 新 artifact 应保持稳定 anchor；追加任务时不重排既有 `T-*`。 |
| 并发或 multi-plan | 本次不改 multi-plan 语义；如果未来使用 multi-plan，仍按 child plan 前缀组合全局引用。 |
| 权限失败 | 不涉及外部权限系统；本次是 repo 内 skill 合约和测试。 |
| 依赖超时 | 不涉及外部服务；验证命令失败按正常测试失败处理。 |
| 回滚 | 文档和测试变更可通过 git revert 回滚，无数据迁移。 |
| 不变行为 | 不改变 CLI runtime、hooks、multi-plan state、finish audit runtime 语义。 |

## Rationale / 理由与取舍

| Alternative | Why Not |
|---|---|
| 按 skill 拆成多个 plan | 容易每个 skill 局部正确，但上下游 contract 断开。 |
| 实现通用 artifact validator | 用户已确认本次排除；范围会扩展到 CLI/scripts 平台能力。 |
| 实现 local metrics | 与主链路 contract 无直接依赖，已排除。 |
| 新增 `acceptance-testcase-generator` | 需求阶段 `test-cases.md` 已由 `clarify` 承接；新增 skill 是后续可选演进。 |
| 强兼容旧 artifact | 用户明确旧文件不会再修改或执行，不做强兼容。 |
| 把 final-review 改成全量 AC/D/T hard gate | 当前目标是补上 `Test Trust` 和链路一致性，不把 final-review 变成通用 artifact validator。 |

## Compatibility / 兼容性

本提案对新生成的 skill artifacts 是 contract strengthening，对历史 artifact 不做迁移。

不变表面：

- 不改变 `plan-to-exec` multi-plan package 语义。
- 不改变旧计划文件。
- 不改变 CLI 命令表面。
- 不改变 `.loopx/finish` runtime 数据结构的核心语义。
- 不改变 package/install surface。

新行为只约束新生成的主链路 artifacts 和 skill 文档指令。

## Operational And Security Impact / 运行与安全影响

运行影响较低。本次主要修改 skill 文档、prompt 模板和治理测试。风险集中在：

- skill 文档之间的 wording 不一致，导致下游 agent 误读。
- governance tests 过宽，无法防止链路断开。
- governance tests 过窄，把未来合理改动误判为失败。

安全与隐私影响不涉及外部数据、权限、网络、密钥或用户数据处理。

## Implementation And Transition / 实现与过渡

后续实施应走一个普通单 plan。推荐高层顺序：

1. 先补齐 contract inventory，确认文章中七个主链路 skill 的剩余缺口。
2. 更新上游 contract：`spec` contract blocks、`plan-to-exec` 到 `exec` / `subagent-exec` 的 evidence bridge。
3. 更新下游 contract：`review`、`final-review` `Test Trust`、`finish` delta candidate naming。
4. 增加治理测试并回标文章完成状态。

这不是任务计划；具体文件和步骤由 `plan-to-exec` 生成。
