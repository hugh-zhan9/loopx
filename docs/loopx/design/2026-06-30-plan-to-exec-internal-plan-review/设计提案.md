# 在 plan-to-exec 内部增加 source-to-plan review，而不扩展主流程

Author(s): zhangyukun, Codex
Last updated: 2026-06-30
Status: Draft
Discussion: 不涉及
Source requirements: `.loopx/intake/2026-06-30-plan-to-exec-internal-plan-review/`
Support lenses: architecture-designer

## Abstract / 摘要

本提案选择在 `plan-to-exec` 内部增加一个强制的 source-to-plan review pass：先生成 draft plan，再使用 `plan-reviewer` support lens 审核 draft 是否完整覆盖 source requirements/design/test cases，修复 Critical/Important findings 后才保存最终 plan 或展示执行 handoff。

这个 reviewer 优先通过 subagent 执行；没有 subagent 能力时，`plan-to-exec` 在当前上下文内使用同一 rubric 降级复核，并在最终 plan 或 handoff 中标记 `same-context/degraded` 和残余独立性风险。主链路保持不变，不新增 `plan-review` workflow stage，也不要求用户多跑一个命令。

## Background / 背景与动机

用户在多次使用中观察到：`plan-to-exec` 生成的 plan 经 `exec` 或 `subagent-exec` 执行后，`final-review` 才发现覆盖不足，例如 `Coverage: 6/11 requirements fully covered`。仓库证据显示：

- 当前 `plan-to-exec` 只有 self-review checklist，能检查 `AC-*`、`D-*`、`TC-*`、`T-*` 等映射，但检查者仍是生成计划的同一主体。
- `exec` 的 Step 1 会 review plan，`subagent-exec` 有 Pre-Flight Plan Review，但它们主要检查可执行性、冲突、接口缺失和 surface-change 证据，不是完整 source-to-plan coverage audit。
- `subagent-exec` 已经用“实现 subagent + reviewer subagent”的内部模式提升任务质量，说明独立 review 可以作为某个 workflow skill 的内部机制存在，而不需要新增外部 workflow state。

问题的关键不是缺少又一个用户可见流程，而是 `plan-to-exec` 在保存最终产物前缺少独立视角。若 plan 本身遗漏设计点，执行者和 task reviewer 可能会忠实执行不完整 plan，直到最终复审才发现源需求未覆盖。

## Goals And Non-Goals / 目标与非目标

目标：

- 在 `plan-to-exec` 内部强制审核 draft plan，提前发现 source-to-plan coverage gap。
- 使用 subagent 时获得独立 reviewer 视角。
- 没有 subagent 时使用同一 rubric 降级执行，并显式标记独立性风险。
- 将 review rubric 做成 support skill/lens，便于复用和治理。
- 保持正常主链路不变：`clarify -> spec -> plan-to-exec -> exec/subagent-exec -> final-review -> finish`。

非目标：

- 不新增 `plan-review` 主流程阶段。
- 不新增用户必须执行的 `$plan-review ...` handoff。
- 不审核尚不存在的实现代码。
- 不让 reviewer 重新设计已批准的产品、架构或 workflow 决策。
- 不迁移历史 plan。
- 不新增 runtime state、CLI command、hook 行为或数据库/持久化数据。

## Proposal / 设计方案

### 核心规则

`plan-to-exec` 的生成过程调整为：

1. 读取 source artifact，包括 intake package 或 design spec。
2. 生成 draft implementation plan。
3. 运行 `plan-reviewer` support lens 做 source-to-plan review。
4. 若发现 Critical/Important findings，修订 draft 并重新检查受影响 finding。
5. 当 Critical/Important 清零后，保存最终 plan 并展示现有执行选项。

这个 review 是 `plan-to-exec` 的内部质量门禁，不是用户可见的工作流节点。最终输出仍是 `docs/loopx/plans/...` 的 plan。

### `plan-reviewer` support lens

新增 support skill `plan-reviewer`，定位类似 `go-style`、`cli-developer`、`architecture-designer`：

- 作为 `plan-to-exec` 内部 mandatory lens 使用。
- 可以被用户直接调用做 ad-hoc plan audit。
- 不进入 `RESOLVER.md` 的 Core Workflow Skills。
- 不出现在 normal next-step handoff 中。
- 不替代 `review` 或 `final-review`，因为它不看实现 diff。

### Subagent 与降级

有 subagent 能力时，`plan-to-exec` 派独立 reviewer subagent：

- 输入：source artifact、draft plan、相关 repo spec/memory 摘要、review rubric。
- 输出：Critical/Important/Minor findings，覆盖矩阵结论，review mode。
- 限制：不得审查实现代码，不得新增设计决策。

无 subagent 能力时，`plan-to-exec` 必须在当前上下文内执行同一 rubric，并在最终 plan 或 handoff 记录：

```text
Plan review mode: same-context
Reviewer independence: degraded
Residual risk: source-to-plan coverage was not independently reviewed by a separate subagent
```

该降级路径不阻断 plan 生成，但必须暴露风险，方便 `exec/subagent-exec` pre-flight 和 `final-review` 后续加权判断。

### Findings gate

Severity 规则：

- Critical：source 中必须实现的 AC/D/TC 完全未进入 plan；plan 引入与 source 冲突的新行为；reviewer 无法判断 plan 是否可执行且会导致错误实现。
- Important：source coverage 部分缺失；verification/review focus/expected evidence 不足；task handoff 上下文不足，容易导致 subagent 漏实现。
- Minor：不影响正确执行的清晰度、组织或局部措辞问题。

Critical/Important 必须在最终保存或 handoff 前处理。Minor 可以保留，但必须记录 residual risk 或明确不影响执行。

### 产物与证据

最终 plan 或 handoff summary 应记录：

- `Plan review mode`: `subagent` 或 `same-context`
- `Reviewer independence`: `independent` 或 `degraded`
- `Blocking findings`: `none` 或已处理摘要
- `Residual risk`: `none` 或具体风险

可选 scratch review artifact 可写到 `.loopx/plan-to-exec/<slug>-plan-review.md`。该 artifact 是本地 workflow scratch，不进入 repo-tracked docs，除非用户明确要求。

## Boundary Scenarios / 边界场景

| 场景 | 处理 |
|---|---|
| source 缺 AC/TC 或设计锚点互相矛盾 | `plan-to-exec` 不应靠 reviewer 补设计；应返回 `clarify` 或 `spec`。 |
| draft plan 漏掉某个 AC/D/TC | reviewer 报 Critical/Important；`plan-to-exec` 修订并复核后才能保存。 |
| draft plan 发明 source 未批准的新行为 | reviewer 报 Critical；必须删除或返回 `spec` 重新设计。 |
| subagent 不可用 | 使用同一 rubric same-context 复核，记录 degraded independence。 |
| reviewer 只发现 Minor | 可保存 plan，但记录 residual risk 或说明无执行风险。 |
| 用户直接调用 `plan-reviewer` | 允许 ad-hoc audit；不改变 workflow state，也不自动进入执行。 |
| 历史 plan 没有 review 证据 | 不迁移、不重写；新规则只适用于新生成 plan。 |
| 多计划 package | 每个 child plan draft 应接受同类 review；overview 的拆分和 child 独立性也属于 review 范围。 |
| 执行阶段 pre-flight review | 保持不变；它仍检查执行可行性，不替代 source-to-plan review。 |

## Rationale / 理由与取舍

| Alternative | Why Not |
|---|---|
| 新增 `plan-review` 主流程 stage | 用户明确反对流程扩充；会增加 handoff 和状态复杂度。 |
| 只强化 `plan-to-exec` self-review | 无法解决 planner 自己漏项自己不知道的问题。 |
| 交给 `exec/subagent-exec` pre-flight | 它们职责是执行前可行性检查，太晚且不专注 source coverage。 |
| 把 rubric 内嵌在 `plan-to-exec`，不单独 support skill | 可复用性和治理弱，也不便于 ad-hoc audit；support lens 更符合现有 loopx 模式。 |

选中方案的代价是 `plan-to-exec` 内部会多一次 review 循环，生成计划的耗时和 token 使用会上升。但它把遗漏设计点的发现时间从 final-review 前移到 implementation 前，修复成本更低。

## Compatibility / 兼容性

这是 additive change。

- 主链路不变。
- `plan-to-exec` 输出路径不变。
- `exec` / `subagent-exec` handoff 不变。
- 历史 plan 不迁移。
- 无 CLI/API/runtime state 变更。
- 若新增 `plan-reviewer` 为 bundled support skill，需要更新 `LOOPX_BUNDLED_SKILLS`、`skills/RESOLVER.md`、skills docs、README support skill 列表和治理测试。

## Operational And Security Impact / 运行与安全影响

- 运行影响：无服务端、无 runtime command、无 daemon。
- 安全影响：review 输入为本地 source/draft plan，不要求访问新权限。
- 失败模式：subagent 不可用时必须降级并记录风险；review artifacts 若写入 `.loopx/`，默认不进入 git。
- 可维护性：support lens rubric 单独维护，避免 `plan-to-exec` 主文档膨胀过多。

## Implementation And Transition / 实现与过渡

高层落地路径：

1. 新增 `skills/plan-reviewer/SKILL.md` support lens rubric。
2. 更新 `plan-to-exec`，要求 draft plan 后运行 `plan-reviewer`，优先 subagent，缺失时 same-context。
3. 更新 `RESOLVER.md`、docs、bundled skill discovery 和 governance tests，确保 `plan-reviewer` 是 support skill 而非 workflow state。
4. 更新 `plan-to-exec` plan template/self-review/handoff，记录 review mode、reviewer independence、residual risk。
