# 多 Plan 执行状态与 Finish 门禁设计提案

## Abstract / 摘要

我们将 multi-plan package 定义为一个 spec 下的多个可独立执行 child plan。每个 child plan 可以独立执行、独立做 plan-level final-review，但不能独立触发 `finish`；只有所有 child plan 完成并且 spec-level final-review 通过后，`finish` 才能继续。运行态状态保存在 `.loopx/multi-plan/<feature-slug>/state.json`，`finish` 通过 `finish-start --source` 记录的 plan path 发现对应状态并执行硬门禁。

## Background / 背景与动机

当前 `plan-to-exec` 已允许从一个 source artifact 生成目录式 multi-plan package：

```text
docs/loopx/plans/YYYY-MM-DD-<feature-slug>/
  00-overview.md
  01-<plan-slug>.md
  02-<plan-slug>.md
```

但现有执行链路仍以单 plan 文件为自然单位：

- `skills/subagent-exec/SKILL.md` 执行一个 approved implementation plan，完成后进入 `final-review` 和 `finish`。
- `skills/subagent-exec/scripts/task-brief` 接受 `PLAN_FILE TASK_NUMBER`，并要求 plan 是文件。
- `skills/final-review/SKILL.md` 审查完整 feature 的 git range 和 source requirements，可接受 spec 或 plan。
- `skills/finish/SKILL.md` 读取 latest final-review report，再做 finish audit 和完成记录。
- `src/finish-runtime.mjs` 的 `finish-start` 只记录一个 `source` 字段，`finish-audit` 将其放入 `change_window.source_artifacts`。

如果 multi-plan package 仍沿用单 plan 完整闭环，会产生两个问题：每个 child plan 后都 `finish` 会切碎一个 spec 的整体交付；一次性执行整个目录又会提高上下文、token、失败半径，并阻碍并行执行。

## Goals And Non-Goals / 目标与非目标

目标：

- 支持一个 spec 拆成多个 child plan 后，child plan 可以独立执行和独立 plan-level final-review。
- 保证 multi-plan package 只在 spec-level final-review 通过后才允许 `finish`。
- 使用本地 runtime state 跟踪 multi-plan package 进度，避免依赖 agent 记忆。
- 保持单 plan workflow 不变。
- 避免自动执行或调度所有 child plan，保留用户并行执行空间。

非目标：

- 不新增自动执行整个 plan 目录的 orchestrator。
- 不新增自动并行调度。
- 不在 runtime 层阻塞 `final-review`。
- 不把 mutable 执行状态写入 repo-tracked plan 目录。
- 不扫描所有 `.loopx/multi-plan/*/state.json` 猜测当前 feature。
- 第一版不记录 child plan base/head。

## Proposal / 设计方案

### Multi-plan package 保持人工可读，执行状态留在本地

`00-overview.md` 继续作为 repo-tracked 的人工可读概览，记录 source spec、child plan 列表、依赖、执行顺序、并行关系和拆分理由。执行进度、review artifact path、spec-level gate 等 mutable 状态写入：

```text
.loopx/multi-plan/<feature-slug>/state.json
```

最小状态形状：

```json
{
  "schema_version": 1,
  "feature_slug": "2026-06-29-feature",
  "plan_package": "docs/loopx/plans/2026-06-29-feature/",
  "source_spec": "docs/loopx/design/2026-06-29-feature/需求设计文档.md",
  "status": "in_progress",
  "plans": [
    {
      "path": "docs/loopx/plans/2026-06-29-feature/01-core.md",
      "status": "complete",
      "plan_final_review": ".loopx/final-review/2026-06-29-01-core.md",
      "ready_for_spec_review": true
    }
  ],
  "spec_final_review": {
    "path": ".loopx/final-review/2026-06-29-feature.md",
    "ready_for_finish": "Yes"
  }
}
```

### Child plan 执行完成后进入 plan-level final-review，不进入 finish

`subagent-exec` 仍执行单个 plan 文件。对于 multi-plan package 中的 child plan，执行完成后应做 plan-level final-review，并更新 `.loopx/multi-plan/<feature-slug>/state.json` 中对应 child plan 的 `status`、`plan_final_review` 和 `ready_for_spec_review`。

plan-level final-review 的目标是确认当前 child plan 自己的目标、测试、接口产出和变更范围合格；它不是整个 spec 的最终完成门。

### 所有 child plan 完成后做 spec-level final-review

spec-level final-review 使用 source spec、`00-overview.md`、所有 child plan、所有 plan-level final-review artifact 和完整 feature git range。它负责检查跨 plan 集成、完整需求覆盖、接口拼接、回归风险和遗漏。

spec-level final-review 通过后，将 `spec_final_review.path` 和 `spec_final_review.ready_for_finish` 写入 multi-plan state。

### Finish runtime 做硬门禁

`finish` 通过 `finish-start --source` 发现适用的 multi-plan state：

- 如果 source 是 `docs/loopx/plans/YYYY-MM-DD-<feature-slug>/00-overview.md`，使用该 package。
- 如果 source 是同目录的 `01-*.md`、`02-*.md` 等 child plan，使用同一个 package。
- 不扫描所有 `.loopx/multi-plan/*/state.json`。
- 没有匹配 multi-plan state 时，保持普通单 plan 行为。

找到匹配 state 后，`finish` 只有在以下条件全部满足时放行：

- `plans[]` 非空。
- 每个 child plan `status == "complete"`。
- 每个 child plan 有 `plan_final_review`。
- 每个 child plan `ready_for_spec_review == true`。
- `spec_final_review.path` 存在。
- `spec_final_review.ready_for_finish == "Yes"`。

否则 `finish` 停止，并报告缺失的 child plan 或 review gate。

## Support Lens Checks / 专项设计检查

| Support lens | Trigger | Design checks applied | Result |
|---|---|---|---|
| `architecture-designer` | 变更 workflow state、runtime gate、跨 skill 边界 | 明确状态所有权、系统边界、失败模式、单 plan 兼容性 | 采用本地 runtime state + finish 单点硬门禁 |
| `cli-developer` | `finish` CLI/runtime 行为和错误输出变化 | 保持现有命令签名，避免新增交互，错误应可操作，单 plan 不变 | 不新增 public CLI 命令；在现有 finish runtime 阶段增加 gate |

## Boundary Scenarios / 边界场景

- 无 matching state：`finish-start --source` 不指向 multi-plan package，或没有 `.loopx/multi-plan/<feature-slug>/state.json`，按普通单 plan 流程处理。
- source 指向 child plan：从 child plan 父目录推导 package slug，读取同一个 state。
- child plan 未完成：`finish` 阻止完成，报告对应 child plan path。
- child plan 完成但缺 plan-level final-review：`finish` 阻止完成，报告缺失 `plan_final_review`。
- plan-level final-review 存在但 `ready_for_spec_review` 不是 true：`finish` 阻止完成。
- 所有 child plan 完成但缺 spec-level final-review：`finish` 阻止完成。
- spec-level final-review 为 `No` 或 `With fixes`：`finish` 阻止完成。
- 多个 feature 并行存在：不全局扫描，避免误用其他 state。
- repo-tracked plan 文件不变：`00-overview.md` 和 child plan 内容不会被 runtime 自动改写。
- final-review 本身不被 runtime 卡住：agent 可以执行 plan-level 或 spec-level final-review，但必须按 skill contract 更新状态。
- 单 plan workflow：没有 matching state 时保持不变。

## Rationale / 理由与取舍

| Alternative | Why Not |
|---|---|
| 只改 skill 文档，不做 runtime gate | 最终 `finish` 仍依赖 agent 自觉，容易在 multi-plan 未完成时误收口。 |
| 自动执行整个 plan 目录 | 增加上下文、token 和失败半径，阻碍用户并行执行 child plan。 |
| 每个 child plan 都 `finish` | 切碎一个 spec 的整体完成语义，final-review 和 finish audit 只看局部。 |
| 状态写入 plan 目录 | 执行状态会进入 repo diff，增加 merge 冲突和 finish 审计噪音。 |
| 全局扫描 `.loopx/multi-plan/*` | 多个 feature 并行时会误判当前工作归属。 |
| 第一版记录 child plan base/head | finish 已有整体 baseline..HEAD；child base/head 在 rebase 和并行场景下更脆。 |

## Compatibility / 兼容性

该方案对单 plan workflow 保持兼容。未发现 matching multi-plan state 时，`finish` 保持现有行为。

会新增或调整的当前产品表面：

- skill contracts：`plan-to-exec`、`subagent-exec`、`final-review`、`finish`、`RESOLVER`，必要时包括 `clarify`。
- runtime state：新增 `.loopx/multi-plan/<feature-slug>/state.json`。
- finish runtime：在现有 `finish-record`/finish 完成记录前增加 multi-plan gate。
- tests/governance：新增状态模型和 finish gate 测试。

不会改变：

- `subagent-exec scripts/task-brief PLAN_FILE N` 的单文件任务抽取模型。
- `loopx finish-start`、`finish-audit`、`finish-record` 的 public 命令签名。
- `.loopx/final-review/YYYY-MM-DD-<slug>.md` report artifact 位置。

## Operational And Security Impact / 运行与安全影响

运行影响主要是本地 `.loopx/multi-plan/` 状态需要被正确维护。该状态不包含 secrets，不应写入 repo。并行 worktree 场景下，每个 worktree 的本地状态可能不同，需要通过人工或后续工具汇总；第一版不解决跨 worktree 状态同步。

错误处理应具体说明阻塞原因，例如缺少哪个 child plan review 或 spec-level final-review。JSON 输出若暴露 gate 失败，应使用稳定字段，而不是只能解析人类文本。

## Implementation And Transition / 实现与过渡

第一版以 additive 方式落地：

1. 补充 skill contracts 和 governance tests。
2. 增加 multi-plan state helper，解析 source path 和 state。
3. 在 finish completion record 前增加 gate 校验。
4. 补充 workflow tests 覆盖 incomplete/complete state。

历史 plan 文件和历史 final-review/finish artifact 不迁移。已有单 plan 使用方式不变。

无。

## Detailed Design Handoff / 详细设计交接

需要写详细设计。详细设计必须将以下决策作为固定约束：

- `.loopx/multi-plan/<feature-slug>/state.json` 是 mutable runtime state。
- `finish` 是唯一 runtime hard gate。
- `final-review` 不 runtime-blocked，但要支持 plan-level/spec-level 语义。
- `finish` 通过 `finish-start --source` 的 path 发现 multi-plan state。
- 不自动执行整个 multi-plan package。
