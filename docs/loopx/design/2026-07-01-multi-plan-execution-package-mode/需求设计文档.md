## 二、需求信息

### 2.1 需求背景

- 背景：loopx 已支持 `plan-to-exec` 产出 multi-plan package，`final-review` 已支持 plan-level/spec-level 两层 review，`finish` runtime 已有 multi-plan gate。但 `exec` 和 `subagent-exec` 仍主要以单 plan 或单 child plan 为执行单位，用户想一次性执行整个 package。
- 需求目的：让 multi-plan package 可以通过现有执行入口完成，不新增 workflow skill，同时保留 child plan targeted execution、plan-level review、spec-level review 和 finish gate。
- 目标用户/使用方：
  - 使用 loopx 处理大型需求的 agent/user。
  - 维护 `exec`、`subagent-exec`、`plan-to-exec`、`final-review`、`finish` 的 workflow 维护者。
  - 依赖 `.loopx/multi-plan/<feature-slug>/state.json` 的本地状态使用者。
- 需求链接：
  - [设计提案](./设计提案.md)
  - `.loopx/intake/2026-07-01-multi-plan-execution-package-mode/requirements.md`

  - `.loopx/intake/2026-07-01-multi-plan-execution-package-mode/clarification.md`
- 关联原始材料：

### 2.2 需求范围

- 本期范围：
  - 为 `exec` 和 `subagent-exec` 增加相同的 package input scope：multi-plan directory 和 `00-overview.md`。[D-001]
  - 保留 numbered child plan direct execution，只执行当前 child plan。[D-002]
  - 定义 package mode 外层顺序 orchestration，并保留各执行 lane 内部纪律。[D-003][D-004][D-005]
  - 定义缺失 `.loopx/multi-plan/<feature-slug>/state.json` 时的 schema v2 初始化规则，以及已有 state 的校验/阻塞规则。[D-006]
  - 定义 package mode 全部 child plans ready 后自动运行 spec-level `final-review`，clean 后进入 `finish`。[D-007]
  - 更新 `plan-to-exec` multi-plan handoff，默认推荐 package mode，保留 child plan direct execution 作为 targeted/resume/manual-control 用法。[D-008]
  - 更新治理测试和当前 skill wording，替换旧的“不要执行整个目录”约束。[D-010]
- 非目标：
  - 不新增 `multi-plan-exec` skill。[D-011]
  - 不新增 public `loopx multi-plan` CLI 或其他 runtime command。[D-011]
  - 不自动并行执行 child plans。[D-005]
  - 不改变 `subagent-exec` 的平台 subagent 能力发现和 per-task subagent 模型。[D-004]
  - 不把 mutable state 写入 repo-tracked `docs/loopx/plans/.../`。
  - 不迁移历史 plan/design 文档。
- 决策边界：
  - package mode 是执行 skill 的 input scope 扩展，不是新的 workflow stage。
  - package mode 是顺序 orchestrator，不是并行 scheduler。
  - state 缺失可以初始化；state 存在但 invalid/stale/conflicting 时必须阻塞。
  - spec-level `final-review` 仍是 package finish 的唯一 review gate。
  - child plan direct execution 仍然可用，不被 package mode 替代。
- 依赖方：
  - `skills/plan-to-exec/SKILL.md`
  - `skills/subagent-exec/SKILL.md`
  - `skills/exec/SKILL.md`
  - `skills/final-review/SKILL.md`
  - `skills/finish/SKILL.md`
  - `skills/RESOLVER.md`
  - `src/finish-runtime.mjs`
  - `test/workflow.test.mjs`
  - `test/skill-governance.test.mjs`
  - `scripts/verify-skills.mjs`
- 约束条件：
  - 保持 single-plan workflow 行为不变。
  - 保持 `.loopx/multi-plan/<feature-slug>/state.json` 为本地 workflow state。
  - 新写入的 multi-plan state 使用 schema v2 的 `plan_review.status/reviewed_at/summary`，不得重新引入 `plan_final_review` 作为新 contract。[D-006]
  - 修改 bundled skill docs 时编辑 `skills/` canonical source，并只 bump 被改动 skill 的 `metadata.version`。
  - 变更后需要通过 `node scripts/verify-skills.mjs`、相关 Node tests 和 governance tests。
- 触发的辅助 skills：`architecture-designer`

### 2.3 可行性分析

- 业务可行性：intake 已确认 AC-001 至 AC-009，无 open questions。
- 技术可行性：现有 `00-overview.md` 已包含 source spec、package slug、state path、child plan list、execution order；现有 runtime 已有 multi-plan state validation 和 final-review/finish gate。
- 团队接受能力：改动集中在 workflow skill contracts、local state helper/validation、governance tests，符合当前仓库维护方式。
- 时间成本：中等。需要同时更新 `exec`、`subagent-exec`、`plan-to-exec`、`finish` wording 和测试。
- 资源成本：低。不新增依赖、服务端、数据库或 public CLI。
- 替代方案：
  - 新增 `multi-plan-exec` skill：已拒绝，增加流程心智负担。
  - 继续 per-child 手工执行：已拒绝，不能满足“一次跑完整个 package”。
  - package mode 只加到 `subagent-exec`：已拒绝，`exec` 需要作为 no-subagent fallback。
  - 自动并行 child plans：已拒绝，第一版不处理并发 state 写和 git 冲突。
- 关键风险：
  - `00-overview.md` 可解析性不足会影响 state 初始化。
  - `exec` 与 `subagent-exec` 的 package wording 若不统一，会产生行为分叉。
  - 历史 docs/plan 中旧约束仍可能出现；治理测试应只约束 current product surfaces。

## 三、概要设计

### 3.1 方案总述

- 设计目标：用现有 `exec` / `subagent-exec` 入口支持 whole-package multi-plan execution，让用户一次执行整个 package，同时保留 review/final-review/finish 的安全门禁。
- 总体思路：
  - 对输入路径做 scope classification。[D-001]
  - package scope 下读取 `00-overview.md`，初始化或校验 `.loopx/multi-plan/<feature-slug>/state.json`。[D-006]
  - 按 execution order 顺序执行未完成 child plans。[D-003][D-005]
  - 每个 child plan 完成后运行 plan-level `final-review`，仅更新 child state。[D-002][D-006]
  - 全部 child plans ready 后运行 spec-level `final-review`，clean 后进入 `finish`。[D-007]
- 核心模块：
  - Package scope classifier
  - Overview parser / package manifest reader
  - Multi-plan state initializer and validator
  - `subagent-exec` package controller
  - `exec` package controller
  - `plan-to-exec` handoff contract
  - Governance/runtime tests
- 主要难点：
  - 既要执行整个 package，又不能破坏 child plan direct mode。
  - 两条 execution lane 需要共享 package semantics，但内部执行机制不同。
  - state 缺失自动初始化和已有 state 阻塞边界必须清晰。
- 技术指标：
  - package dir 和 `00-overview.md` 都进入 package mode。
  - child plan path 仍只执行当前 child plan。
  - missing state 可初始化为 schema v2。
  - invalid/duplicate/stale/mismatched state 阻塞。
  - package mode 不并行 child plans。
  - `plan-to-exec` 默认 handoff 指向 package mode。

### 3.2 整体架构设计

- 业务模式：
  - `plan-to-exec` 产出 multi-plan package。
  - `exec/subagent-exec` 可执行 single plan、child plan 或 whole package。
  - `final-review` 继续分 plan-level 和 spec-level。
  - `finish` 继续只在 spec-level final-review clean 后完成。
- 系统边界：
  - `plan-to-exec` 负责 package artifact 和 handoff。
  - `exec/subagent-exec` 负责 package mode orchestration 和 child execution。
  - `final-review` 负责 review verdict 和 state update。
  - `finish` 负责最终 gate 与 completion，不补跑 final-review。
- 上下游系统：
  - 上游：intake/spec、`docs/loopx/plans/.../00-overview.md`、child plans。
  - 当前：`exec`、`subagent-exec`、`final-review`、`finish`。
  - 下游：`fix-review`、finish audit、memory/spec extraction。
- 应用架构：
  - 主要变更是 skill contracts 和 governance tests。
  - 如实现需要 runtime helper，可放在现有 finish/multi-plan state helper 同域；不要求新增 public CLI。
- 技术架构：
  - Markdown skill contracts。
  - Local JSON state under `.loopx/multi-plan/`.
  - Node.js ESM tests and validation helpers。
- 数据流转：

```text
docs/loopx/plans/YYYY-MM-DD-feature/00-overview.md
  -> package mode resolves child plan order
  -> .loopx/multi-plan/YYYY-MM-DD-feature/state.json initialized or validated
  -> child plan 01 executes
  -> plan-level final-review updates plans[0].plan_review
  -> child plan 02 executes
  -> plan-level final-review updates plans[1].plan_review
  -> spec-level final-review updates spec_final_review
  -> finish checks multi-plan gate and completes
```

### 3.3 核心流程设计

| 流程 | 触发条件 | 参与系统/模块 | 主流程 | 异常/补偿 | 输出 |
|---|---|---|---|---|---|
| Scope classification | 用户调用 `exec/subagent-exec <arg>` | `exec`, `subagent-exec` | 判断 single plan / package / child plan / invalid | invalid path 阻塞 | scope |
| Package state prepare | scope = package | execution skill, `.loopx/multi-plan` | 读取 overview，missing state 初始化，existing state 校验 | invalid/stale/conflict 阻塞 | schema v2 state |
| Child plan execution | package 中存在未完成 child | `exec` 或 `subagent-exec` | 按顺序执行一个 child plan，做 task review/checkpoint review | task/review/fix 阻塞则不继续 sibling | child implementation |
| Plan-level final-review | child plan tasks 全部完成 | `final-review` | review child plan，更新 `plan_review` 和 `ready_for_spec_review` | review 不通过则 fix-review/复审 | child row ready |
| Spec-level final-review | 全部 child plans ready | `final-review` | review source spec + overview + child plans + current state | Critical/Important 或 Ready No 阻塞 finish | `spec_final_review` |
| Finish | spec-level review clean | `finish` | 验证 tests/gates，检查 multi-plan state，完成 finish flow | gate incomplete 阻塞 | finish audit/record |

### 3.4 功能模块

| 模块 | 职责 | 关键功能 | 依赖 | 备注 |
|---|---|---|---|---|
| Scope classifier | 判断输入作用域 | single/package/child/invalid | input path, repo paths | `exec` 和 `subagent-exec` 共享语义 |
| Overview reader | 从 `00-overview.md` 提取 package info | source spec、slug、state path、child plan list、execution order | plan-to-exec overview contract | 字段缺失时阻塞 |
| State initializer/validator | 准备 `.loopx/multi-plan` state | schema v2 init、existing state match、defect reporting | local filesystem | missing 可 init，invalid 不修 |
| Package controller | 顺序调度 child plans | skip completed, execute pending, stop on blocker | execution lane | 不并行 |
| Child executor | 执行一个 child plan | `exec` same-context 或 `subagent-exec` per-task subagents | existing skill rules | child direct mode 与 package loop 共用 |
| Final gate runner | 完成 spec-level review 和 finish | final-review clean 后进入 finish | final-review, finish | finish 不生成 final-review |
| Governance tests | 防行为回退 | wording、state schema、handoff、negative assertions | Node tests | 覆盖 old wording 替换 |

### 3.5 新增/调整功能说明

- `plan-to-exec`：
  - multi-plan package 的 primary handoff 改为 package mode。[D-008]
  - 仍在 `00-overview.md` 记录 child plan list、dependencies、parallel-capable hints，但 package mode 第一版顺序执行。[D-005]
- `subagent-exec`：
  - package input 进入 package mode。
  - child plan input 保持 targeted mode。
  - package mode 内每个 child plan 仍按 task dispatch fresh implementer/reviewer subagents。[D-004]
- `exec`：
  - package input 进入 same-context package mode。[D-003]
  - child plan input 不再走 single-plan finish；它只完成 child plan + plan-level final-review + state update。[D-002]
- `final-review`：
  - 保持 plan-level/spec-level scope。
  - package mode 负责在全部 child ready 后调用 spec-level review。[D-007]
- `finish`：
  - 保持 multi-plan gate。
  - wording 必须使用 schema v2 `plan_review`，不得要求 `plan_final_review`。[D-006]

### 3.6 专项设计检查

| 辅助 skill | 触发原因 | 检查内容 | 设计结论 |
|---|---|---|---|
| `architecture-designer` | workflow state ownership、execution boundary、failure modes、compatibility | 系统边界、状态所有权、并发、失败补偿、兼容性 | package orchestration 放入现有 execution skills；state 仍本地；不新增 skill/CLI；不自动并行 |

## 四、详细设计

### 4.1 输入作用域分类详细设计

#### 4.1.1 需求内容

- 入口：`exec <arg>`、`subagent-exec <arg>`。
- 操作人/调用方：user/agent。
- 前置条件：`arg` 指向 plan 文件、multi-plan package 目录或 `00-overview.md`。
- 输出结果：明确的执行 scope。

#### 4.1.2 方案设计

- 核心逻辑：`exec` 和 `subagent-exec` 使用同一套 scope classification。[D-001]
- 状态流转：
  - `single_plan` -> existing single-plan execution。
  - `package` -> package mode。
  - `child_plan` -> targeted child-plan mode。
  - `invalid` -> block。
- 数据变更：classification 本身不写 state。
- 计算公式：
  - `docs/loopx/plans/<slug>.md` -> `single_plan`
  - `docs/loopx/plans/<slug>/00-overview.md` -> `package`
  - `docs/loopx/plans/<slug>/` -> `package`
  - `docs/loopx/plans/<slug>/NN-*.md` -> `child_plan`
- 幂等设计：同一路径重复 classification 结果相同。
- 权限/越权控制：不涉及用户权限；文件不可读时阻塞。
- 异常处理：缺 overview、路径不存在、非 markdown plan、歧义路径均阻塞。
- 补偿/重试：修正路径或补齐 overview 后重试。
- 日志与审计：执行 skill 的 progress/checkpoint 应记录 resolved scope。

#### 4.1.3 流程步骤

1. 标准化输入路径，移除 `./` 和尾部 `/` 差异。
2. 判断路径是目录还是文件。
3. 目录时要求存在 `00-overview.md`。
4. 文件时按 `00-overview.md`、`NN-*.md`、single-plan `.md` 依次匹配。
5. 生成 scope 和 canonical source path。

#### 4.1.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| package dir 缺 `00-overview.md` | 阻塞 | 报告 missing overview | 不涉及 |
| `00-overview.md` 被当成 child plan | 不允许，必须 package scope | 明确 scope=package | 不涉及 |
| child plan direct input | 只执行该 child plan [D-002] | 不执行 sibling | 不涉及 |
| single plan file | 保持现有 flow | 行为不变 | 不涉及 |
| Windows path separator | normalize 为 `/` | 路径可识别 | 不涉及 |

#### 4.1.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| single-plan `exec/subagent-exec` | 兼容已有 workflow | governance tests |
| numbered child plan direct execution | targeted/resume/manual-control 需要 | TC-002 |

### 4.2 Package state 初始化与校验详细设计

#### 4.2.1 需求内容

- 入口：package mode start。
- 操作人/调用方：`exec` / `subagent-exec` package controller。
- 前置条件：已解析 `00-overview.md`。
- 输出结果：可供 final-review/finish 使用的 `.loopx/multi-plan/<feature-slug>/state.json`。

#### 4.2.2 方案设计

- 核心逻辑：missing state 自动初始化；existing state 严格校验，不自动猜测修复。[D-006]
- 状态流转：
  - missing -> write schema v2 `in_progress` state。
  - valid existing -> continue/resume。
  - invalid/stale/conflicting -> block。
- 数据变更：
  - 初始化写 `.loopx/multi-plan/<feature-slug>/state.json`。
  - child complete 后更新对应 `plans[]` row。
  - spec-level final-review 后更新 `spec_final_review`。
- 计算公式：
  - `feature_slug` 来自 overview package slug 或 package directory name，两者必须一致。
  - `plan_package` 存 canonical path，不带尾部 `/`。
  - `plans[].path` 按 overview child plan list 顺序写入。
- 幂等设计：
  - missing state 初始化只执行一次。
  - valid state 的 complete child rows 可被 package mode 跳过。
  - existing state 与 overview 不一致时不覆盖。
- 权限/越权控制：文件系统写入失败即阻塞。
- 异常处理：
  - invalid JSON 阻塞。
  - duplicate child plan path 阻塞。
  - feature slug/source spec/plan package mismatch 阻塞。
  - schema v1 existing state 可继续由 runtime 兼容读取，但 package mode 新写入必须 schema v2。
- 补偿/重试：人工修正 state 或删除错误 state 后重试；删除 state 会触发重新初始化。
- 日志与审计：package mode summary 记录 state path、initialized/reused、blocked defect。

#### 4.2.3 流程步骤

1. 从 overview 读取 required fields：source spec path、package slug、local state path、child plan list、execution order。
2. 计算 expected state identity。
3. 如果 state 不存在，创建 schema v2 state。
4. 如果 state 存在，解析 JSON 并校验 identity、child list 和 schema shape。
5. 返回 pending/complete child plan list。

#### 4.2.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| state missing | 初始化 | 报告 initialized | 不涉及 |
| invalid JSON | 阻塞 | 报告 state path invalid | 不涉及 |
| duplicate child paths | 阻塞 | 报告 duplicate path | 不涉及 |
| overview 和 state child list 不一致 | 阻塞 | 报告 mismatch | 不涉及 |
| state schema v1 | 兼容读取，但新写 v2 | 报告 legacy/normalized if relevant | 不涉及 |
| state file permission denied | 阻塞 | 报告 write/read failure | 不涉及 |

#### 4.2.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `.loopx/multi-plan/` 是本地状态 | 避免 repo-tracked mutable progress | git status / governance |
| finish runtime v1 compatibility | 避免旧 state 直接不可用 | workflow tests |

### 4.3 `subagent-exec` package mode 详细设计

#### 4.3.1 需求内容

- 入口：`subagent-exec <00-overview.md|plan-dir>`。
- 操作人/调用方：user/agent。
- 前置条件：subagent capability available, package state prepared。
- 输出结果：whole package executed through child plan sequence, final review and finish gate reached。

#### 4.3.2 方案设计

- 核心逻辑：外层 package controller 顺序选择 child plans；每个 child plan 内复用现有 `subagent-exec` task flow。[D-004][D-005]
- 状态流转：
  - package `in_progress` -> child `pending/in_progress/complete` -> package `ready_for_spec_review` -> `ready_for_finish`。
- 数据变更：
  - 每个 child plan-level review 写 `plan_review.status: "passed"`、`reviewed_at`、`summary`、`ready_for_spec_review: true`。
- 计算公式：下一个 child plan = 第一条未满足 `status: complete && plan_review.status: passed && ready_for_spec_review === true` 的 row。
- 幂等设计：已完成 child row 跳过，不重新 dispatch subagents。
- 权限/越权控制：不涉及。
- 异常处理：
  - implementer/reviewer BLOCKED 走现有 `subagent-exec` blocker handling。
  - plan-level final-review 不 clean 不继续 sibling。
  - spec-level final-review 不 clean 不进入 finish。
- 补偿/重试：fix-review/重新执行未完成 child；已完成 child 不重复。
- 日志与审计：progress ledger 继续记录 task-level evidence；package summary 记录 child sequence。

#### 4.3.3 流程步骤

1. 确认 subagent capability。
2. 解析 package scope 并准备 state。
3. 按 state/order 找到下一未完成 child plan。
4. 对该 child plan 按现有 `subagent-exec` 流程逐 task dispatch implementer 和 reviewer subagents。
5. child tasks 全部 clean 后运行 plan-level `final-review`，只更新 state。
6. 重复步骤 3-5，直到全部 child ready。
7. 运行 spec-level `final-review`。
8. review clean 后进入 `finish`。

#### 4.3.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| subagent 不可用 | fallback 到 `exec` 或按现有规则提示 | 不声称使用 subagent-exec | 不涉及 |
| child task review 有 Critical/Important | fix-review 后复审 | package 暂停在该 child | 不涉及 |
| child plan 已完成 | 跳过 | resume 快速进入下一 child | 不涉及 |
| overview 标记可并行 | 忽略自动并行，顺序执行 | 行为可预测 | 不涉及 |

#### 4.3.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| fresh implementer subagent per task | `subagent-exec` 核心价值 | governance wording |
| combined task reviewer per task | 保持 per-task quality gate | governance wording |
| child direct mode 不执行 sibling | targeted/resume 需要 | TC-002 |

### 4.4 `exec` package mode 详细设计

#### 4.4.1 需求内容

- 入口：`exec <00-overview.md|plan-dir>`。
- 操作人/调用方：user/agent。
- 前置条件：package state prepared。
- 输出结果：whole package executed inline without subagents。

#### 4.4.2 方案设计

- 核心逻辑：`exec` 使用与 `subagent-exec` 相同的 package controller，但 child plan 内使用 same-context task execution 和 mandatory checkpoint reviews。[D-003]
- 状态流转：同 4.3。
- 数据变更：同 4.2；`exec` checkpoint 文件仍按 child plan 记录。
- 计算公式：同 package state next-child formula。
- 幂等设计：已完成 child row 跳过；child checkpoint 支持 resume。
- 权限/越权控制：不涉及。
- 异常处理：
  - checkpoint review 不 clean 时走 `fix-review`。
  - final checkpoint 未覆盖所有 changes 时不得进入 child plan-level final-review。
  - child plan-level final-review 不 clean 不继续 sibling。
- 补偿/重试：继续未完成 child；必要时使用 child checkpoint。
- 日志与审计：checkpoint 记录 task evidence，package summary 记录 child progress。

#### 4.4.3 流程步骤

1. 解析 package scope 并准备 state。
2. 为 package run 使用 overview path 记录 `execution-start` 和 `finish-start` source identity。
3. 选择下一未完成 child plan。
4. 按现有 `exec` task loop 执行该 child plan。
5. 按 mandatory checkpoint rules 完成 checkpoint review。
6. 运行 child plan-level `final-review`，更新 state，停止 child-level finish。
7. 继续下一 child。
8. 全部 ready 后运行 spec-level `final-review`，clean 后进入 `finish`。

#### 4.4.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| checkpoint review required | 必须完成 review 后继续 | 和现有 `exec` 一致 | 不涉及 |
| child direct input | child plan 完成后不 run package siblings | targeted mode | 不涉及 |
| package mode 中断 | checkpoint + state resume | 下次跳过 completed child | 不涉及 |
| spec-level final-review 不 clean | 不进入 finish | 需要 fix-review/复审 | 不涉及 |

#### 4.4.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| same-context execution | `exec` 是 no-subagent lane | governance wording |
| mandatory checkpoint review | 保持 inline execution quality gate | existing governance/tests |
| single-plan `exec` final-review + finish | 兼容历史 workflow | regression tests |

### 4.5 `plan-to-exec` handoff 详细设计

#### 4.5.1 需求内容

- 入口：`plan-to-exec` 产出 multi-plan package。
- 操作人/调用方：planning agent。
- 前置条件：plan review clean。
- 输出结果：handoff 推荐 package mode。

#### 4.5.2 方案设计

- 核心逻辑：multi-plan package 的 primary execution handoff 改为 whole-package execution。[D-008]
- 状态流转：不写 runtime state；只写 plan package 和 handoff。
- 数据变更：`00-overview.md` 必须保留 package mode 初始化需要的字段。
- 幂等设计：重复 plan generation 保持 same package metadata。
- 异常处理：如果不能写可解析 overview，不应推荐 package mode。
- 补偿/重试：修正 overview 后重新 handoff。
- 日志与审计：plan review evidence 记录 package mode handoff。

#### 4.5.3 流程步骤

1. `plan-to-exec` 生成 `00-overview.md` 和 child plans。
2. `00-overview.md` 包含 source spec path、package slug、local state path、child plan list、execution order、parallel-capable hints、final gate。
3. handoff 首选：

```text
$subagent-exec docs/loopx/plans/YYYY-MM-DD-feature/00-overview.md
```

4. no-subagent fallback：

```text
$exec docs/loopx/plans/YYYY-MM-DD-feature/00-overview.md
```

5. 文档说明 direct child plan execution 仅用于 targeted/resume/manual-control。

#### 4.5.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| single plan output | 保持原 handoff | 不出现 package mode | 不涉及 |
| multi-plan package | 推荐 package mode | 用户一个入口执行 | 不涉及 |
| child plan 需要单独执行 | 文档保留 direct invocation | resume/targeted 可用 | 不涉及 |

#### 4.5.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| child plans 仍自包含 | review/targeted execution 需要 | plan governance |
| `00-overview.md` 仍记录 parallel-capable info | 人工调度和未来并行设计需要 | snapshot/governance |

### 4.6 final-review 与 finish 收口详细设计

#### 4.6.1 需求内容

- 入口：package mode 发现全部 child plans ready。
- 操作人/调用方：`exec` / `subagent-exec` package controller。
- 前置条件：每个 child row `status: complete`、`plan_review.status: passed`、`ready_for_spec_review: true`。
- 输出结果：spec-level final-review clean 后进入 finish。

#### 4.6.2 方案设计

- 核心逻辑：package mode 自动调用 spec-level `final-review`；只有 clean verdict 才进入 `finish`。[D-007]
- 状态流转：
  - all child ready -> spec-level review pending。
  - spec-level clean -> `spec_final_review.ready_for_finish: "Yes"` -> finish。
  - spec-level not clean -> blocked/fix-review。
- 数据变更：spec-level review 写 canonical final-review report 和 `spec_final_review` state。
- 幂等设计：重复 spec-level review 更新同一 canonical report。
- 异常处理：final-review missing scope、coverage gap、Critical/Important findings 均阻塞 finish。
- 补偿/重试：fix-review 后重新 spec-level final-review。
- 日志与审计：finish report 继续记录 final evidence。

#### 4.6.3 流程步骤

1. package controller 验证所有 child ready。
2. 收集 source spec、overview、child plans、state、execution range/current HEAD。
3. 运行 spec-level `final-review`。
4. 若 `Ready for finish? Yes` 且无 unresolved Critical/Important，进入 `finish`。
5. 若不是 clean，停止并走 fix-review/复审。

#### 4.6.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| 某 child 未 ready | 不运行 spec-level review | 报告缺失 child gate | 不涉及 |
| spec-level review `No` | 不进入 finish | 显示 blocking issues | 不涉及 |
| spec-level review `With fixes` | 先 fix-review/复审 | 不完成 finish | 不涉及 |
| finish gate 与 state 不一致 | finish 阻塞 | 报告 state defect | 不涉及 |

#### 4.6.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| child plan-level final-review 不写 report artifact | 当前 schema v2 设计 | governance tests |
| finish 不生成 final-review | 职责边界 | finish skill governance |
| spec-level final-review 是唯一 package final review artifact | 防止 artifact 分裂 | workflow tests |

### 8.1 灰度方案

- 灰度范围：本地 skill contract / tests；无服务端灰度。

- 降级触发条件：package mode contract 造成执行混乱或 state 初始化缺陷。
- 降级行为：回退 skill wording 和 tests 到 per-child handoff；保留 single/child execution。
- 用户影响：multi-plan package 需重新手工 per-child 执行。
- 恢复方式：修复 package mode 后重新发布。

### 8.3 关联系统/功能影响

| 系统/功能 | 影响 | 依赖动作 | 负责人 | 验证方式 |

| `finish` | wording 对齐 schema v2 gate | 去除 `plan_final_review` 新 contract | loopx maintainers | workflow/governance |

### 8.4 回滚方案

- 回滚条件：package mode contract 造成严重误执行或 state corruption。
- 回滚步骤：
  1. 回退 `exec/subagent-exec/plan-to-exec/finish` skill wording。
  2. 回退相关 governance tests。
  3. 保留 runtime v2 state compatibility，不删除用户本地 `.loopx/multi-plan`。
- 数据回滚：不自动删除 local state；必要时用户手工删除错误 state 文件。
- 配置回滚：不涉及。
- 风险：历史 docs 中 package mode handoff 可能短期存在；current product docs 应随回滚同步。
