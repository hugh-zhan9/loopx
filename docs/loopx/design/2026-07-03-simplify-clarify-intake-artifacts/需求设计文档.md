## 二、需求信息

### 2.1 需求背景

- 背景：当前 `clarify` intake package 默认包含 `clarification.md`、`requirements.md`、`test-cases.md` 三个文件。用户反馈 `clarify/spec` 产物数量偏多，且 `test-cases.md` 当前主要被 runtime 创建、展示和传递，没有被 runtime 语义化消费；它的价值主要来自 skill 契约中的 `TC-*` traceability。
- 需求目的：减少需求澄清阶段的默认 artifact 数量和下游读取成本，让 `requirements.md` 成为 clarify intake package 的唯一 canonical contract，并把 `TC-*` 验收场景合并到 `requirements.md` 内。[D-001]
- 目标用户/使用方：loopx CLI 用户、Codex/Claude/Cursor agent、后续 `spec`、`plan-to-exec`、`review`、`final-review`、`finish` workflow。
- 需求链接：当前对话中的 `$spec "Simplify clarify intake artifacts: make requirements.md canonical, keep clarification.md supporting, remove test-cases.md as a standalone artifact"`。
- 关联原始材料：
  - `src/workflow.mjs`
  - `templates/intake-requirements.md`
  - `templates/intake-test-cases.md`
  - `skills/clarify/SKILL.md`
  - `skills/spec/SKILL.md`
  - `skills/plan-to-exec/SKILL.md`
  - `skills/plan-reviewer/SKILL.md`
  - `src/cli.mjs`
  - `src/html-views.mjs`
  - `scripts/codex-workflow-hook.mjs`
  - `scripts/claude-workflow-hook.mjs`
  - `test/workflow.test.mjs`
  - `test/skill-governance.test.mjs`
  - `test/trellis-hardening.test.mjs`
  - `README.md`、`README.zh-CN.md`、`docs/loopx/cli*.md`、`docs/loopx/skills*.md`、`docs/loopx/specs/installation.md`

### 2.2 需求范围

- 本期范围：
  - 新 `clarify` intake package 只创建 `requirements.md` 和 `clarification.md`。[D-002]
  - `requirements.md` 是 canonical source of truth，包含需求事实、范围、非目标、决策、约束、`AC-*`、`TC-*` 验收场景、开放问题和 handoff。[D-001]
  - `clarification.md` 仅作为 supporting log / resume state，不是下游默认主输入。[D-003]
  - 删除 standalone `test-cases.md` 的 runtime state 字段、模板、CLI/hook/html 展示、文档说明和 governance 断言。[D-004]
  - 当 source 是 intake package 时，`spec`、`plan-to-exec`、`plan-reviewer` 等 skill contract 改为从 `requirements.md` 读取 `AC-*` 与 `TC-*`，只在追溯或恢复时读取 `clarification.md`；当 source 是详细设计文档时，`plan-to-exec` 仍读取该设计文档作为实施计划来源。[D-005]
  - 这是尚未上线前的 breaking change，不保留历史兼容分支，不支持旧 `test-cases.md` intake package 继续作为当前契约输入。[D-006]
- 非目标：
  - 不瘦身 `plan-to-exec` 输出。执行计划仍保持足够详细。
  - 不改变 `spec` 默认产出详细设计文档的路径规则。
  - 不新增 runtime artifact validator 或自动解析 `AC-*`/`TC-*` 内容。
  - 不迁移已有 `docs/loopx/design/`、`docs/loopx/plans/` 历史文档。
  - 不改变 `clarification.md` 的 resume state 职责。
- 决策边界：
  - 可以破坏当前未上线的 runtime state JSON schema 和 public docs contract。
  - 不能让下游重新解释 transcript；`requirements.md` 必须承载足够完整的需求契约。
  - 可以删除 `test_cases_path` 字段；调用方应以 `requirements_path` 为主。
- 依赖方：
  - `workflow.mjs` 负责创建 intake package 和 status artifact。
  - CLI、hooks、HTML view 负责展示当前 state。
  - skill markdown 和 README/docs 负责 agent contract。
  - tests 和 `scripts/verify-skills.mjs` 负责 release gate。
- 约束条件：
  - 使用 Node.js ESM 现有风格，不新增依赖。
  - 继续使用 `node:test`。
  - `package.json.files` 不能发布不存在的 template。
  - `docs/loopx/specs/installation.md` 仍要求 `loopx status --json` 暴露 package 和 child artifact paths；本设计把 child artifacts 收敛为 `requirements_path` 与 `clarification_path`。
- 触发的辅助 skills：`cli-developer`

### 2.3 可行性分析

- 业务可行性：需求明确，用户确认当前不需要兼容旧契约，且目标是减少默认文档和 token 消耗。
- 技术可行性：`test-cases.md` 当前由模板创建、state 引用和 UI 展示组成，没有复杂 runtime 语义解析；移除主要是 contract 和测试同步。
- 团队接受能力：改动集中在 loopx workflow artifact contract，影响面清晰。
- 时间成本：中等，涉及 runtime、skills、docs、tests 多处同步。
- 资源成本：无新增运行时依赖，无新增服务。
- 替代方案：
  - 保留 `test-cases.md` 但下游按需读：文件数仍多，无法解决默认 artifact 膨胀。
  - 只更新 skill 契约不改 runtime：state/CLI 仍鼓励 agent 读三文件，收益有限。
  - 合并为单个 `intake.md`：更激进，会丢失 `clarification.md` 的恢复日志边界。
- 关键风险：
  - 文档和 tests 里 `test-cases.md` 引用较多，漏改会导致治理测试或发布校验失败。
  - 下游 skill 如果只删除文件名但没明确 `requirements.md` 内的 `TC-*` 规则，会削弱测试场景覆盖。

## 三、概要设计

### 3.1 方案总述

- 设计目标：把 `clarify` 默认产物从三文件收敛为两文件，减少下游默认读取面，同时保留 `AC-*` 和 `TC-*` traceability。
- 总体思路：删除 standalone `test-cases.md` artifact，把其语义移动到 `requirements.md` 的 `Acceptance Scenarios` section；runtime state 不再暴露 `test_cases_path`；skill contract 要求 intake package 消费方默认读取 `requirements.md`。经过 `spec` 后再进入 `plan-to-exec` 时，详细设计文档仍是 `plan-to-exec` 的 source。[D-001][D-002][D-004][D-005]
- 核心模块：
  - Runtime intake package creation: `src/workflow.mjs`
  - Templates: `templates/intake-requirements.md`，删除 `templates/intake-test-cases.md`
  - Human/JSON output and hooks: `src/cli.mjs`、`scripts/*workflow-hook.mjs`
  - HTML artifacts: `src/html-views.mjs`
  - Skill contracts: `skills/clarify`、`skills/spec`、`skills/plan-to-exec`、`skills/plan-reviewer`
  - Docs/tests/package surface
- 主要难点：这是 cross-surface contract change，必须同时更新 runtime、published files、docs、tests，避免残留 `test_cases_path` 当前契约。
- 技术指标：
  - 新 `loopx clarify` 不创建 `test-cases.md`。
  - 新 state JSON 不包含 `test_cases_path`。
  - `requirements.md` 模板包含 `Acceptance Criteria` 和 `Acceptance Scenarios`。
  - `npm test` 通过。

### 3.2 整体架构设计

- 业务模式：`clarify` 继续生成本地 `.loopx/intake/YYYY-MM-DD-<slug>/`，供 agent 后续 handoff 使用。
- 系统边界：只改变 loopx 本仓库 runtime artifact contract 和 bundled skill 文档，不改变外部 API 或网络服务。
- 上下游系统：
  - 上游：用户请求、repo evidence、`loopx clarify`。
  - 下游：`spec`、`plan-to-exec`、`exec/subagent-exec`、`review/final-review/finish`。
- 应用架构：CLI/runtime 生成和展示 artifact；skills 定义 agent 如何填充和消费 artifact；tests 锁定 contract。
- 技术架构：Node.js ESM CLI、Markdown templates、bundled skills、Node test suite。
- 数据流转：

```text
loopx clarify <slug>
  -> .loopx/intake/YYYY-MM-DD-<slug>/requirements.md
  -> .loopx/intake/YYYY-MM-DD-<slug>/clarification.md
  -> .loopx/workflows/<slug>/state.json
       intake_package_path
       requirements_path
       clarification_path
       spec_artifact_path = requirements_path

spec / plan-to-exec with intake package source
  -> default read requirements.md
  -> read clarification.md only for process evidence, exact wording, or resume context

plan-to-exec with design document source
  -> read docs/loopx/design/.../需求设计文档.md
  -> preserve D-* plus AC-* / TC-* mappings carried by the design
```

### 3.3 核心流程设计

| 流程 | 触发条件 | 参与系统/模块 | 主流程 | 异常/补偿 | 输出 |
|---|---|---|---|---|---|
| 创建 intake package | 用户运行 `loopx clarify <slug>` | `src/workflow.mjs`、templates | 生成 package 目录，写 `requirements.md` 和 `clarification.md`，写 state | 同日重名继续追加时间后缀 | 两文件 intake package |
| 展示状态 | 用户运行 `loopx status` / hooks 读取 state | CLI、hooks、HTML | 展示 intake、requirements；HTML 渲染 requirements/clarification | state 缺字段时显示现有 fallback，不引入 `test cases` 行 | 简化后的状态输出 |
| 下游消费 intake package | 用户 handoff 到 `spec` 或直接 handoff 到 `plan-to-exec` 的 source 是 intake package | skills | 默认读 `requirements.md`，保留 `AC-*`/`TC-*` 覆盖 | 若 `requirements.md` 缺少 material contract，回 `clarify` | 设计或实施计划 |
| 下游消费设计文档 | 用户从 `spec` handoff 到 `plan-to-exec` 的 source 是详细设计文档 | `plan-to-exec` | 读取详细设计文档，保留其中的 `D-*`、`AC-*`、`TC-*` 映射 | 若设计缺少 material decision，回 `spec` | 实施计划 |

### 3.4 功能模块

| 模块 | 职责 | 关键功能 | 依赖 | 备注 |
|---|---|---|---|---|
| Runtime intake creation | 创建 package 和 state | 删除 `test_cases_path` 和 `test-cases.md` 创建 | templates | Breaking change |
| Requirements template | 承载 canonical contract | 添加 `Acceptance Scenarios` | `clarify` skill | 包含 `TC-*` |
| Clarification template | 支持 Q&A 追溯和 resume | 保持 `Resume State` | `clarify` skill | 非主输入 |
| Output surfaces | 人类/JSON/hooks/html 展示 | 移除 `test cases` 行和 artifact | CLI/hooks/html | JSON field 删除 |
| Skill contracts | 定义 agent 消费方式 | `requirements.md` canonical | bundled skills | 需要 bump metadata.version |
| Governance/tests/docs | 锁定新 contract | 更新 assertions 和 package files | test suite | release gate |

### 3.5 新增/调整功能说明

- `requirements.md` 增加 `## Acceptance Scenarios`：

```markdown
## Acceptance Scenarios

| TC | Covers AC | Scenario | Verification | Status |
|---|---|---|---|---|
| TC-001 | AC-001 | Replace with confirmed black-box acceptance or integration scenario. | manual until a concrete test layer is confirmed | pending |
```

- `clarify` skill 要求：
  - `requirements.md` 是唯一 canonical source。
  - `TC-*` 是 `requirements.md` 内的验收场景。
  - `clarification.md` 只用于 Q&A 过程、用户原话、被挑战假设、拒绝方案、brownfield evidence 和 resume state。
- `spec` / `plan-to-exec` 要求：
  - intake package 默认读取 `requirements.md`。
  - 只有 `requirements.md` 缺口、需要追溯用户原话、恢复中断上下文时读取 `clarification.md`。
  - 如果 `plan-to-exec` 的 source 是 `spec` 生成的详细设计文档，则读取详细设计文档，不绕回只读 intake package。
  - 不再要求独立 `test-cases.md`。

### 3.6 专项设计检查

| 辅助 skill | 触发原因 | 检查内容 | 设计结论 |
|---|---|---|---|
| `cli-developer` | 改变 CLI human output、`--json` state 字段、hook advisory 文本 | human 默认简洁、JSON 机器可读、stdout 不混入额外诊断、public JSON schema 是 intentional breaking change | 删除 `test cases` human 行和 JSON 字段；保留 `requirements_path` 和 `clarification_path` 作为结构化字段；docs/tests 明确 breaking contract |

## 四、详细设计

### 4.1 Runtime intake package 详细设计

#### 4.1.1 需求内容

- 入口：`loopx clarify <slug>`、`initWorkspace(..., { slug })`。
- 操作人/调用方：CLI 用户、tests、installed hooks 间接读取 state。
- 前置条件：loopx workspace 可创建 `.loopx/intake/` 与 `.loopx/workflows/`。
- 输出结果：package 下只有 `requirements.md` 与 `clarification.md`，state 中没有 `test_cases_path`。[D-002][D-004]

#### 4.1.2 方案设计

- 核心逻辑：
  - `intakeChildPaths(packagePath)` 只返回 `clarification_path` 和 `requirements_path`。
  - `createIntakePackage()` 只写 `intake-clarification.md` 与 `intake-requirements.md`。
  - `clarifyStage()` 写 state 时删除 `test_cases_path`。
  - `createInitialState()` 删除初始 `test_cases_path: null`。
  - `statusSummary()` 顶层 payload 删除 `test_cases_path`。
  - `workflowArtifactStatus()` 删除 `test_cases_path` / `test_cases_exists` artifact。
- 状态流转：`spec_artifact_path` 继续指向 `requirements_path`，保持 “requirements 是当前需求工作副本” 的语义。[D-007]
- 数据变更：`.loopx/workflows/<slug>/state.json` schema 破坏性变更，移除 `test_cases_path`。
- 计算公式：不涉及。
- 幂等设计：现有同日 package 重名处理保持不变。
- 权限/越权控制：不涉及。
- 异常处理：模板缺失时沿用现有 `renderTemplate`/文件写入错误。
- 补偿/重试：不涉及自动补偿；命令失败可重跑。
- 日志与审计：不新增日志。

#### 4.1.3 流程步骤

1. 规范化 slug 并计算 package path。
2. 创建 package 目录。
3. 写 `clarification.md`。
4. 写 `requirements.md`。
5. 写 workflow state，其中 `intake_package_path`、`clarification_path`、`requirements_path`、`spec_artifact_path` 指向当前 package 文件。
6. 返回 human/JSON 输出。

#### 4.1.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| 同日同 slug 已存在 | 保持现有时间后缀逻辑 | 生成新的 package 目录 | 无 |
| `requirements.md` 模板缺失 | 命令失败 | CLI 报错 | 测试覆盖 |
| `test-cases.md` 不存在 | 正常行为 | 不展示 `test cases` | 测试覆盖 |
| 旧测试仍查 `test_cases_path` | 更新测试为负断言 | 失败提示实现未同步 | CI |
| 依赖 `spec_artifact_path` 的当前逻辑 | 保持指向 `requirements_path` | 旧内部语义不丢失 | 测试覆盖 |

#### 4.1.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `.loopx/intake/YYYY-MM-DD-<slug>/` 目录格式 | 下游 handoff 仍以 package 目录为参数 | workflow tests |
| `clarification.md` 的 `## Resume State` | 支持中断恢复 | template/governance tests |
| `requirements_path` 与 `spec_artifact_path` | 保持 status 和旧内部命名的需求源语义 | workflow tests |
| `loopx next` handoff package path | 继续让下游按 package 消费 | workflow tests |

### 4.2 Requirements template 详细设计

#### 4.2.1 需求内容

- 入口：`templates/intake-requirements.md`。
- 操作人/调用方：`clarify` skill 和后续 `spec` / `plan-to-exec`。
- 前置条件：clarify 已确认至少一个 material answer 后开始增量写入。
- 输出结果：单文件承载 source facts、intent、scope、non-goals、decisions、constraints、`AC-*`、`TC-*`、open questions、handoff。[D-001]

#### 4.2.2 方案设计

- 核心逻辑：
  - 保留现有 `Acceptance Criteria` section。
  - 新增 `Acceptance Scenarios` section，使用 `TC-*` 表格或小节，必须引用 `AC-*`。
  - 高风险 `AC-*` 仍需要至少一个 boundary/failure/manual scenario，除非明确 deferred rationale。
  - `Open Questions` 保留 `[PENDING]`，handoff 仍记录 `blocked` / `needs_spec` / `direct_to_plan`。
- 状态流转：`requirements.md` 从 pending 到 ready 的语义由 skill 填写，不由 runtime 自动判断。
- 数据变更：模板内容扩大，但文件数减少。
- 计算公式：不涉及。
- 幂等设计：重复 clarify 新建新 package，不覆盖旧 package。
- 权限/越权控制：不涉及。
- 异常处理：如果 `AC-*` 与 `TC-*` 自身冲突，下游回到 `clarify` 修复 `requirements.md`。
- 补偿/重试：agent 通过继续 clarify 更新同一 package。
- 日志与审计：用户原话和过程证据仍写入 `clarification.md`。

#### 4.2.3 流程步骤

1. `clarify` 记录 source facts 和 intent。
2. 每轮确认后更新 scope、non-goals、decisions、constraints。
3. 为可验证需求写 `AC-*`。
4. 在同一文件里为 `AC-*` 写 `TC-*` acceptance scenarios。
5. 更新 open questions 和 handoff recommendation。

#### 4.2.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| `TC-*` 缺少覆盖某个 high-risk AC | handoff 不应 ready，或写 deferred rationale | 下游可见缺口 | governance 文案测试 |
| 需求仅为 docs/test/internal refactor | 允许无产品级 TC，但必须写 rationale | 下游不编造产品验收 | plan-reviewer 检查 |
| `requirements.md` 与 `clarification.md` 冲突 | 以 `requirements.md` 为准；明显陈旧则回 `clarify` | 下游不自行解释 transcript | skill contract |
| 表格过长 | 可改用 `### TC-001` 小节格式，但仍在 `requirements.md` | 文件数不增加 | 人工 review |

#### 4.2.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `AC-*` stable anchors | downstream traceability 依赖 | governance tests |
| `TC-*` stable anchors | plan/review 仍需测试场景覆盖 | governance tests |
| `[PENDING]` 标记 | 支持 resume 和 blocked handoff | template tests |

### 4.3 Clarification log 详细设计

#### 4.3.1 需求内容

- 入口：`templates/intake-clarification.md`。
- 操作人/调用方：`clarify` skill、恢复会话的 agent。
- 前置条件：用户进入澄清流程。
- 输出结果：保留过程证据和 resume state，但不作为 intake package 的下游默认主输入。[D-003]

#### 4.3.2 方案设计

- 核心逻辑：
  - 保持 `Source Inputs`、`Q&A Rounds`、`User Wording`、`Assumptions Challenged`、`Rejected Alternatives`、`Brownfield Evidence`、`Resume State`。
  - skill contract 明确：当 source 是 intake package 时，`spec`/`plan-to-exec` 只有在 `requirements.md` 缺口、需要精确用户原话、或恢复上下文时读取 `clarification.md`。
- 状态流转：Resume State 仍可驱动 readiness fallback 逻辑。
- 数据变更：无结构性变更。
- 计算公式：不涉及。
- 幂等设计：不涉及。
- 权限/越权控制：不涉及。
- 异常处理：如果 `clarification.md` 与 `requirements.md` 冲突，不允许下游凭 transcript 覆盖 contract。
- 补偿/重试：回到 `clarify` 修正 `requirements.md`。
- 日志与审计：继续承担审计日志。

#### 4.3.3 流程步骤

1. 记录原始输入。
2. 逐轮追加 Q&A。
3. 标记假设、拒绝方案和 repo evidence。
4. 更新 `Resume State`。
5. 把确认后的 contract 同步到 `requirements.md`。

#### 4.3.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| 下游需要用户原话 | 读取 `clarification.md` | token 成本为按需 | 无 |
| 只有 `clarification.md` 有某个决策 | 不能作为 ready contract，回 `clarify` 写入 `requirements.md` | 下游停止扩展 | skill contract |
| Resume State stale | 沿用现有 status fallback 测试更新 | readiness 判断不被破坏 | workflow tests |

#### 4.3.5 不变行为

### 4.5 Skill contract 详细设计

#### 4.5.1 需求内容

- 入口：bundled `skills/*/SKILL.md`。
- 操作人/调用方：agent。
- 前置条件：用户调用相应 skill。
- 输出结果：所有当前 skill contract 不再把 standalone `test-cases.md` 作为当前输入。[D-005]

#### 4.5.2 方案设计

- 核心逻辑：
  - `clarify`：
    - 输出只列 `clarification.md` 和 `requirements.md`。
    - `requirements.md` 记录 canonical requirement contract 和 `TC-*` acceptance scenarios。
    - `clarification.md` 记录 process/resume。
    - main-chain handoff rule 改为下游消费 `requirements.md` 中的 `AC-*`/`TC-*`。
  - `spec`：
    - intake package 输入默认读 `requirements.md`。
    - `clarification.md` 仅按需读取。
    - detailed design verification strategy 从 `requirements.md` 内的 `TC-*` 映射到设计级策略。
  - `plan-to-exec`：
    - intake package 输入默认读 `requirements.md`。
    - detailed design 输入默认读设计文档，并保留设计文档中的 `D-*`、`AC-*`、`TC-*` 映射。
    - intake-sourced plan 保留 `AC-*` 与 `TC-*` 覆盖，来源是 `requirements.md`。
    - self-review 的 test-case coverage 改为检查 source requirements 中的 `TC-*`。
  - `plan-reviewer`：
    - source 类型说明改为 intake package with canonical `requirements.md`。
  - `review` / `final-review`：
    - 若仅泛称 `TC-*` anchors，不要求改；若提到 file-specific `test-cases.md`，同步删除。
- 状态流转：不涉及。
- 数据变更：skill metadata.version 需要按实际改动逐个 bump。
- 计算公式：不涉及。
- 幂等设计：不涉及。
- 权限/越权控制：不涉及。
- 异常处理：如果 `requirements.md` 缺少 `AC-*` 或 `TC-*`，route back to `clarify`，不要由 `spec`/`plan-to-exec` 编造。
- 补偿/重试：回 `clarify` 修正 canonical contract。
- 日志与审计：`clarification.md` 可用于解释原话和历史。

#### 4.5.3 流程步骤

1. `clarify` 写 `requirements.md` 和 `clarification.md`。
2. `spec` 读取 `requirements.md`，必要时读取 `clarification.md`，生成设计。
3. `plan-to-exec` 读取设计或 requirements，映射 `AC-*`/`TC-*` 到 tasks/verifications。
4. `review`/`final-review` 使用 plan/design 中保留的 anchors。

#### 4.5.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| requirements 缺测试场景 | `spec` 或 `plan-to-exec` 回 `clarify`，除非有 explicit deferred rationale | 不继续扩展需求 | governance tests |
| clarification 有额外决策 | 不作为主 contract | 下游要求更新 requirements | skill contract |
| plan-to-exec source 是 detailed design | 沿用 design 内的 anchors 和 verification strategy | 不依赖 intake package 形态 | plan governance |

#### 4.5.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `AC-*` / `TC-*` traceability | 主链闭环仍需要 | governance tests |
| `clarification.md` 按需读取 | 过程证据仍有价值 | skill contract tests |
| `plan-to-exec` 详细 plan 输出 | 执行正确率优先 | 不改相关 plan tests |
