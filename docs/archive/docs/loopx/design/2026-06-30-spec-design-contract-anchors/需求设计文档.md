## 二、需求信息

### 2.1 需求背景

- 背景：用户明确要求 `spec` 输出的设计文档继续服务于人类审阅，同时希望吸收 Harness Engineering 中 `D-*` 设计改动点的可追踪能力。
- 需求目的：让 `spec` 生成的人类设计文档携带稳定设计契约锚点，使 `plan-to-exec` 和 `review` 能把需求、设计、任务和验证串联起来。
- 目标用户/使用方：使用 loopx workflow skills 的 Codex/Claude 风格 coding agent、维护 loopx skill 契约的开发者、后续执行 `plan-to-exec` 和 `review` 的 agent。
- 需求链接：
  - [设计提案](./设计提案.md)
  - `.loopx/intake/2026-06-30-spec-design-contract-anchors/requirements.md`
  - `.loopx/intake/2026-06-30-spec-design-contract-anchors/test-cases.md`
  - `.loopx/intake/2026-06-30-spec-design-contract-anchors/clarification.md`
- 关联原始材料：
  - `skills/spec/SKILL.md`
  - `skills/spec/DESIGN_SPEC_TEMPLATE.md`
  - `skills/spec/references/design-proposal.md`
  - `skills/plan-to-exec/SKILL.md`
  - `skills/review/SKILL.md`
  - `docs/articles/harness-engineering-loopx-takeaways.md`
  - `docs/loopx/specs/installation.md`
  - `test/skill-governance.test.mjs`

### 2.2 需求范围

- 本期范围：
  - 更新 `spec` skill contract，要求 implementation-relevant 详细设计决策带 `D-*` 锚点。[D-001][D-002]
  - 定义 `D-*` 契约条目的最小字段和适用边界。[D-003]
  - 要求 `D-*` inline 出现在正文决策旁，并在详细设计末尾建立完整索引表。[D-004]
  - 明确 support lenses 合并进统一设计文档，不产生第二权威 contract 文件。[D-005]
  - 保留 intake package 的 `TC-*` verification coverage 映射规则。[D-006]
  - 更新 `plan-to-exec` 消费 `D-*` 的计划规则。[D-007]
  - 更新 `review` Stage 1 spec compliance 对 `D-*` 的检查规则。[D-008]
  - 更新治理测试和 skill metadata version，仅限改动的 skill。[D-009]
- 非目标：
  - 不新增 runtime state machine、CLI 命令、状态字段或独立 contract artifact。
  - 不迁移历史设计文档。
  - 不要求 proposal-only、research-only、explanatory 或无实现输出设计强制写 `D-*`。
  - 不把所有 contract category 变成每份设计的必填 checklist。
  - 不把 `final-review` 完整矩阵支持纳入第一版门禁。
- 决策边界：
  - `spec` 负责生成设计决策文档，不写实施计划。
  - `plan-to-exec` 负责把设计锚点映射到任务、验证和 deferred rows，不重新做设计。
  - `review` 负责先做 spec compliance，再做 code quality。
  - support lenses 是检查输入，不是 workflow state 或独立权威来源。
- 依赖方：
  - `spec` skill 和模板。
  - `plan-to-exec` skill。
  - `review` skill。
  - `test/skill-governance.test.mjs`。
  - `scripts/verify-skills.mjs` 发布门禁。
- 约束条件：
  - 保持现有 spec 输出路径。
  - 保持详细设计中文模板章节顺序。
  - 保持 intake package flow 和 `TC-*` coverage 规则。
  - 修改 bundled skill docs 时只 bump 内容或行为契约变更的 `metadata.version`。
  - 运行 `node scripts/verify-skills.mjs`。
- 触发的辅助 skills：`architecture-designer`

### 2.3 可行性分析

- 业务可行性：需求已澄清，AC-001 至 AC-005 均为 confirmed，无开放问题。
- 技术可行性：现有 skill docs 已有 AC/TC 和 spec compliance 基础；新增 `D-*` 是文档契约变化，不需要 runtime 依赖。
- 团队接受能力：变更集中在 skill docs、模板和治理测试，符合 loopx skill-first 维护方式。
- 时间成本：中等。需要同步三份 skill contract、一个模板和治理测试。
- 资源成本：极低。无新依赖、无服务资源。
- 替代方案：独立 contract 文件、只写末尾表、只写 inline、同步改 final-review、引入 CLI/runtime 均已在设计提案中拒绝。
- 关键风险：
  - `D-*` 过多导致设计文档变成 checklist。
  - `plan-to-exec` 或 `review` 只保留关键词，不真正做覆盖判断。
  - 治理测试无法完全证明人工 workflow 质量，需要保留 TC 手动检查。

## 三、概要设计

### 3.1 方案总述

- 设计目标：在不牺牲人类审阅性的前提下，让设计决策可被稳定引用、计划覆盖和 review 检查。
- 总体思路：给 implementation-relevant 决策加 `D-*` inline anchor，详细设计末尾汇总索引；下游 `plan-to-exec` 和 `review` 读取并保留这些锚点。[D-001][D-004][D-007][D-008]
- 核心模块：
  - `skills/spec/SKILL.md`
  - `skills/spec/DESIGN_SPEC_TEMPLATE.md`
  - `skills/plan-to-exec/SKILL.md`
  - `skills/review/SKILL.md`
  - `test/skill-governance.test.mjs`
- 主要难点：
  - 控制 `D-*` 的适用范围，避免过度结构化。
  - 让 `D-*` 与 `AC-*`、`TC-*` 形成桥接，而不是新增一套孤立编号。
  - 让 support lenses 的结论合并进统一设计。
- 技术指标：
  - `spec` skill 明确 `D-*` 适用范围、inline 位置、索引表和 not applicable 条件。
  - `plan-to-exec` skill 明确任务、验证和 deferred rows 如何携带 `D-*`。
  - `review` skill 明确 Stage 1 检查 `AC-*` 与 `D-*`。
  - `test/skill-governance.test.mjs` 覆盖关键文档契约。
  - `node scripts/verify-skills.mjs` 通过。

### 3.2 整体架构设计

- 业务模式：`clarify` 产出 `AC-*` 和 `TC-*`，`spec` 产出带 `D-*` 的设计，`plan-to-exec` 生成覆盖 AC/D/TC 的计划，`review` 先检查实现是否符合需求与设计契约。
- 系统边界：
  - `spec` 是唯一设计权威来源。
  - support lenses 只作为检查清单输入。
  - `plan-to-exec` 不重新解释设计，只做任务映射。
  - `review` 不补设计，只判定实现和设计是否一致。
- 上下游系统：
  - 上游：`.loopx/intake/2026-06-30-spec-design-contract-anchors/requirements.md` 和 `test-cases.md`。
  - 当前：`spec` proposal 和 detailed design。
  - 下游：`plan-to-exec`、`exec`/`subagent-exec`、`review`、后续 `final-review`。
- 应用架构：Node.js package 中的 markdown skill contracts 和 Node test governance，无运行时代码架构变化。
- 技术架构：无新增依赖、无新增 CLI surface、无新增 persisted runtime state。[D-009]
- 数据流转：

```text
.loopx/intake/.../requirements.md  (AC-*)
.loopx/intake/.../test-cases.md    (TC-* -> AC-*)
  -> spec
  -> docs/loopx/design/.../需求设计文档.md (D-* -> AC-*, TC strategy)
  -> plan-to-exec (tasks -> AC-* + D-* + TC verification)
  -> review (spec compliance checks AC-* + D-*)
```

### 3.3 核心流程设计

| 流程 | 触发条件 | 参与系统/模块 | 主流程 | 异常/补偿 | 输出 |
|---|---|---|---|---|---|
| 生成带锚点设计 | `spec` 处理有实现相关决策的 source | `spec` skill、support lenses | 写人类可读正文，并在关键决策旁插入 `D-*` | 无实现决策时标 not applicable | 设计提案、详细设计 |
| 汇总设计索引 | 详细设计完成前 | `spec` skill、详细设计模板 | 收集所有 `D-*`，写末尾索引表 | 索引缺项时补齐或返回 spec 修正文档 | `D-*` index |
| 保留 TC 覆盖 | source 是 intake package | `spec` skill | 将 `TC-*` 映射到验证策略、人工检查或 deferred-with-rationale | AC/TC 冲突时返回 clarify | verification strategy |
| 计划消费 D | `plan-to-exec` 读取 design spec | `plan-to-exec` skill | 每个相关 task 写 Source AC、Design anchors、Verification | `D-*` 无任务覆盖时 deferred 或返回 spec | implementation plan |
| review 检查 D | 实现完成后请求 review | `review` skill | Stage 1 检查 AC/D 合规，Stage 2 再看 code quality | D 违反时先修实现或设计 | review findings |

### 3.4 功能模块

| 模块 | 职责 | 关键功能 | 依赖 | 备注 |
|---|---|---|---|---|
| `spec` skill | 生成统一设计文档 | `D-*` 规则、support lens 合并、TC preservation | intake package、设计模板 | 不写计划 |
| `DESIGN_SPEC_TEMPLATE.md` | 约束详细设计结构 | 增加设计决策索引位置 | `spec` skill | 保持原章节顺序 |
| `plan-to-exec` skill | 生成实施计划 | 任务映射 `AC-*`、`D-*`、`TC-*` | design spec | 不重开设计 |

### 3.5 新增/调整功能说明

`spec` 新增/调整：

- detailed design 有 implementation-relevant decisions 时，关键决策必须有稳定 `D-*`。[D-002]
- `D-*` 放在正文决策旁，并在详细设计末尾完整列出。[D-004]
- 每条设计契约尽量引用 Source AC。[D-003]
- 无实现决策的 spec 可以写 `Design anchors: not applicable`，并说明原因。[D-002]

`plan-to-exec` 新增/调整：

- 当 source design 有 `D-*` 时，task、verification 或 deferred rows 必须保留相关 `D-*`。[D-007]
- self-review 增加 design anchor coverage 检查。

`review` 新增/调整：

- Stage 1 spec compliance 检查 AC 和 D 覆盖。[D-008]
- 未覆盖、偏离或新增未授权行为优先按 spec compliance finding 处理。

## 四、详细设计

### 4.1 spec D-* 设计契约详细设计

#### 4.1.1 需求内容

- 入口：`$spec .loopx/intake/2026-06-30-spec-design-contract-anchors/`，以及未来任何包含实现相关决策的 spec source。
- 操作人/调用方：主 agent、`spec` skill、support lens skill。
- 前置条件：requirements 已澄清；若 source 是 intake package，`requirements.md` 与 `test-cases.md` 的 `AC-*` 不冲突。
- 输出结果：人类可读的 `设计提案.md` 和 `需求设计文档.md`，其中关键设计决策可由 `D-*` 稳定引用。[D-001]

#### 4.1.2 方案设计

- 核心逻辑：
  - `spec` 先按原规则阅读 source、repo specs、memory 和相关代码/docs。
  - 判断是否存在 implementation-relevant decisions。
  - 存在时，为关键决策分配稳定 `D-001`、`D-002` 等锚点。[D-002]
  - 在正文对应决策旁写 inline anchor，保持上下文可读。[D-004]
  - 在详细设计末尾写完整索引表，列出 Source AC、contract type、decision summary、downstream expectation。[D-003][D-004]
- 状态流转：不新增 workflow 状态。设计文档从 draft 到 review 仍由文件和后续人工/agent review 表达。
- 数据变更：只新增/修改 markdown skill docs、模板、治理测试和生成的设计文档。
- 计算公式：无。
- 幂等设计：
  - 同一设计文档内 `D-*` 稳定，不因段落编辑随意重排。
  - 新增决策时追加新编号；删除决策时可保留索引记录为 removed/deferred，或在同一变更中更新所有引用。
- 权限/越权控制：不涉及外部权限；只受 repo 文件读写权限约束。
- 异常处理：
  - AC/TC 冲突：停止并返回 `clarify`。
  - 设计决策无法归属现有 AC：可标 Source AC 为 `not_applicable` 并写 rationale；若暗含新需求，返回 `clarify`。
  - `D-*` 索引缺失：设计不完整，不进入 `plan-to-exec`。
- 补偿/重试：修改设计文档即可；无 runtime rollback。
- 日志与审计：git diff 和文档索引保留决策变化。

#### 4.1.3 流程步骤

1. 读取 source requirements/test cases。
2. 确认 support lenses。
3. 写 proposal，记录主要方向和边界。
4. 写 detailed design 时标出 implementation-relevant decisions。
5. 为每个关键决策分配 `D-*`。
6. 在正文决策旁写 inline anchor。
7. 在详细设计末尾写完整 `D-*` 索引。
8. 将 `TC-*` 覆盖映射到验证策略。
9. 自查 `AC-*`、`TC-*`、`D-*` 是否互相一致。

#### 4.1.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| 正常详细设计含实现决策 | 写 inline `D-*` 和末尾索引 | reviewer 可按 D 查找 | 无 |
| proposal-only 或 research-only | 写 `Design anchors: not applicable` 和原因 | 不出现 fake anchors | 无 |
| 非法输入：requirements/test-cases 缺失 | 停止并返回 clarify/source 修复 | 无设计输出或输出 blocked 说明 | 无 |
| AC/TC 冲突 | 停止，返回 `clarify` | 明确冲突原因 | 无 |
| 重复引用同一决策 | 允许正文多处引用同一 `D-*` | 索引表保持一条 | 无 |
| 并发编辑同一设计文档 | 依赖 git diff/review 发现冲突 | merge conflict 或 review finding | 无 |
| 旧设计文档无 D | 不迁移历史 | 下游仅对新/更新 spec 使用 D | 无 |
| 回滚 | revert 文档和测试改动 | 无 runtime 残留 | 无 |

#### 4.1.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| spec 输出路径 | 已是 skill 契约 | skill governance assertions |
| 详细设计中文章节顺序 | 模板约束 | markdown review |
| `TC-*` preservation | 已有 intake package 契约 | TC-004、skill governance assertions |
| support lenses 不替代 spec | 已有 spec/lens 边界 | TC-003、文档检查 |

### 4.2 plan-to-exec D-* 消费详细设计

#### 4.2.1 需求内容

- 入口：`$plan-to-exec docs/loopx/design/2026-06-30-spec-design-contract-anchors/需求设计文档.md`。
- 操作人/调用方：`plan-to-exec` skill、后续 `exec` 或 `subagent-exec`。
- 前置条件：source design 的 `D-*` 索引完整，且无 material open question。
- 输出结果：实施计划中任务、验证或 deferred rows 显式引用相关 `D-*`。[D-007]

#### 4.2.2 方案设计

- 核心逻辑：
  - 读取 detailed design 的 `D-*` 索引。
  - 为每个 task 写 `Source AC` 和 `Design anchors`。
  - 对无法在第一版实现的 D 写 deferred-with-rationale。
  - self-review 检查每个 D 是否被任务、验证或 deferred 行覆盖。
- 状态流转：不新增状态；延续计划 checklist。
- 数据变更：只生成 plan markdown。
- 幂等设计：重复运行 plan 可生成同样锚点映射；若设计锚点变化，以最新 source design 为准。
- 权限/越权控制：不涉及外部权限。
- 异常处理：
  - D 索引缺失或互相冲突：返回 `spec`。
  - 计划需要新增设计行为：返回 `spec` 或 `clarify`。
- 补偿/重试：更新 design 后重跑 plan。
- 日志与审计：plan 中保留 source path、AC/D/TC 映射。

#### 4.2.3 流程步骤

1. 读取 source design。
2. 抽取 `AC-*`、`D-*`、`TC-*`。
3. 设计 file structure。
4. 切分 bite-sized tasks。
5. 给每个 task 写 Source AC 和 Design anchors。
6. 给每个 task 写 verification，并覆盖相关 TC。
7. 写 deferred-with-rationale 行。
8. 自查 design anchor coverage。

#### 4.2.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| D 有明确实现任务 | task 引用该 D | implementer 可直接看到约束 | 无 |
| D 只影响 review 或文档 | verification/review focus 引用该 D | 不强行拆任务 | 无 |
| D 本期不实现 | deferred-with-rationale | 风险显式 | 无 |
| D 与 AC 冲突 | 返回 spec/clarify | 不生成不可信计划 | 无 |
| D 索引缺失 | 返回 spec | plan blocked | 无 |
| 重复运行 plan | 以最新 design 为准 | 可能覆盖旧计划，需 git review | 无 |

#### 4.2.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| plan 输出路径 | 现有 skill contract | governance tests |
| bite-sized task structure | 现有执行契约 | plan self-review |
| `AC-*` preservation | 已有 requirements traceability | skill governance |
| `TC-*` coverage | 已有 intake package 规则 | TC-004 |

### 4.3 review D-* 合规检查详细设计

#### 4.3.1 需求内容

- 入口：实现完成后执行 `review`，并提供 source plan/spec。
- 操作人/调用方：主 agent、reviewer subagent、`review` skill。
- 前置条件：有 formal plan/spec 时执行 Stage 1 spec compliance。
- 输出结果：review findings 能指出实现覆盖或违反哪些 `D-*`，未覆盖或 deferred 的设计决策显式可见。[D-008]

#### 4.3.2 方案设计

- 核心逻辑：
  - Stage 1 先读取 task requirements、plan/spec、implementation summary 和 diff。
  - 如果 source 有 `D-*`，检查相关实现是否符合 D。
  - 发现缺失、额外行为或偏离 D 时，作为 spec compliance finding。
  - Stage 1 通过后，Stage 2 再执行 code quality。
- 状态流转：
  - spec compliance fail：修实现或返回 spec。
  - spec compliance pass：进入 code quality。
  - code quality fail：按现有 review 反馈处理。
- 数据变更：review 输出文本或报告；不改 runtime state。
- 幂等设计：同一 diff 和 source spec 应给出一致 D coverage 判断。
- 权限/越权控制：reviewer 仍应以只读检查为主；修复由主 agent 或 fix-review 执行。
- 异常处理：
  - 没有 formal spec/plan：按现有规则 degrade 为 intent check，不强行要求 D。
  - source 有 D 但 implementation summary 未提：reviewer 仍需从 source 和 diff 检查。
- 补偿/重试：修复后重新 request relevant review stage。
- 日志与审计：review findings 引用 D anchors。

#### 4.3.3 流程步骤

1. 确认是否有 formal source。
2. 读取 source 中的 AC 和 D。
3. 读取 diff 和实现摘要。
4. 检查是否覆盖每个相关 D。
5. 检查是否新增 source 未授权行为。
6. 输出 Critical/Important/Suggestion findings。
7. Stage 1 通过后进入 code quality。

#### 4.3.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
