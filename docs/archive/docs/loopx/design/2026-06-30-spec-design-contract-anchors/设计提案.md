# spec 设计文档增加可追踪 D-* 契约锚点

Author(s): loopx maintainers

## Abstract / 摘要

我们保留 `spec` 的核心定位：输出给人审阅的 `设计提案.md` 和 `需求设计文档.md`。本次变化是在人类可读设计文档中增加稳定的 `D-*` 设计决策锚点和简洁契约摘要，使后续 `plan-to-exec` 与 `review` 能把 `AC-* -> D-* -> task/review/verification` 串起来，而不是重新解释整篇设计。`D-*` 不是新 runtime artifact，也不是替代正文的机器表格；它是正文中的 inline 决策标记，加上详细设计末尾的完整索引表。[D-001][D-002][D-004]

第一版只更新 `spec`、`plan-to-exec`、`review` 的 skill 契约和治理测试。`final-review` 对 `D-*` 的完整矩阵支持作为后续增强，不作为本次交付门禁。[D-007][D-008][D-009]

## Background / 背景与动机

intake package 已确认用户对 `spec` 的定位：`spec` 输出的是设计文档，设计文档是给人审阅的。用户同时接受 Harness Engineering 文章中“设计文档需要机器可比对契约”的纪律，但明确不希望把 `spec` 变成纯结构化机器产物。

当前 repo 证据：

- `skills/spec/SKILL.md` 已规定新 spec 默认输出 `docs/loopx/design/YYYY-MM-DD-<kebab-slug>/设计提案.md` 和 `需求设计文档.md`。
- `skills/spec/SKILL.md` 已支持 `.loopx/intake/YYYY-MM-DD-<slug>/`，并要求详细设计引用 `requirements.md`、`test-cases.md`，保留 `TC-*` 覆盖。
- `skills/plan-to-exec/SKILL.md` 已要求计划保留 `AC-*`，并覆盖 `TC-*` 场景。
- `skills/review/SKILL.md` 已把 review 分为 “spec compliance first, then code quality”。
- `docs/articles/harness-engineering-loopx-takeaways.md` 建议 `spec` 加入 `D-*` 设计改动点，让实现和 reviewer 能按设计项逐项比对。

因此本次设计不需要新增流程状态、CLI 命令或单独 contract 文件。最小有效改动是把 `D-*` 接入现有的人类设计文档、计划生成和 review 合规检查入口。[D-009]

## Goals And Non-Goals / 目标与非目标

目标：

- `spec` 输出继续是可审阅的普通设计文档，而不是机器专用 artifact。[D-001]
- 对影响实现行为、API、数据、状态、CLI、权限、兼容、发布或运维的设计决策，写入稳定 `D-*` 锚点和简洁契约条目，并尽量标明来源 `AC-*`。[D-002][D-003]
- `D-*` 出现在正文相关决策旁，详细设计末尾有完整索引表，方便人工审阅和下游查找。[D-004]
- support lenses 只作为 `spec` 的检查清单输入，结果合并进统一设计文档，不产生需要下游 reconcile 的第二权威来源。[D-005]
- `test-cases.md` 中的 `TC-*` 覆盖继续在详细设计验证策略中保留。[D-006]
- 第一版让 `plan-to-exec` 和 `review` 消费 `D-*`，并显式记录未覆盖或延期的设计决策。[D-007][D-008]

非目标：

- 不把 `设计提案.md` 或 `需求设计文档.md` 替换成纯结构化 contract 文件。
- 不要求 proposal-only、research-only、explanatory 或没有实现输出的 spec 强行发明 `D-*`。
- 不让所有可能契约类别都成为每份设计的必填大 checklist。
- 不新增 runtime state machine、CLI 命令、状态字段或独立 artifact validator。
- 不在第一版强制 `final-review` 支持 `D-*` 完整矩阵；后续可单独设计。

## Proposal / 设计方案

### 1. `spec` 仍以人类设计文档为主

`spec` 的正文结构不变：设计提案继续解释背景、目标、方案、取舍、边界和兼容性；详细设计继续使用现有中文模板章节。`D-*` 只给关键设计决策加稳定引用，不替代设计叙述。[D-001]

示例：

```markdown
`spec` 对实现相关决策必须写 inline `D-*` 锚点，并在详细设计末尾维护索引表。[D-002]
```

边界：如果输出是 proposal-only、research-only、explanatory，或明确没有实现相关决策，可写 `Design anchors: not applicable` 并说明原因，不需要伪造锚点。[D-002]

### 2. implementation-relevant 决策必须有 `D-*`

详细设计中，只要决策影响下列任一表面，就应给出 `D-*`：[D-002]

- 行为和用户可观察结果
- API、CLI、函数签名、输出格式或错误模型
- 数据、状态、权限、兼容性、迁移、发布、回滚或运维
- 下游计划和 review 必须遵守的边界

每个契约条目至少包含：

- `D-*` anchor
- Source AC，若 intake 中存在对应 `AC-*`
- Contract type，例如 behavior、data、state、CLI、compatibility、operations、workflow contract
- Decision
- Boundary / non-goal
- Downstream expectation，说明 `plan-to-exec` 或 `review` 应如何消费[D-003]

### 3. inline anchor 加详细设计末尾索引

设计正文中的 inline anchor 保留上下文，让 reviewer 不需要跳到表格才能理解设计。详细设计末尾增加完整索引表，作为 downstream lookup 和 coverage check 的唯一集中视图。[D-004]

表格建议列：

| D anchor | Source AC | Contract type | Decision summary | Downstream expectation |
|---|---|---|---|---|
| `D-001` | `AC-001` | workflow contract | `spec` remains human-readable | `plan-to-exec` must not replace narrative with a machine-only contract |

### 4. support lenses 合并进统一 spec

触发 `api-designer`、`sql-style`、`architecture-designer`、`cli-developer` 等 support lenses 时，`spec` 需要记录触发原因和检查结论，但这些 lens 不输出第二份权威设计合同。它们的结论应体现在统一设计文档的正文、边界、兼容性、测试策略或 `D-*` 条目中。[D-005]

本次设计触发 `architecture-designer`，原因是它改变 skill 间长期契约边界和 downstream consumption 关系；不触发 API、SQL、CLI、Go 或 Kratos lens。

### 5. `plan-to-exec` 消费 `D-*`

当 source design 包含 `D-*`，`plan-to-exec` 生成任务时应把相关设计锚点写进 task、verification 或 deferred-with-rationale 行。[D-007]

示例：

```markdown
### Task 2: Add design anchor requirements to spec skill

Source AC: AC-001, AC-002
Design anchors: D-001, D-002, D-003, D-004
Verification: node --test test/skill-governance.test.mjs
```

计划不得用 `D-*` 重新设计需求；如果设计锚点缺失、互相冲突，或某个实现相关决策没有落入任何 task/deferred 行，计划应返回 `spec` 修正。

### 6. `review` 先检查 `AC-*` 与 `D-*` 合规

`review` 的 Stage 1 spec compliance 应在已有 AC 覆盖基础上检查 `D-*`：[D-008]

- 实现是否覆盖相关 `D-*`。
- 是否引入了设计文档没有批准的新行为。
- 未覆盖的 `D-*` 是否有明确 deferred rationale。
- support lens 相关设计约束是否被遵守。

Stage 2 code quality 仍然在 spec compliance 之后执行，避免先审代码风格却漏掉契约偏差。

## Support Lens Checks / 专项设计检查

| Support lens | Trigger | Design checks applied | Result |
|---|---|---|---|
| `architecture-designer` | `D-*` 改变 `spec`、`plan-to-exec`、`review` 之间的长期契约和边界 | 明确权威来源、下游所有权、兼容边界、失败模式、回滚路径和运营成本 | 采用统一文档内锚点；不新增第二权威 contract 文件；不新增 runtime/CLI 表面 |

## Boundary Scenarios / 边界场景

| 场景 | 处理 |
|---|---|
| 详细设计有实现相关决策 | 必须给关键决策 inline `D-*`，并在末尾索引表列出。[D-002][D-004] |
| proposal-only、research-only、explanatory 或无实现输出设计 | 可写 `Design anchors: not applicable` 和短原因，不强制发明 fake anchor。[D-002] |
| intake package 缺 `AC-*` 或 `TC-*` | 沿用现有 `spec` 规则，回到 `clarify`，不由设计阶段自行补需求。[D-006] |
| `requirements.md` 与 `test-cases.md` 的 AC 冲突 | 沿用现有规则，停止并返回 `clarify`，不在 `spec` 内调和。 |
| support lens 产出独立建议 | 只作为检查输入；必须并入统一设计文档，不能形成第二权威 contract。[D-005] |
| 同一 `D-*` 被重复引用 | 允许重复引用同一稳定决策；索引表只保留一条权威摘要。 |
| `plan-to-exec` 发现某个 `D-*` 无法安排任务 | 写 deferred-with-rationale，或返回 `spec` 修正；不能静默丢弃。[D-007] |
| `review` 发现实现覆盖 AC 但违反 D | Stage 1 spec compliance 失败，先修契约偏差，再进入 code quality。[D-008] |
| 依赖超时或部分失败 | 不涉及外部依赖；对应到 agent 工作流时表现为未能读取 source 或 skill 文件，应停止并说明缺失文件。 |
| 权限失败 | 本变更只修改 repo 文件；如果无法读取/写入 skill docs 或测试，实施必须失败并报告，不降级为口头约定。 |
| 并发或重复执行 | 两次 `spec` 可生成相同 `D-*` 文档；实施时以 git diff 和最终文件为准，不引入共享 runtime 锁。 |
| legacy design docs | 不迁移历史 `docs/loopx/design/*`；新规则只约束新 `spec` 输出和后续更新过的 skill 文档。 |
| rollback | 回滚 skill 文档和测试即可；没有 runtime state、数据迁移或 CLI surface 需要回滚。[D-009] |
| unchanged behavior | 保持既有输出路径、中文详细设计章节顺序、intake package flow、`TC-*` preservation 和 review 两阶段顺序。 |

## Rationale / 理由与取舍

| Alternative | Why Not |
|---|---|
| 生成独立 `design-contract.json` 或 `contracts.md` | 会把权威来源拆成两份，下游需要 reconcile；也偏离用户强调的“设计文档给人审阅”。 |
| 只在末尾放 `D-*` 表，不做正文 inline | 人类 reviewer 看正文时无法在上下文中看到哪个决策可被下游引用。 |
| 只做正文 inline，不放末尾索引 | downstream planning/review 需要全文搜索，无法快速做覆盖检查。 |
| 每份 spec 都强制完整契约 checklist | 对 research-only 或小型 explanatory 文档制造噪音，违背“只在实现相关决策上加锚点”的范围。 |
| 第一版同步改 `final-review` 完整矩阵 | intake 已确认这不是第一 slice；会扩大范围并增加计划风险。 |
| 新增 runtime/CLI command 管理 D anchors | 当前问题是 skill 文档契约和 downstream consumption，不需要运行时状态。 |

选择 inline anchor 加末尾索引，是因为它同时满足人类审阅和机器/agent 查找；选择只改 `spec`、`plan-to-exec`、`review`，是因为这些正是 AC/TC 到计划和评审之间的既有契约入口。

## Compatibility / 兼容性

本方案对 runtime 和 CLI 不破坏兼容：

- `spec` 输出路径保持 `docs/loopx/design/YYYY-MM-DD-<kebab-slug>/设计提案.md` 和 `需求设计文档.md`。
- 详细设计中文模板章节顺序保持不变。
- `.loopx/intake/YYYY-MM-DD-<slug>/` 作为 source 的读取规则不变。
- 旧设计文档不迁移、不回填 `D-*`。
- support lenses 的定位不变：辅助检查，不替代 workflow skill。
- `final-review` 不被要求在本次第一版支持完整 `D-*` 矩阵。

需要接受的兼容成本：

- 新生成或更新后的 `spec` 文档会出现 `D-*` 标记和索引表。
- `plan-to-exec` 与 `review` 文档会新增消费 `D-*` 的规则。
- 改动后的 skill 需要 bump 对应 `metadata.version`，并通过 `node scripts/verify-skills.mjs`。

## Operational And Security Impact / 运行与安全影响

运行影响很小：没有新增服务、后台任务、CLI 命令、状态文件或外部依赖。主要维护成本是 skill 文档和治理测试需要保持同步。

安全和隐私影响：不新增权限、网络、认证、数据持久化或敏感数据处理。`D-*` 只是现有设计文档中的引用标记，不改变信息暴露范围。

失败模式：

- skill 文档更新不完整，导致 `plan-to-exec` 或 `review` 忽略 `D-*`。
- governance test 只检查关键词，不能证明真实 workflow 质量；需要保留 TC-001 至 TC-005 的人工检查空间。
- 过度使用 `D-*` 可能让设计变成大 checklist；通过 “implementation-relevant only” 边界控制。

## Implementation And Transition / 实现与过渡

第一版高层落地路径：

1. 更新 `skills/spec/SKILL.md`，说明 `D-*` 适用范围、inline 位置、索引表和 not applicable 条件。
2. 更新 `skills/spec/DESIGN_SPEC_TEMPLATE.md`，在详细设计末尾加入设计决策索引位置，并保持原章节顺序。
3. 更新 `skills/plan-to-exec/SKILL.md`，要求从设计文档读取 `D-*` 并在 task/deferred/verification 中保留。
4. 更新 `skills/review/SKILL.md`，要求 Stage 1 spec compliance 检查 `AC-*` 与 `D-*` 覆盖。
5. 更新 `test/skill-governance.test.mjs` 和 `node scripts/verify-skills.mjs` 相关发布门禁。

这不是任务计划；具体文件、测试断言和 commit 切分由后续 `plan-to-exec` 决定。[D-007][D-009]
