## 二、需求信息

### 2.1 需求背景

- 背景：27 个 bundled skills 已形成完整主链，但存在合同重复、agent 拓扑失控、runtime/skill 路由不一致和外围治理不足。
- 需求目的：用一个 current-only 合同统一运行时、skills、references、测试、安装和公开文档。
- 目标用户/使用方：loopx maintainers、Codex/Claude coding agents、使用 loopx 的工程团队。
- 需求链接：本次对话的全量审计与用户批准。
- 关联原始材料：`设计提案.md`；计划 overview 中的 `AC-001`–`AC-008`、`TC-001`–`TC-008`。

### 2.2 需求范围

- 本期范围：agent topology、clarify handoff state、workflow roots、diagnosis/TDD/evidence、domain lenses、27-skill governance、公开文档和 package surface。
- 非目标：旧运行状态迁移、历史文档改写、新依赖、第三方 skills、兼容 alias。
- 决策边界：旧 artifact 可保留在磁盘但当前 runtime 不读取或转换。
- 依赖方：Node.js ESM CLI、内置 tests、canonical `skills/` 安装面。
- 约束条件：breaking current-only release；dirty worktree 中用户已有修改必须保留。
- 触发的辅助 skills：architecture-designer、cli-developer。

### 2.3 可行性分析

- 业务可行性：用户明确允许不兼容正在进行的任务。
- 技术可行性：仓库已有强治理测试、package verifier 和清晰 canonical source。
- 团队接受能力：通过分 child plan、边界提交和 final-review 控制风险。
- 时间成本：高；涉及全部 bundled skills 和部分 runtime。
- 资源成本：无新依赖。
- 替代方案：增量兼容补丁已在提案中拒绝。
- 关键风险：大范围文档合同变更可能产生遗漏或 phrase-only 测试脆弱性。

## 三、概要设计

### 3.1 方案总述

- 设计目标：单一事实源、有限 agent 拓扑、明确状态转换、可验证的全量治理。
- 总体思路：共享合同先行，消费者引用；runtime 与 skill 同步切换，不提供兼容层。
- 核心模块：shared contracts、workflow runtime、core workflow skills、support/domain lenses、governance/docs。
- 主要难点：控制跨 skill 重复、保证全量覆盖、处理部分失败。
- 技术指标：27/27 skills 有治理项；测试 0 failure；package dry-run 正确。

### 3.2 整体架构设计

- 业务模式：skill-first workflow suite。
- 系统边界：skills 是执行合同；CLI 是安装、状态、诊断与审计辅助。
- 上下游系统：Codex/Claude runtime、git、Node.js filesystem。
- 应用架构：canonical `skills/` + `src/` runtime + deterministic tests/verifier。
- 技术架构：Markdown contracts、JSON state、ESM CLI、node:test。
- 数据流转：AC/TC → D → T → evidence → review → final-review → finish。

### 3.3 核心流程设计

| 流程 | 触发条件 | 参与系统/模块 | 主流程 | 异常/补偿 | 输出 |
|---|---|---|---|---|---|
| clarify handoff | intake ready | clarify, workflow, next-skill | 持久化 decision → CLI 路由 | 非法/旧 state 拒绝 | `$spec`、`$plan-to-exec` 或无 handoff |
| agent dispatch | workflow 需要独立 worker | controller, prompt | controller spawn → leaf work → result | bounded wait、无 replacement race | 单一 worker 结果 |
| verification | task/plan/package 完成 | evidence, review, finish | 记录证据 → scope review → final gate | finding 修复后重审 | 可追踪 completion |

### 3.4 功能模块

| 模块 | 职责 | 关键功能 | 依赖 | 备注 |
|---|---|---|---|---|
| Shared contracts | 拥有跨 skill 不变量 | agent/review/evidence schema | package surface | normative references |
| Workflow runtime | 当前状态与下一步 | handoff decision、current-only rejection | src/tests | 不迁移旧状态 |
| Skill roots | 编排 | fast path、gates、reference routing | shared contracts | bounded bodies |
| Governance | 防止合同漂移 | 27-skill semantic matrix | verifier/tests | 避免纯 phrase 堆积 |

### 3.5 新增/调整功能说明

所有当前 workflow dispatch 变为 leaf worker；clarify 的设计门成为持久化状态；诊断与 evidence 使用共享 schema；domain skill 改为条件化、repository-first guidance。

### 3.6 专项设计检查

| 辅助 skill | 触发原因 | 检查内容 | 设计结论 |
|---|---|---|---|
| architecture-designer | workflow/state/ownership | 边界、故障、恢复、单一 owner | shared contract + current-only reset |
| cli-developer | next/status/错误 | human/JSON、状态枚举、退出行为 | 明确 handoff 决策和 restart diagnostic |

## 四、详细设计

### 4.1 Shared Contracts 详细设计

#### 4.1.1 需求内容

- 入口：任何 workflow skill dispatch 或 review/verification handoff。
- 操作人/调用方：顶层 controller。
- 前置条件：当前 bundled skill 被选中。
- 输出结果：唯一的 agent、review、evidence normative contract。

#### 4.1.2 方案设计

**Workflow Contract `D-001`（Source `AC-001`）：** 只有顶层 controller 能创建、等待、消息、替换、中断或释放 agent。所有 implementer、reviewer、fixer、final reviewer 都是 leaf worker。

**Workflow Contract `D-002`（Source `AC-003`）：** task/checkpoint/plan/spec review 的单位、职责、severity 和持久化结果由共享 review contract 定义，消费者不得复制另一套定义。

**Operational Contract `D-003`（Source `AC-003`, `AC-004`）：** verification evidence 至少包含 command、cwd、timestamp、exit code、scope、result、output summary、skipped checks 和 environment constraints。

#### 4.1.3 流程步骤

1. controller 读取 owning workflow 和共享合同。
2. controller 将 leaf clause 直接放入 worker-visible prompt。
3. worker 直接完成角色并返回结果，不派生 agent。
4. controller 记录 evidence 和 review state。

#### 4.1.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| wait 窗口为空 | 保持同一 worker，按需继续 meaningful wait | 无错误 | tool state |
| worker BLOCKED | controller 改上下文、模型或 scope | 明确 blocker | report |
| worker 尝试委派 | prompt 与治理合同禁止 | 任务失败/审查 finding | governance test |

#### 4.1.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| canonical `skills/` source | 安装架构不变 | verifier/package dry-run |
| task review 和 final-review 分层 | 已验证的质量门 | governance tests |

### 4.2 Runtime And Current-State 详细设计

#### 4.2.1 需求内容

- 入口：clarify state 更新、`loopx status/next`。
- 操作人/调用方：CLI 用户与 agent hook。
- 前置条件：当前 schema state。
- 输出结果：与 `handoff_decision` 一致的下一 skill。

#### 4.2.2 方案设计

**State/CLI Contract `D-004`（Source `AC-002`）：** `handoff_decision` 只允许 `needs_spec`、`direct_to_plan`、`blocked`；ready 不再隐含 direct-to-plan。

**Compatibility Contract `D-005`（Source `AC-008`）：** 缺少 current schema/decision 的旧运行状态被拒绝并提示启动新 workflow；不读时规范化、不迁移、不删除。

#### 4.2.3 流程步骤

1. clarify 将最终 decision 写入 state。
2. next-skill 验证 state 与 readiness。
3. `needs_spec` 输出 `$spec`；`direct_to_plan` 输出 `$plan-to-exec`；`blocked` 输出 null。

#### 4.2.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| 非法 decision | 拒绝 | specific error | CLI stderr/JSON error |
| old state | 不转换 | restart diagnostic | CLI output |
| human/JSON 不一致 | 测试失败 | 不发布 | node:test |

#### 4.2.5 不变行为

`loopx init/clarify/status/next` 命令名和 canonical intake path 保持不变。

### 4.3 Skill And Governance Reset 详细设计

#### 4.3.1 需求内容

- 入口：27 个 bundled skills 及 references。
- 操作人/调用方：agent runtime、maintainers。
- 前置条件：shared contracts 已建立。
- 输出结果：bounded roots、correct domain guidance、全量 semantic matrix。

#### 4.3.2 方案设计

**Workflow Contract `D-006`（Source `AC-003`）：** root `SKILL.md` 只保留 purpose/boundary/fast path/gates/output/reference routing；详细 schema 与 rubric 放在按需 references。

**Behavior Contract `D-007`（Source `AC-004`）：** `debug` 只产出 canonical diagnosis；`issue` 消费；`fix` 执行。TDD 不得要求删除用户、既有或 dirty implementation。

**Design Discipline Contract `D-008`（Source `AC-005`）：** domain lenses 的规则必须条件化、repository-first，并通过 factual-trap tests；不得用通用 cookbook 推荐覆盖现有 stack。

**Governance Contract `D-009`（Source `AC-006`, `AC-007`）：** 每个 bundled skill 恰有一个 matrix entry，至少定义 role、boundary、output、safety、integration 和 references。

#### 4.3.3 流程步骤

1. 提取共享合同。
2. 收敛核心 roots。
3. 修复 issue/support/domain contracts。
4. 建立 matrix 与 public docs。
5. 全量测试、package dry-run、spec-level final-review。

#### 4.3.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| reference 未打包 | verifier 失败 | 不发布 | verification output |
| skill 无 matrix entry | test 失败 | 不发布 | governance test |
| 历史文档含旧文本 | 允许 | 无 | strict paths 排除历史目录 |
| current docs 含旧合同 | negative assertion 失败 | 不发布 | test output |

#### 4.3.5 不变行为

bundled skill 名称、安装目标、feature/issue 两条主流程概念保持不变。

## 五、存储类设计

### 5.1 库表设计

不涉及数据库。持久化对象是本地 JSON/Markdown state、ledger、report 和 contract matrix。

### 5.2 数据迁移/初始化

- DDL/DML/回填：不涉及。
- 老数据兼容：明确不支持。
- 新老系统读写关系：current runtime 只读 current schema；旧文件不自动删除。

### 5.3 缓存设计

不涉及。

## 六、其他组件设计

消息、定时任务、分布式锁、加密和限流均不涉及。配置仍使用现有 env/config surface，不新增依赖或 feature flag。

## 七、接口设计

### 7.1 接口设计原则

本次接口是 CLI 状态、JSON 文件和 Markdown contract。字段必须稳定、可验证；错误必须说明 restart/current-contract 动作。

### 7.2 接口清单

| 接口 | 调用方 | 服务方 | 权限/认证 | 幂等 | 文档地址 | 备注 |
|---|---|---|---|---|---|---|
| `nextSkillCommand(state)` | CLI/hooks | `src/next-skill.mjs` | 本地 | 是 | `docs/loopx/cli.md` | 按 handoff decision 路由 |
| skill contract matrix | verifier/tests | bundled skills | 本地 | 是 | `docs/loopx/skills.md` | 27 项一一对应 |

### 7.3 接口明细

`handoff_decision` 枚举：`needs_spec | direct_to_plan | blocked`。非法或缺失 current value 不允许推断。

## 八、系统发布

### 8.1 灰度方案

不灰度。一次性 current-contract reset。

### 8.2 降级方案

无运行时降级或兼容 fallback。失败时停止发布并修复当前合同。

### 8.3 关联系统/功能影响

| 系统/功能 | 影响 | 依赖动作 | 负责人 | 验证方式 |
|---|---|---|---|---|
| Codex/Claude skill install | prompt/reference 更新 | 重新安装 skills | maintainer/user | doctor + package test |
| 进行中的 pre-v2 workflow | 不再支持 | 创建新 workflow | user | restart diagnostic |

### 8.4 回滚方案

代码级回滚使用 git revert 到前一发布版本；不支持把 v2 新状态转换回旧状态。发布前必须完成每 child plan review 和 package final-review。

## 九、系统监控与维护

### 9.1 监控与告警

本地产品无在线监控；通过 test、verifier、doctor、CLI diagnostics 和 final-review 观察异常。

### 9.2 性能与容量

主要指标是 prompt/reference 体积、agent turn 数和测试耗时。root skill 收敛用于降低模型注意力竞争，不设硬 token 指标。

### 9.3 可靠性与兜底

不添加 fallback。partial failure 使用 checkpoint、边界提交、reconcile 和重新 review。

## 十、排期与规划

### 10.1 任务拆分与工作量评估

由 multi-plan package 的六个 child plans 承载；不在设计文档重复任务步骤。

### 10.2 计划时间

由执行会话决定，不设置虚构日期。

### 10.3 发布计划

共享合同 → runtime → core workflow → issue/support → domain lenses → governance/docs → final-review → finish。

### 10.4 遗留问题与后续规划

无已知阻塞项。独立 plan review 可在执行开始前补做，但不是设计缺口。

### 10.5 Planning Handoff

- `plan-to-exec` 可以决定：精确文件拆分、TDD 顺序、测试组织、reference 文件边界和 child plan 内任务粒度。
- 必须返回 `spec`：需要恢复旧兼容、改变 bundled skill 名称、增加依赖或修改 agent ownership。
- 必须返回 `clarify`：改变用户已批准的破坏性范围或新增产品目标。
- 推荐下一步：执行现有 package。

```text
$exec docs/loopx/plans/2026-07-13-skill-suite-v2-reset/00-overview.md
```
