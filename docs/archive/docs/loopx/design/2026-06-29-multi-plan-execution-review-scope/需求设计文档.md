## 二、需求信息

### 2.1 需求背景

- 背景：`plan-to-exec` 已支持一个 source artifact 产出 multi-plan package，但 `subagent-exec`、`final-review` 和 `finish` 仍以单 plan 完整闭环为默认语义。
- 需求目的：支持 child plan 独立执行和独立 review，同时保证整个 spec 只在 spec-level final-review 通过后执行一次 `finish`。
- 目标用户/使用方：使用 loopx 处理大型 spec、希望并行执行多个 child plan 的 agent/user。
- 需求链接：不涉及。
- 关联原始材料：`.loopx/intake/clarify-multi-plan-execution-review-scope-2026-06-29.md`。

### 2.2 需求范围

- 本期范围：
  - 新增 `.loopx/multi-plan/<feature-slug>/state.json` 状态模型。
  - 更新 multi-plan 相关 skill contracts。
  - 在 finish runtime 增加 multi-plan 状态硬门禁。
  - 增加治理和 runtime 测试。
- 非目标：
  - 不自动执行 multi-plan 目录。
  - 不自动调度并行 child plan。
  - 不 runtime 阻塞 `final-review`。
  - 不把 mutable 状态写入 repo-tracked plan 目录。
  - 不扫描所有 `.loopx/multi-plan/*/state.json` 猜测 active package。
  - 第一版不记录 child plan base/head。
- 决策边界：
  - `subagent-exec` 的执行单位仍是单 plan 文件。
  - `finish` 的完成单位在 matching multi-plan state 存在时升级为 spec-level package。
  - `final-review` 分为 plan-level 和 spec-level 语义，但不新增 runtime CLI 命令。
- 依赖方：
  - `skills/plan-to-exec/SKILL.md`
  - `skills/subagent-exec/SKILL.md`
  - `skills/final-review/SKILL.md`
  - `skills/finish/SKILL.md`
  - `skills/RESOLVER.md`
  - `src/finish-runtime.mjs`
  - `test/workflow.test.mjs`
  - `test/skill-governance.test.mjs`
- 约束条件：
  - 单 plan workflow 必须保持不变。
  - 不新增 public CLI surface，除非实现时证明无法通过现有 finish runtime 完成。
  - 运行态状态默认不进 git。
  - 错误信息必须指出缺失的 plan/review gate。
- 触发的辅助 skills：`architecture-designer`, `cli-developer`

### 2.3 可行性分析

- 业务可行性：需求已澄清，核心决策完整。
- 技术可行性：现有 `finish-start` 已记录 `source`，可作为 multi-plan state discovery 的锚点。
- 团队接受能力：改动集中在 workflow skill contracts 和 finish runtime，符合现有架构。
- 时间成本：中等；需要 runtime helper、finish gate、skill 文档和测试。
- 资源成本：低；不引入依赖，不需要服务端。
- 替代方案：文档-only、自动执行目录、repo-tracked status、全局扫描状态均已拒绝。
- 关键风险：多个 worktree 的本地 `.loopx/multi-plan/` 状态不会自动同步。

## 三、概要设计

### 3.1 方案总述

- 设计目标：multi-plan package 可以分 plan 执行，最终完成由 spec-level gate 控制。
- 总体思路：把计划结构留在 `docs/loopx/plans/.../00-overview.md`，把执行状态放在 `.loopx/multi-plan/.../state.json`，由 `finish` runtime 在完成前校验。
- 核心模块：
  - Multi-plan state helper
  - Finish gate validator
  - Skill contract updates
  - Governance/runtime tests
- 主要难点：既要防止 premature finish，又不能破坏 child plan 独立执行和并行执行。
- 技术指标：
  - 单 plan workflow 不变。
  - Matching multi-plan state incomplete 时 `finish-record --status done` 必须失败。
  - Complete multi-plan state with spec-level `Ready for finish? Yes` 时 finish 可继续。

### 3.2 整体架构设计

- 业务模式：skill-first workflow；runtime 只提供轻量状态和完成门禁。
- 系统边界：
  - `plan-to-exec` 负责产出 plan package。
  - `subagent-exec`/`exec` 负责执行单个 child plan。
  - `final-review` 负责 plan-level 或 spec-level review。
  - `finish` 负责最终完成和 audit。
- 上下游系统：
  - 上游：source spec、plan package、child plan、final-review artifact。
  - 下游：finish audit、finish record、memory/spec extraction。
- 应用架构：
  - 新增 finish runtime 内部 helper，读取 local state。
  - 不新增外部服务或数据库。
- 技术架构：
  - Node.js ESM runtime helper。
  - JSON state stored under `.loopx/multi-plan/`.
- 数据流转：
  1. `plan-to-exec` 生成 multi-plan package。
  2. agent 初始化或维护 `.loopx/multi-plan/<feature-slug>/state.json`。
  3. child plan 执行后，plan-level final-review 更新 child status。
  4. spec-level final-review 更新 `spec_final_review`。
  5. `finish` 从 baseline source path 推导 state 并校验。

### 3.3 核心流程设计

| 流程 | 触发条件 | 参与系统/模块 | 主流程 | 异常/补偿 | 输出 |
|---|---|---|---|---|---|
| Multi-plan 初始化 | `plan-to-exec` 产出目录式 package | `plan-to-exec`, agent | 写 `00-overview.md`，建立本地 state | 未建立 state 时 finish 按普通流程，直到 matching state 出现 | plan package + state |
| Child plan 执行 | 用户/agent 执行 `01-*.md` | `subagent-exec`, `final-review` | 执行 task，plan-level final-review，更新 state | review 不通过则不标记 ready | child plan complete |
| Spec-level review | 所有 child plan ready | `final-review` | 用 spec、overview、child plans、review artifacts 做整体 review | review 为 No/With fixes 则不允许 finish | spec final-review artifact |
| Finish gate | `finish-record --status done` 或 finish 完成记录 | `finish-runtime.mjs` | 从 source path 发现 state，校验 gate | 缺失条件则抛错并提示缺口 | finish allowed/blocked |

### 3.4 功能模块

| 模块 | 职责 | 关键功能 | 依赖 | 备注 |
|---|---|---|---|---|
| Multi-plan state helper | 读写和校验本地状态 | path 推导、JSON 读取、schema 校验、gate 报告 | `node:fs/promises`, `node:path` | 可放入 `src/finish-runtime.mjs` 或独立模块 |
| Finish gate validator | 在完成记录前阻止 premature finish | 校验 child plans 和 spec final-review | finish audit state | 不影响 `pending` 记录 |
| Skill contract updates | 明确分层语义 | plan-level/spec-level final-review，finish only once | skill files | 需 bump 相关 skill metadata |
| Governance tests | 防回退 | 文档断言、runtime gate 测试 | Node test | 保持 package surface |

### 3.5 新增/调整功能说明

#### Multi-plan state

新增本地 runtime 文件：

```text
.loopx/multi-plan/<feature-slug>/state.json
```

#### Final-review 分层

- plan-level final-review：针对单个 child plan 的完成质量。
- spec-level final-review：针对整个 source spec 和所有 child plan 的最终完成质量。

#### Finish 门禁

`finish` 不负责创建 state，也不负责补齐 review；只在 matching state 存在且不满足 gate 时拒绝完成。

## 四、详细设计

### 4.1 Multi-plan 状态模型详细设计

#### 4.1.1 需求内容

- 入口：agent 或 runtime helper 读写 `.loopx/multi-plan/<feature-slug>/state.json`。
- 操作人/调用方：`subagent-exec` controller、`final-review` controller、`finish` runtime。
- 前置条件：存在 multi-plan package。
- 输出结果：可被 `finish` 校验的状态文件。

#### 4.1.2 方案设计

- 核心逻辑：
  - state 以 `<feature-slug>` 为目录名。
  - state 记录 source spec、plan package、child plans、spec final-review。
  - `finish` 只读 state，不自动补齐 state。
- 状态流转：
  - `in_progress`：至少一个 child plan 未完成。
  - `ready_for_spec_review`：所有 child plan complete 且 ready。
  - `ready_for_finish`：spec-level final-review 为 Yes。
  - `blocked`：人工或 review 标记阻塞。
- 数据变更：
  - child plan 完成后更新对应 row。
  - spec-level final-review 后更新 `spec_final_review`。
- 计算公式：
  - `ready_for_finish = all(plans[].status == "complete" && plans[].ready_for_spec_review == true && plans[].plan_final_review) && spec_final_review.ready_for_finish == "Yes"`。
- 幂等设计：
  - 重复写入同一 plan 的 complete 状态应覆盖为同一结果。
  - `finish` gate 是只读校验。
- 权限/越权控制：本地文件权限；不涉及用户身份。
- 异常处理：
  - JSON 无法解析：matching state 视为 invalid，阻止 finish。
  - 缺字段：阻止 finish 并报告字段。
- 补偿/重试：
  - 修正 state 或补齐 review 后可重试 `finish`。
- 日志与审计：
  - finish audit report 应记录 multi-plan gate 结果。

#### 4.1.3 流程步骤

1. `plan-to-exec` 产出 `docs/loopx/plans/YYYY-MM-DD-<feature-slug>/`。
2. agent 创建或更新 `.loopx/multi-plan/<feature-slug>/state.json`。
3. 每个 child plan 完成 plan-level final-review 后更新 `plans[]`。
4. spec-level final-review 后更新 `spec_final_review`。
5. `finish` 读取 state 并校验。

#### 4.1.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| 非法 JSON | 阻止 finish | 看到 state invalid 和 path | finish report 记录 |
| `plans[]` 为空 | 阻止 finish | 提示 no child plans | finish report 记录 |
| 重复 child path | 阻止 finish 或要求去重 | 提示 duplicate plan path | finish report 记录 |
| 并发写 state | 第一版不加锁；后写覆盖 | 需要重新检查状态 | 不涉及 |
| 缺 plan-level review | 阻止 finish | 提示缺 `plan_final_review` | finish report 记录 |
| 缺 spec-level review | 阻止 finish | 提示缺 `spec_final_review` | finish report 记录 |
| state 不存在 | 若 source path 未匹配或 state 缺失，普通流程；若后续实现选择 source 匹配但 state 缺失为 gate miss，则提示缺 state | 明确区分普通流程和缺 state | finish report 记录 |

#### 4.1.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| 单 plan `finish` | 兼容现有用户 | existing finish lifecycle test |
| `task-brief PLAN_FILE N` | `subagent-exec` 仍执行单文件 plan | script tests/governance |
| `.loopx/final-review/YYYY-MM-DD-<slug>.md` | 保持 review artifact 位置 | governance test |

### 4.2 Finish gate 详细设计

#### 4.2.1 需求内容

- 入口：`finishRecordStage(..., { status: "done" })`。
- 操作人/调用方：`skills/finish` 通过 `loopx finish-record ... --status done`。
- 前置条件：finish audit 已存在。
- 输出结果：允许或拒绝完成记录。

#### 4.2.2 方案设计

- 核心逻辑：
  - 从 finish audit state 的 `audit.change_window.source_artifacts` 读取 source path。
  - 若 source path 属于 `docs/loopx/plans/YYYY-MM-DD-<feature-slug>/`，推导 feature slug。
  - 读取 `.loopx/multi-plan/<feature-slug>/state.json`。
  - 若 state 存在，执行 gate。
  - gate 未通过时抛出稳定错误，例如 `finish_record_multi_plan_incomplete`。
- 状态流转：
  - gate 通过后沿用现有 `finish_record` 状态流转。
  - gate 不通过不修改 finish state。
- 数据变更：
  - 无额外写入；finish report 可在 audit 阶段记录 gate evidence，record 阶段错误不写入。
- 计算公式：同 4.1。
- 幂等设计：重复 `finish-record --status done` 在 gate 条件不变时结果相同。
- 权限/越权控制：不涉及。
- 异常处理：
  - state invalid/incomplete：拒绝 done。
  - state complete：继续现有 audit completeness 校验。
- 补偿/重试：补齐 state 或 final-review artifact 后重试。
- 日志与审计：JSON 错误应包含缺失项；human 错误由 CLI catch 现有机制输出。

#### 4.2.3 流程步骤

1. 用户/agent 调用 `finish-record --status done`。
2. runtime 读取 finish audit state。
3. runtime 执行现有 audit state 校验。
4. runtime 执行 multi-plan gate。
5. gate 通过后写 choice；失败则抛错。

#### 4.2.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| source path 是普通 `docs/plan.md` | 不启用 multi-plan gate | 单 plan 行为不变 | 不涉及 |
| source path 是 child plan 但 state 不存在 | 推荐阻止并提示 expected state path，避免误 finish | 看到 missing state | stderr/JSON error |
| source path 是 overview 但 state incomplete | 阻止 | 看到缺失 child plan/review | stderr/JSON error |
| `status` 不是 done | 不执行完成硬门禁 | pending/failed/aborted 可记录 | 不涉及 |
| spec final-review 为 With fixes | 阻止 | 提示 spec final-review not ready | stderr/JSON error |

#### 4.2.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `finish-record` action/status 枚举 | 避免破坏 CLI API | existing tests |
| audit extraction completeness gate | multi-plan gate 叠加，不替代 | finish audit lifecycle tests |

### 4.3 Skill contract 详细设计

#### 4.3.1 需求内容

- 入口：agent 调用 `plan-to-exec`、`subagent-exec`、`final-review`、`finish`。
- 操作人/调用方：Codex/Claude/Cursor agent。
- 前置条件：skills 已安装。
- 输出结果：一致的 multi-plan workflow 语义。

#### 4.3.2 方案设计

- `plan-to-exec`：
  - 说明何时拆 multi-plan。
  - `00-overview.md` 必须包含 child plan 列表、依赖、并行关系、status state path。
- `subagent-exec`：
  - 执行 child plan 后不进入 `finish`。
  - 对 child plan 执行 plan-level final-review。
  - 更新 multi-plan state。
- `final-review`：
  - 明确 plan-level 和 spec-level scope。
  - spec-level review 需覆盖 source spec、overview、所有 child plan、plan-level review artifacts。
  - spec-level review 通过后更新 state。
- `finish`：
  - matching multi-plan state 存在时，必须先满足 gate。
- `RESOLVER`/docs：
  - 说明 multi-plan package 最终通过 spec-level final-review 和一次 finish 收口。

#### 4.3.3 流程步骤

1. `plan-to-exec` 创建 multi-plan package。
2. `subagent-exec` 执行 child plan。
3. `final-review` 做 plan-level review。
4. 所有 child plan ready 后，`final-review` 做 spec-level review。
5. `finish` 收口。

#### 4.3.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| agent 忘记更新 state | finish 阻止 | 提示缺 state/review | 不涉及 |
| plan-level review 误标 ready | spec-level final-review 仍应发现跨 plan/覆盖风险 | final-review finding | 不涉及 |
| child plans 并行执行 | 本地 state 需人工合并或顺序更新 | 可能出现状态冲突 | 不涉及 |

#### 4.3.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| workflow 主链名称 | 保持 docs/API 兼容 | governance docs tests |
| support lens 机制 | 本需求只改变 workflow gate | skill governance |

## 七、接口设计

### 7.1 接口设计原则

- 不新增 public CLI 命令。
- `finish-record --status done` 的错误必须具体、可操作。
- JSON mode 如暴露错误，应稳定表达 missing gate。
- 命令签名保持兼容。

### 7.2 接口清单

| 接口 | 调用方 | 服务方 | 权限/认证 | 幂等 | 文档地址 | 备注 |
|---|---|---|---|---|---|---|
| `loopx finish-start [slug] --source <path>` | agent | CLI | 本地文件权限 | 是 | `src/cli.mjs` | 记录 source path |
| `loopx finish-record <audit-id> --action <action> --status done` | agent | CLI | 本地文件权限 | 是 | `src/cli.mjs` | 增加 multi-plan gate |
| `.loopx/multi-plan/<feature-slug>/state.json` | agent/runtime | 文件系统 | 本地文件权限 | 覆盖写 | 本设计 | 本地 runtime state |

### 7.3 接口明细

#### 7.3.1 Multi-plan state JSON

- 路径：`.loopx/multi-plan/<feature-slug>/state.json`
- 必填字段：
  - `schema_version: 1`
  - `feature_slug`
  - `plan_package`
  - `source_spec`
  - `status`
  - `plans[]`
- `plans[]` item：
  - `path`
  - `status`
  - `plan_final_review`
  - `ready_for_spec_review`
- `spec_final_review`：
  - `path`
  - `ready_for_finish`
- 错误码：
  - `finish_record_multi_plan_state_missing`
  - `finish_record_multi_plan_state_invalid`
  - `finish_record_multi_plan_incomplete`
- 业务校验：见 finish gate。
- 数据变更：由 agent/final-review 更新；finish 只读。
- 日志字段：missing plan paths、missing review paths、spec readiness value。

## 八、系统发布

### 8.1 灰度方案

- 灰度范围：本地 CLI/skill workflow，无服务端灰度。
- 灰度开关：不新增。
- 验证指标：tests passing；single-plan finish unchanged；multi-plan incomplete blocked。
- 放量节奏：随 npm package 发布。

### 8.2 降级方案

- 降级触发条件：finish gate 误阻塞。
- 降级行为：修正 state 或在后续版本调整 discovery；不提供跳过 gate 的第一版设计。
- 用户影响：multi-plan package 可能需要补齐 state。
- 恢复方式：补齐 child plan/final-review 状态后重试。

### 8.3 关联系统/功能影响

| 系统/功能 | 影响 | 依赖动作 | 负责人 | 验证方式 |
|---|---|---|---|---|
| `finish-runtime.mjs` | 新增 gate | 实现 state 读取和校验 | loopx maintainer | workflow tests |
| `subagent-exec` | child plan 不直接 finish | 更新 skill 文档 | loopx maintainer | governance tests |
| `final-review` | 增加 plan/spec scope | 更新 skill 文档 | loopx maintainer | governance tests |
| `plan-to-exec` | overview 需包含 state path 和 package status | 更新 skill 文档 | loopx maintainer | governance tests |

### 8.4 回滚方案

- 回滚条件：multi-plan gate 破坏单 plan flow 或误判大量合法 finish。
- 回滚步骤：回退 finish gate helper 和相关 skill 文档。
- 数据回滚：删除 `.loopx/multi-plan/` 本地状态即可。
- 配置回滚：不涉及。
- 风险：回滚后 multi-plan premature finish 风险恢复。

## 九、系统监控与维护

### 9.1 监控与告警

- 系统异常：JSON parse/read failure。
- 业务异常：multi-plan incomplete。
- 重试异常：state 修复后仍阻塞。
- 超时：不涉及。
- 关键接口指标：测试覆盖 gate pass/fail。
- 告警渠道：不涉及。

### 9.2 性能与容量

- TPS/吞吐：本地命令，不涉及。
- CPU/内存/磁盘 IO/网络 IO：读取一个小 JSON 文件，影响可忽略。
- 数据容量：每个 feature 一个 state JSON。
- 缓存容量：不涉及。
- 跑批耗时：不涉及。
- 是否压测：不需要。

### 9.3 可靠性与兜底

- 幂等击穿：finish gate 只读，重复执行稳定。
- 并发失效：并行 agent 写本地 state 可能覆盖；第一版通过人工协调。
- 冷热备：不涉及。
- 关键任务独立性：child plan 可独立执行，finish 统一收口。
- 字段兜底：缺字段阻止 finish。
- 老新数据兼容：没有 matching state 时单 plan flow 不变。
