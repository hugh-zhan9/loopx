# 为 plan-to-exec 引入稳定 T-* 任务锚点

Author(s): loopx maintainers
Last updated: 2026-06-30
Status: Accepted
Discussion: 不涉及
Source requirements: `.loopx/intake/2026-06-30-plan-to-exec-task-anchors/`
Support lenses: architecture-designer

## Abstract / 摘要

本提案建议在 `plan-to-exec` 生成的实施计划中引入稳定、plan-local 唯一的 `T-*` 任务锚点，并保留现有 `Task N` 可读标签，形成 `### T-001 / Task 1: Add ledger validation` 的兼容标题格式。`exec`、`subagent-exec` 和 `review` 在消费计划时保留或引用 `T-*`，让任务执行、checkpoint、subagent handoff、task report 和 review finding 能稳定对齐同一个任务。

本提案不新增 runtime state machine、CLI command、artifact validator，不迁移历史 plans，也不把 `final-review` 的完整 `AC -> D -> T -> verification` 矩阵变成第一版硬门禁。

## Background / 背景与动机

`docs/articles/harness-engineering-loopx-takeaways.md` 中已经把 `D-*` design anchors 标记为落地，但仍保留 `T-*` task ID 作为 `plan-to-exec` 的后续增强点。当前 `plan-to-exec` 已有 `AC-*`、`D-*`、`TC-*` traceability，但任务本身仍主要依赖 `Task N` 序号和标题。

现状证据：

- `skills/plan-to-exec/SKILL.md` 的任务模板是 `### Task N: [Component Name]`。
- `skills/subagent-exec/scripts/task-brief` 通过 `Task N` 从计划中抽取 task brief。
- `skills/subagent-exec/SKILL.md` 的 report、progress ledger 和 handoff 仍以 `Task N` 表达。
- `skills/review/SKILL.md` 已能按 `AC-*` / `D-*` 做 spec compliance，但没有任务锚点规则。

这导致下游可以追踪需求和设计，却缺少稳定任务锚点。当任务标题改写、计划插入任务、subagent report 和 review finding 需要交叉引用时，纯 `Task N` 表达不够稳定。

## Goals And Non-Goals / 目标与非目标

目标：

- `plan-to-exec` 生成稳定 `T-*` task anchors。
- `T-*` 与现有 `Task N` 共存，保持人类阅读和旧习惯兼容。
- `exec`、`subagent-exec`、`review` 能在进度、handoff、report、checkpoint 或 finding 中保留 `T-*`。
- 每个任务都有 `Review focus`，让 reviewer 知道该任务的审查重点。
- 单计划内 `T-*` plan-local 唯一；multi-plan 通过 child plan slug/path + `T-*` 组合引用。

非目标：

- 不新增 runtime state machine。
- 不新增 CLI command。
- 不做 artifact validator。
- 不迁移历史 plans。
- 不要求旧 `Task N` plans 立刻改写为 `T-*`。
- 不重做已落地的 `D-*` design anchor 规则。
- 不把 `final-review` full `AC -> D -> T -> verification` matrix 作为本 slice hard gate。

## Proposal / 设计方案

### 1. 任务标题采用兼容格式

`plan-to-exec` 的任务标题使用：

```markdown
### T-001 / Task 1: Add ledger validation
```

`T-001` 是稳定下游引用锚点，`Task 1` 保留现有人类阅读和脚本参数习惯。后续插入任务时追加新 `T-*` 编号，不重排已经存在的锚点。这个规则只适用于新生成或更新的计划，不迁移历史 plan。

### 2. `T-*` 的唯一性是 plan-local

单个 plan 内 `T-*` 必须唯一。multi-plan child plan 仍从 `T-001` 开始，保持 child plan 自包含。跨 child plan 引用时使用组合引用，例如：

```text
01-auth/T-001
01-auth::T-001
docs/loopx/plans/2026-06-30-feature/01-auth.md#T-001
```

设计只要求表达 child plan slug/path + plan-local `T-*`，不强制唯一分隔符，避免为 markdown 计划引入额外解析标准。

### 3. 每个任务必须有 `Review focus`

`Review focus` 是任务级 review contract。它不要求每个任务都触发完整 review，但必须说明如果审查该任务，重点检查什么。

```markdown
**Review focus:**
- Verify `T-001` preserves `AC-002` and `D-004`.
- Check no behavior outside the approved task contract is introduced.
```

对纯文档、纯测试或机械同步任务，允许：

```markdown
**Review focus:** not_applicable - docs-only wording update with no product behavior.
```

### 4. 下游消费范围限定为 exec、subagent-exec、review

`exec` 应在 checkpoint 和 review request 中保留 `T-*`。`subagent-exec` 应在 task brief、implementer prompt、task report、review prompt 和 progress ledger 中保留 `T-*`。`review` 在 spec compliance finding 或 coverage note 中可引用相关 `T-*`。

`final-review` 可以读取已有 `T-*` 作为上下文，但本提案不要求它实现完整 `AC -> D -> T -> verification` hard gate。

### 5. task-brief 兼容只服务于新 heading

如果 `scripts/task-brief` 不能识别 `### T-001 / Task 1: ...`，可以扩展其 heading 匹配规则。这个调整只是为了保持现有 handoff 能继续按 numeric task 参数抽取任务，不引入新 CLI command 或新的 workflow state。

## Boundary Scenarios / 边界场景

| Scenario | Handling |
|---|---|
| 新 plan 正常生成多个任务 | 每个任务使用 `### T-001 / Task 1: ...`，并包含 `Review focus` |
| 历史 plan 只有 `### Task 1: ...` | 不迁移；现有执行路径继续按旧格式读取 |
| 单 plan 插入新任务 | 追加新 `T-*` 编号，不重排旧锚点 |
| multi-plan child 都有 `T-001` | 合法；跨 plan 引用加 child slug/path |
| task 没有产品行为 | `Source AC` 可按既有规则写 `not_applicable`，`Review focus` 可写 `not_applicable` + 理由 |
| `task-brief` 无法识别新 heading | 作为兼容性缺口修脚本匹配，不改变命令形态 |
| reviewer 看到实现偏离计划任务 | finding 引用对应 `T-*`，并按现有 Critical/Important/Minor 或 task reviewer gate 处理 |
| final-review 需要全矩阵 | 本 slice 不处理；后续单独 clarify/spec |
| artifact validator 需求出现 | 本 slice 不处理；后续单独设计 |

## Rationale / 理由与取舍

选择兼容标题格式的原因是它同时满足稳定锚点和现有习惯。`T-*` 提供跨 report/review/checkpoint 的稳定引用，`Task N` 继续支撑人类阅读和现有 `task-brief PLAN_FILE N` 参数模型。

| Alternative | Why Not |
|---|---|
| 只把 `Task N` 视为任务 ID | 插入任务或跨文档引用时不够稳定，也不容易与 AC/D/TC 形成显式链路 |
| 直接替换为 `### T-001: ...` | 会削弱现有阅读和脚本习惯，增加无必要迁移成本 |
| package-global 唯一编号 | multi-plan child 失去自包含性，编号治理复杂度高 |
| 新增 artifact validator | 超出本 slice；当前需求只要求契约和治理测试 |
| 直接做 final-review 全矩阵 | 已明确非目标；需要单独设计最终评审输出形态 |

## Compatibility / 兼容性

本提案是增量兼容变更。

- 历史 plan 不迁移。
- 新 plan 增加 `T-*`，保留 `Task N`。
- `task-brief PLAN_FILE N` 参数不变。
- 不新增 CLI command、runtime state、config key 或 artifact。
- `D-*` design anchor 契约保持不变。

如果 `task-brief` 匹配逻辑需要更新，变更应同时支持旧 `### Task 1: ...` 和新 `### T-001 / Task 1: ...`。

## Operational And Security Impact / 运行与安全影响

无运行时部署、安全、权限、数据暴露或运维影响。本提案只改变 markdown skill contract、prompt/handoff 文档和治理测试。潜在风险是计划文档变得更结构化，因此需要保持 `T-*` 作为轻量锚点，不把任务计划变成额外 runtime 状态源。

## Implementation And Transition / 实现与过渡

高层落地顺序：

1. 先用 governance test 固定 `T-*` contract、下游消费范围和非目标。
2. 更新 `plan-to-exec` 任务结构、self-review 和示例。
3. 更新 `exec`、`subagent-exec`、`review` 对 `T-*` 的消费说明。
4. 如脚本无法识别新 heading，更新 `task-brief` 匹配和对应测试。
5. 运行 `node --test test/skill-governance.test.mjs` 和 `node scripts/verify-skills.mjs`。

这不是实施计划；具体文件和提交拆分由 `plan-to-exec` 决定。
