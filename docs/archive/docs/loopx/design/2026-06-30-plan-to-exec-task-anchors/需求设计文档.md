## 二、需求信息

### 2.1 需求背景

- 背景：`docs/articles/harness-engineering-loopx-takeaways.md` 中 `plan-to-exec` 仍有 `T-*` task ID 增强项；当前 `plan-to-exec` 已保留 `AC-*`、`D-*`、`TC-*`，但 task 本身缺少稳定锚点。
- 需求目的：让 `plan-to-exec` 输出的实施任务可以被 `exec`、`subagent-exec` 和 `review` 稳定引用，避免只依赖脆弱的 ordinal prose。
- 目标用户/使用方：loopx workflow skill 使用者、执行计划的 agent、subagent implementer/reviewer、维护 skill contract 的开发者。
- 需求链接：
  - `.loopx/intake/2026-06-30-plan-to-exec-task-anchors/requirements.md`
  - `.loopx/intake/2026-06-30-plan-to-exec-task-anchors/test-cases.md`
  - `.loopx/intake/2026-06-30-plan-to-exec-task-anchors/clarification.md`
  - [设计提案](./设计提案.md)
- 关联原始材料：
  - `docs/articles/harness-engineering-loopx-takeaways.md`
  - `skills/plan-to-exec/SKILL.md`
  - `skills/exec/SKILL.md`
  - `skills/subagent-exec/SKILL.md`
  - `skills/review/SKILL.md`
  - `skills/subagent-exec/scripts/task-brief`
  - `test/skill-governance.test.mjs`

### 2.2 需求范围

- 本期范围：
  - `plan-to-exec` 生成稳定 `T-*` task anchors。[D-001]
  - 任务 heading 使用 `### T-001 / Task 1: Add ledger validation`，保留 `Task N` 兼容性。[D-002]
  - `T-*` plan-local 唯一；multi-plan 使用 child plan slug/path + plan-local `T-*` 组合引用。[D-003]
  - 每个 task 必须包含 `Review focus`，允许 `not_applicable` + 理由。[D-004]
  - `exec`、`subagent-exec`、`review` 消费或保留 `T-*`。[D-005]
  - 必要时更新 `task-brief` heading 匹配以兼容新格式，不改变命令形态。[D-006]
  - 用 governance tests 固定契约和负向边界。[D-007]
- 非目标：
  - 不新增 runtime state machine。
  - 不新增 CLI command。
  - 不做 artifact validator。
  - 不迁移历史 plans。
  - 不要求旧 `Task N` plans 立即改写为 `T-*`。
  - 不重做已落地的 `D-*` design anchor 规则。
  - 不把 `final-review` full `AC -> D -> T -> verification` matrix 作为本 slice hard gate。
- 决策边界：
  - `plan-to-exec` 是 `T-*` 的生成者。
  - `exec`、`subagent-exec`、`review` 是本 slice 的显式消费者。
  - `final-review` 可读取 `T-*` 上下文，但不承担 hard matrix 门禁。
  - `task-brief` 只做 heading 兼容，不变成新 artifact validator。
- 依赖方：
  - `skills/plan-to-exec/SKILL.md`
  - `skills/exec/SKILL.md`
  - `skills/subagent-exec/SKILL.md`
  - `skills/review/SKILL.md`
  - `skills/subagent-exec/scripts/task-brief`
  - `test/skill-governance.test.mjs`
- 约束条件：
  - 保持现有 plan 输出路径。
  - 保持现有 `task-brief PLAN_FILE TASK_NUMBER [OUTFILE]` 用法。
  - 保持历史 plan 可读可执行。
  - 修改 bundled skill docs 时只 bump 内容或行为契约变化的 skill version。
  - 运行 `node --test test/skill-governance.test.mjs` 和 `node scripts/verify-skills.mjs`。
- 触发的辅助 skills：architecture-designer

### 2.3 可行性分析

- 业务可行性：clarify 已确认 AC-001 至 AC-007，无开放问题。
- 技术可行性：现有 plan/task/review 结构已以 markdown 为主；增加 `T-*` 是文档契约和轻量脚本兼容问题，不需要 runtime 状态。
- 团队接受能力：变更集中在 workflow skills、prompt/handoff 和治理测试，符合 loopx skill-first 维护方式。
- 时间成本：中等。需要同步四个 skill 和可能的 `task-brief` 测试。
- 资源成本：低。无新依赖和运行资源。
- 替代方案：只用 `Task N`、直接替换 `Task N`、package-global 编号、artifact validator、final-review full matrix 均在提案中拒绝。
- 关键风险：
  - `T-*` 与 `Task N` 双标识导致实现者混用。
  - `task-brief` 若不兼容新 heading，会中断 subagent handoff。
  - 下游 skill 只提到 `T-*` 但 report/review 不实际保留。

## 三、概要设计

### 3.1 方案总述

- 设计目标：用稳定 `T-*` 将需求、设计、任务、执行报告和 review finding 串起来，同时不破坏现有 `Task N` 习惯。
- 总体思路：`plan-to-exec` 任务标题写 `### T-001 / Task 1: ...`；任务内部保留 `AC-*`、`D-*`、`TC-*` traceability，并新增必填 `Review focus`；执行和审查阶段保留或引用 `T-*`。[D-001][D-002][D-004][D-005]
- 核心模块：
  - `skills/plan-to-exec/SKILL.md`
  - `skills/exec/SKILL.md`
  - `skills/subagent-exec/SKILL.md`
  - `skills/review/SKILL.md`
  - `skills/subagent-exec/scripts/task-brief`
  - `test/skill-governance.test.mjs`
- 主要难点：
  - 保持新旧 task heading 兼容。
  - 避免将 `T-*` 扩张成 runtime state 或 artifact validator。
  - 保证 multi-plan child 自包含。
- 技术指标：
  - 新 plan 的每个 task 有唯一 plan-local `T-*`。
  - 每个 task 有 `Review focus` 或 `not_applicable` rationale。
  - `exec` checkpoint、`subagent-exec` handoff/report/ledger、`review` finding 能引用 `T-*`。
  - `node --test test/skill-governance.test.mjs` 通过。
  - `node scripts/verify-skills.mjs` 通过。

### 3.2 整体架构设计

- 业务模式：`clarify/spec` 固定需求和设计，`plan-to-exec` 将其拆成带 `T-*` 的任务，`exec/subagent-exec` 按任务执行，`review` 按 `AC/D/T/TC` 的相关上下文检查。
- 系统边界：
  - `T-*` 是 markdown plan 内的稳定锚点，不是 runtime 状态。
  - `Task N` 是人类阅读和现有脚本参数兼容标签。
  - `task-brief` 可以识别新 heading，但不改变命令接口。
  - `final-review` full matrix 是后续能力，不在本设计落地。
- 上下游系统：
  - 上游：intake package 和可选 detailed design。
  - 当前：`plan-to-exec` skill 和计划文档。
  - 下游：`exec`、`subagent-exec`、`review`、后续 `final-review`。
- 应用架构：Node.js package 中的 markdown skill contracts、shell handoff helper、Node governance tests。
- 技术架构：无新增依赖、无新增 CLI surface、无新增 persisted runtime state。[D-007]
- 数据流转：

```text
requirements.md (AC-*) + test-cases.md (TC-*) + optional design spec (D-*)
  -> plan-to-exec
  -> docs/loopx/plans/... (T-* / Task N + AC/D/TC + Review focus)
  -> exec checkpoint or subagent-exec task brief/report/progress
  -> review findings / coverage notes reference T-* where relevant
```

### 3.3 核心流程设计

| 流程 | 触发条件 | 参与系统/模块 | 主流程 | 异常/补偿 | 输出 |
|---|---|---|---|---|---|
| 计划生成 | `plan-to-exec` 读取明确需求或设计 | `plan-to-exec` | 为每个 task 分配 plan-local `T-*`，写兼容 heading、traceability、Review focus | source 决策缺失时返回 clarify/spec | implementation plan |
| 单计划执行 | `exec` 执行带 `T-*` plan | `exec` | 按任务执行、checkpoint 记录 `T-*` 和 Task N | review 退回时标记对应 `T-*` in_progress/blocked | checkpoint |
| subagent 执行 | `subagent-exec` 执行带 `T-*` plan | `subagent-exec`、`task-brief` | 抽取 task brief，handoff/report/progress 保存 `T-*` | 新 heading 无法抽取时修兼容脚本 | task report / progress ledger |
| task review | 完成任务后请求 review | `review` 或 task reviewer | Stage 1 检查 AC/D/T/TC 相关覆盖，finding 引用 `T-*` | T 未覆盖时按 spec compliance gap | review result |
| multi-plan 引用 | child plans 互相依赖或总览引用 | `plan-to-exec`、`subagent-exec` | child 内 `T-*` 自包含；跨 child 用 child slug/path + T | 只写裸 T 造成歧义时补 child 前缀 | unambiguous cross-plan reference |

### 3.4 功能模块

| 模块 | 职责 | 关键功能 | 依赖 | 备注 |
|---|---|---|---|---|
| `plan-to-exec` skill | 生成计划 | `T-*` heading、Review focus、唯一性规则、multi-plan 引用规则 | requirements/spec/test-cases | T 生成源 |
| `exec` skill | 顺序执行计划 | checkpoint/review request 保留 `T-*` | plan | 不新增状态机 |
| `subagent-exec` skill | subagent 执行计划 | task brief、report、progress ledger、review prompt 保留 `T-*` | plan、task-brief | 维持 Task N 参数 |
| `review` skill | task/feature review | finding 或 coverage note 引用相关 `T-*` | plan/spec/diff | 不替代 final-review |
| `task-brief` helper | 抽取单任务上下文 | 支持旧 heading 和新 heading | markdown plan | 兼容性辅助 |
| `skill-governance.test.mjs` | 发布门禁 | 文档契约、脚本兼容、负向范围断言 | bundled skills | 不做 artifact validator |

### 3.5 新增/调整功能说明

`plan-to-exec` 新增/调整：

- Task heading 使用 `### T-001 / Task 1: Add ledger validation`。[D-001][D-002]
- `T-*` plan-local 唯一，后续插入任务追加新编号，不重排旧编号。[D-003]
- multi-plan 跨 child 引用使用 child plan slug/path + `T-*`。[D-003]
- Task structure 增加必填 `Review focus`。[D-004]
- self-review 检查 `T-*` 唯一性、AC/D/TC/T coverage 和 Review focus。

`exec` 新增/调整：

- checkpoint table、blocked escalation、review request 中优先保留 `T-*`；没有 `T-*` 的历史 plan 继续使用 Task N。[D-005]

`subagent-exec` 新增/调整：

- task brief、report file naming guidance、progress ledger、ANCHOR_CONTEXT、implementer/reviewer prompt 均保留 `T-*`。[D-005]
- `task-brief` 支持新 heading 识别，但命令参数仍是 numeric task number。[D-006]

`review` 新增/调整：

- Stage 1 spec compliance 在计划含 `T-*` 时，findings 或 coverage notes 引用相关 `T-*`。[D-005]

## 四、详细设计

### 4.1 plan-to-exec T-* 生成详细设计

#### 4.1.1 需求内容

- 入口：`$plan-to-exec docs/loopx/design/2026-06-30-plan-to-exec-task-anchors/需求设计文档.md`。
- 操作人/调用方：主 agent、`plan-to-exec` skill。
- 前置条件：需求和设计已澄清；若 source 包含 `AC-*`、`D-*`、`TC-*`，彼此无冲突。
- 输出结果：每个 implementation task 有 `T-*` task anchor、兼容 `Task N` 标识、traceability 和 `Review focus`。[D-001][D-002][D-004]

#### 4.1.2 方案设计

- 核心逻辑：
  - 在任务拆分完成后，为每个任务分配 `T-001`、`T-002` 等 plan-local anchor。
  - 任务标题使用 `### T-001 / Task 1: Add ledger validation`。
  - 每个任务继续包含 `Files`、`Interfaces`、`Traceability`、`Support lenses`。
  - 每个任务新增 `Review focus`，说明 reviewer 需要检查的契约、风险或 `not_applicable` 理由。
  - self-review 检查 `T-*` 是否唯一、是否遗漏、是否和 `Task N` 兼容。
- 状态流转：不新增 workflow state；`T-*` 是计划文档内锚点。
- 数据变更：只修改 markdown skill docs、prompt/helper 文本、可能的 shell heading 匹配、治理测试。
- 计算公式：`T-*` 从 1 开始按任务分配三位编号；新插入任务追加新编号，不重排旧编号。
- 幂等设计：同一 plan 更新时已有 `T-*` 保持稳定；删除任务时可在同一更新中删除该锚点，不复用旧编号。
- 权限/越权控制：不涉及权限。
- 异常处理：
  - 任务需要新增未批准产品/设计决策时返回 `clarify` 或 `spec`。
  - `T-*` 重复时计划未完成，必须修正后 handoff。
  - `Review focus` 缺失时计划未完成。
- 补偿/重试：修改计划文档即可；无 runtime rollback。
- 日志与审计：git diff 显示任务锚点变化。

#### 4.1.3 流程步骤

1. 读取 source requirements/design/test cases。
2. 拆分 implementation tasks。
3. 为每个 task 分配 plan-local `T-*`。
4. 写兼容 heading：`### T-001 / Task 1: ...`。
5. 写 task traceability：Source AC、Design anchors、Test cases。
6. 写 `Review focus`。
7. self-review 检查唯一性、覆盖、非目标和 heading 兼容。

#### 4.1.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| 正常新 plan | 每个 task 有唯一 `T-*` | 下游可稳定引用任务 | 无 |
| 历史 plan 无 `T-*` | 不迁移，继续按 Task N 执行 | 旧流程可用 | 无 |
| 插入新 task | 追加新 `T-*`，不重排旧编号 | 引用稳定 | 无 |
| 删除 task | 删除对应锚点，不复用编号 | git diff 可见 | 无 |
| 重复 `T-*` | plan self-review 修正 | 不进入执行 | 无 |
| 缺少 `Review focus` | plan self-review 修正 | 不进入执行 | 无 |
| task 无直接 AC/D/TC | 按既有规则写 not_applicable/deferred rationale | reviewer 看到理由 | 无 |

#### 4.1.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| plan 输出路径 | 已有 workflow contract | governance assertions |
| `Task N` 可读标签 | 兼容历史阅读和执行习惯 | task template assertion |
| `AC-*`、`D-*`、`TC-*` traceability | 已落地契约 | governance assertions |
| 不在 plan 中重新设计需求/架构 | plan-to-exec 边界 | skill text assertions |

### 4.2 exec T-* 消费详细设计

#### 4.2.1 需求内容

- 入口：`$exec docs/loopx/plans/2026-06-30-plan-to-exec-task-anchors.md` 或当前平台等价执行。
- 操作人/调用方：主 agent、`exec` skill。
- 前置条件：plan 已 approved，可能包含 `T-*`。
- 输出结果：checkpoint、review request、blocked escalation 能保留 `T-*`。[D-005]

#### 4.2.2 方案设计

- 核心逻辑：
  - 执行新 plan 时以 `T-* / Task N` 识别任务。
  - checkpoint Progress table 的 Task 列可写 `T-001 / Task 1`。
  - 触发 review 时提供 task text、changed files、test evidence，并保留 `T-*`。
  - 历史 plan 缺 `T-*` 时继续使用 Task N。
- 状态流转：沿用 checkpoint 文件，不新增状态字段要求。
- 数据变更：只更新 skill docs；不改变 checkpoint 存储路径。
- 异常处理：如果计划缺 `T-*` 但不是历史 plan，可作为 plan defect 提醒。

#### 4.2.3 流程步骤

1. 读取 plan。
2. 识别任务 heading 中的 `T-*` 和 Task N。
3. 执行任务时在 update_plan/checkpoint 中保留 `T-*`。
4. review trigger 触发时在请求上下文保留 `T-*`。
5. 完成或 blocked 时记录对应 `T-*`。

#### 4.2.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| plan 有 `T-*` | checkpoint/review request 保留 `T-*` | resume 更明确 | 无 |
| 历史 plan 无 `T-*` | 使用 Task N | 旧流程不破 | 无 |
| `T-*` 与 Task N 不一致 | 作为 plan defect 停止询问 | 明确需要修 plan | 无 |

#### 4.2.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| checkpoint 路径 | 避免 runtime 迁移 | docs assertion |
| review trigger 条件 | 非本 slice 范围 | governance negative assertion |
| final-review/finish 流程 | 非本 slice 范围 | docs assertion |

### 4.3 subagent-exec T-* 消费详细设计

#### 4.3.1 需求内容

- 入口：`$subagent-exec docs/loopx/plans/2026-06-30-plan-to-exec-task-anchors.md` 或用户在 plan-to-exec 后选择 Subagent Exec。
- 操作人/调用方：controller agent、implementer subagent、task reviewer subagent。
- 前置条件：approved plan，可能包含 `### T-001 / Task 1: ...`。
- 输出结果：task brief、prompt、report、progress ledger、review prompt 保留 `T-*`。[D-005][D-006]

#### 4.3.2 方案设计

- 核心逻辑：
  - controller 仍可调用 `scripts/task-brief PLAN_FILE N`。
  - `task-brief` 识别旧 `### Task 1: ...` 和新 `### T-001 / Task 1: ...`。
  - brief 标题可以继续 `# Task 1 Brief`，但正文包含原始 heading 中的 `T-*`。
  - progress ledger 推荐记录 `T-001 / Task 1: complete (...)`。
  - report file 可继续 `task-N-report.md`，不要求改文件名；report 内容必须保存 `T-*`。
  - implementer/reviewer prompt 的 description 和上下文使用 `T-001 / Task 1`。
- 状态流转：不新增 `.loopx/subagent-exec` state schema。
- 数据变更：可能更新 `skills/subagent-exec/scripts/task-brief` heading regex 和治理测试。
- 异常处理：
  - 新 heading 无法抽取：修脚本兼容。
  - plan 中 duplicate T：pre-flight plan review 报 plan defect。

#### 4.3.3 流程步骤

1. Pre-flight plan review 检查任务 heading 和 `T-*` 唯一性。
2. 对 Task N 调用 `task-brief`。
3. brief 输出包含原始 `T-* / Task N` heading。
4. implementer report 写 `task_anchor: T-001` 或在报告正文明确任务锚点。
5. reviewer prompt 和 progress ledger 保留 `T-*`。

#### 4.3.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| 旧 heading | 继续支持 | 无感 | 无 |
| 新 heading | `task-brief` 正确抽取 | brief 包含 T | 无 |
| report 文件名仍 task-N | 允许，内容保留 T | 文件路径兼容 | 无 |
| progress ledger 丢失 | 沿用现有 git log/commits 恢复方式 | 不因 T 改变 | 无 |
| duplicate T | pre-flight plan defect | 停止执行 | 无 |

#### 4.3.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `task-brief PLAN_FILE N` | 避免新增 CLI/命令形态 | script test |
| `task-N-report.md` 文件名 | 降低迁移成本 | docs assertion |
| review-package 流程 | 非本 slice 范围 | no diff / governance |
| final-review gate | 非本 slice 范围 | negative assertions |

### 4.4 review T-* 消费详细设计

#### 4.4.1 需求内容

- 入口：`$review HEAD~1..HEAD` 或 subagent task reviewer。
- 操作人/调用方：main agent、reviewer subagent。
- 前置条件：formal plan 或 task brief 可能包含 `T-*`。
- 输出结果：findings 或 coverage notes 引用相关 `T-*`。[D-005]

#### 4.4.2 方案设计

- 核心逻辑：
  - Stage 1 spec compliance 读取 plan/task brief 中的 `T-*`。
  - 如果 finding 是 task-scoped，引用 `T-*`。
  - 如果 coverage note 覆盖 AC/D/TC，也可带对应 `T-*`。
  - 没有 formal plan 或无 `T-*` 时 degrade 为现有 intent check 或 Task N。
- 状态流转：review 不写状态。
- 数据变更：只更新 review skill 文档和 task reviewer prompt 文本。
- 异常处理：如果 task brief 缺 T 但 plan 源要求 T，可作为 missing plan context 反馈。

#### 4.4.3 流程步骤

1. 读取 plan/task brief。
2. 抽取 task anchor：`T-001`。
3. 对比 diff 与 task requirements。
4. finding 或 coverage note 引用相关 T。
5. 继续 Stage 2 code quality。

#### 4.4.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| plan 有 T | findings 引用 T | 定位更稳定 | 无 |
| plan 无 T | 沿用 Task N/intent | 兼容旧流程 | 无 |
| finding 跨多个 tasks | 引用多个 T 或说明 cross-task | 范围清晰 | 无 |
| ad-hoc review | 不要求 T | 不阻塞 | 无 |

#### 4.4.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| Stage 1 before Stage 2 | 已有 review 契约 | existing test |
| `AC-*` / `D-*` compliance | 已有契约 | existing test |
| findings severity | 不在本 slice 重做 | docs assertion |

## 七、接口设计

### 7.1 接口设计原则

本设计不新增 runtime API 或 CLI command。唯一涉及的接口类表面是 markdown task heading 和 `task-brief` 对 heading 的解析兼容。

### 7.2 接口清单

| 接口 | 调用方 | 服务方 | 权限/认证 | 幂等 | 文档地址 | 备注 |
|---|---|---|---|---|---|---|
| plan task heading | `plan-to-exec`、`exec`、`subagent-exec`、`review` | markdown plan | 本地文件权限 | 是 | 本设计 7.3.1 | 新旧 heading 兼容 |
| `task-brief PLAN_FILE TASK_NUMBER [OUTFILE]` | `subagent-exec` controller | `skills/subagent-exec/scripts/task-brief` | 本地执行权限 | 是 | 本设计 7.3.2 | 命令形态不变 |

### 7.3 接口明细

#### 7.3.1 plan task heading contract

- 路径/方法：`docs/loopx/plans/**/*.md` 中的 markdown heading。
- 请求头：不涉及。
- 请求参数：不涉及。
- 响应参数：不涉及。
- 错误码：不涉及。
- 业务校验：
  - 新 task heading 应为 `### T-001 / Task 1: Add ledger validation`。
  - `T-*` 在单个 plan 内唯一。
  - `Task N` 与任务序号保持可读一致。
  - `Review focus` 必填。
- 数据变更：markdown plan 文本。
- 日志字段：不涉及。

#### 7.3.2 task-brief compatibility contract

- 路径/方法：`skills/subagent-exec/scripts/task-brief PLAN_FILE TASK_NUMBER [OUTFILE]`。
- 请求头：不涉及。
- 请求参数：
  - `PLAN_FILE`：plan markdown path。
  - `TASK_NUMBER`：numeric task number，保持现有参数。
  - `OUTFILE`：可选输出路径。
- 响应参数：输出生成的 brief 文件路径。
- 错误码：沿用 shell exit code。
- 业务校验：
  - 支持旧 `##/### Task N` heading。
  - 支持新 `##/### T-001 / Task N` heading。
  - 仍按 numeric `TASK_NUMBER` 抽取任务。
- 数据变更：写入 brief 文件。
- 日志字段：不涉及。

- 配置回滚：不涉及。
