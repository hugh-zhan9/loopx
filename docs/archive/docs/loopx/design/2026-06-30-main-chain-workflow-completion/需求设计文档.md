## 二、需求信息

### 2.1 需求背景

- 背景：`docs/articles/harness-engineering-loopx-takeaways.md` 已经标注了多项已完成的 Harness Engineering 吸收点，但主链路仍存在若干未完成或部分完成项。用户希望一次性完成 `clarify`、`spec`、`plan-to-exec`、`exec`、`review`、`final-review`、`finish` 的相关改造，并检查链路完整性。
- 需求目的：让主链路从需求、设计、计划、执行、评审、最终评审到 finish 的 contract 能稳定传递，不出现上下游串不起来。
- 目标用户/使用方：loopx skill 用户、维护 loopx workflow 的开发者、后续执行 `plan-to-exec` / `exec` / `subagent-exec` / `review` / `final-review` / `finish` 的 agent。
- 需求链接：`.loopx/intake/2026-06-30-main-chain-workflow-completion/`
- 关联原始材料：
  - `.loopx/intake/2026-06-30-main-chain-workflow-completion/requirements.md`
  - `.loopx/intake/2026-06-30-main-chain-workflow-completion/test-cases.md`
  - `.loopx/intake/2026-06-30-main-chain-workflow-completion/clarification.md`
  - `docs/articles/harness-engineering-loopx-takeaways.md`
  - `docs/loopx/design/2026-06-30-main-chain-workflow-completion/设计提案.md`

### 2.2 需求范围

- 本期范围：
  - 完成文章中适用于 `clarify`、`spec`、`plan-to-exec`、`exec`、`review`、`final-review`、`finish` 的剩余主链路项。
  - 把 `subagent-exec` 纳入 `plan-to-exec` 的执行证据链路。
  - 明确 `AC/TC -> D -> T -> verification -> review -> final-review -> finish` 的端到端 contract。
  - 增加必要治理测试证明新主链路 contract 完整。
  - 回标 `docs/articles/harness-engineering-loopx-takeaways.md` 中完成或部分完成的项。
- 非目标：
  - 不实现 local metrics JSONL。
  - 不实现通用 workflow artifact validator。
  - 不实现 `codebase-spec` repo specs 初始化。
  - 不新增 `acceptance-testcase-generator`。
  - 不改 `plan-to-exec` multi-plan 语义。
  - 不迁移或强兼容历史 workflow artifact。
  - 不实现 deploy/UI/ops 插件型 skill。
- 决策边界：
  - `plan-to-exec` 可决定具体文件、测试和任务拆分，但不得重新定义本设计的主链路 contract。
  - 如发现需要 CLI runtime、通用 validator、metrics 或历史 artifact 迁移，必须回到 `spec` 或 `clarify`。
  - 新 artifact 遵守新 contract；旧 artifact 不作为本期执行对象。
- 依赖方：
  - `skills/clarify/SKILL.md`
  - `skills/spec/SKILL.md`
  - `skills/plan-to-exec/SKILL.md`
  - `skills/exec/SKILL.md`
  - `skills/subagent-exec/SKILL.md`
  - `skills/review/SKILL.md`
  - `skills/final-review/SKILL.md`
  - `skills/finish/SKILL.md`
  - `test/skill-governance.test.mjs`
  - `scripts/verify-skills.mjs`
  - `docs/articles/harness-engineering-loopx-takeaways.md`
- 约束条件：
  - 不写 implementation plan。
  - 不改 runtime code。
  - 使用一个普通单 plan 执行，不使用 multi-plan package。
  - 验证目标包括 `node scripts/verify-skills.mjs` 和 `npm test`。
- 触发的辅助 skills：architecture-designer

### 2.3 可行性分析

- 业务可行性：可行。需求是 workflow skill 合约收敛，不涉及外部用户行为和数据迁移。
- 技术可行性：可行。现有 skill 已有 AC/TC、D、T、review、final-review、finish audit 的基础结构。
- 团队接受能力：中等。需要同时修改多份 skill 文档，必须控制 wording 一致性。
- 时间成本：中等。工作集中在文档和治理测试，不涉及运行时大改。
- 资源成本：低。不新增依赖，不新增服务。
- 替代方案：
  - 继续逐项拆开做：被拒绝，风险是上下游 contract 断开。
  - 引入通用 validator：被拒绝，范围过大。
  - 多 plan package：被拒绝，本次需要一个单 plan 串联主链路。
- 关键风险：
  - 治理测试只检查关键词，不能真正防止链路断开。
  - `final-review` 被误设计成通用 hard matrix gate。
  - `subagent-exec` 被遗漏，导致计划任务只进入 `exec`。

## 三、概要设计

### 3.1 方案总述

- 设计目标：把主链路 contract 固定成新 artifact 的必经路径，并补齐文章中未完成的主链路项。
- 总体思路：不新增平台能力；在现有 skill 合约上补充明确的 upstream/downstream expectation，并用治理测试锁住。
- 核心模块：
  - 需求源头：`clarify`
  - 设计契约：`spec`
  - 计划契约：`plan-to-exec`
  - 执行证据：`exec` / `subagent-exec`
  - 局部评审：`review`
  - 全局评审：`final-review`
  - 完成与沉淀：`finish`
- 主要难点：多份 skill 文档需要对同一条 chain 使用一致术语和边界。
- 技术指标：
  - `node scripts/verify-skills.mjs` 通过。
  - `npm test` 通过。
  - `skill-governance` 覆盖主链路新增 contract。

### 3.2 整体架构设计

- 业务模式：用户通过 loopx skills 逐阶段推进开发，artifact 在文件系统中持久化，后续 skill 读取前序 artifact 而不是依赖会话记忆。
- 系统边界：本期只修改 skill 合约、prompt 模板、治理测试和文章；不修改 CLI runtime 和执行状态机。
- 上下游系统：无外部系统。repo 内上游是 intake/design/plan， 下游是 execution/review/final-review/finish artifact。
- 应用架构：skill-first workflow harness。
- 技术架构：Markdown skill 文档 + Node test governance + `verify-skills` packaging verifier。
- 数据流转：

```text
.loopx/intake/<slug>/requirements.md + test-cases.md
  -> docs/loopx/design/<slug>/需求设计文档.md
  -> docs/loopx/plans/<slug>.md
  -> exec/subagent-exec task evidence
  -> review findings / coverage notes
  -> .loopx/final-review/<slug>.md
  -> .loopx/finish/<audit-id>/finish-state.json + docs/loopx/memory/spec candidates
```

### 3.3 核心流程设计

| 流程 | 触发条件 | 参与系统/模块 | 主流程 | 异常/补偿 | 输出 |
|---|---|---|---|---|---|
| 需求到设计 | intake package ready for spec | `clarify`, `spec` | 读取 AC/TC，写设计提案和详细设计，生成 `D-*` | AC/TC 冲突则回到 clarify | 设计文档 |
| 设计到计划 | 详细设计完成 | `plan-to-exec` | 保留 AC/TC/D，生成 `T-*` tasks | 缺设计决策则回到 spec | 单 plan |
| 计划到执行 | plan approved | `exec`, `subagent-exec` | 保留 T/AC/D/TC，记录 verification evidence | 证据不足则不得标完成 | task evidence |
| 执行到评审 | 任务完成 | `review` | 先 spec compliance，再 code quality，findings/coverage notes 保留 anchors | Critical/Important 回修 | review result |
| 全局评审 | 全 feature 实现完成 | `final-review` | requirements coverage、runtime/regression、Test Trust | Coverage/Test Trust 不足则 With fixes/No | final-review artifact |
| 完成沉淀 | final-review clean | `finish` | 检查 final-review，运行 finish-audit，处理 memory/spec/delta candidates | 未处理 candidates 不允许 done | finish record |

### 3.4 功能模块

| 模块 | 职责 | 关键功能 | 依赖 | 备注 |
|---|---|---|---|---|
| `clarify` | 需求源头 | 输出 AC/TC 同源 intake package | 无 | 已基本落地，本期作为链路源头校准 |
| `spec` | 设计契约 | `D-*` anchors 和分类型 contract blocks | intake package | 本期补 workflow contract 类型细化 |
| `plan-to-exec` | 执行计划 | 生成 `T-*`，绑定 AC/D/TC/verification/review focus | detailed design | 不改 multi-plan 语义 |
| `exec` | 顺序执行 | 保留 `T-*` 和验证证据 | plan | 本期补证据输出一致性 |
| `subagent-exec` | subagent 执行 | task brief、report、review package 保留 anchors | plan | 必须纳入执行链路 |
| `review` | 局部评审 | AC/D/T spec compliance 和 code quality | plan + diff | 本期校准执行证据消费 |
| `final-review` | 全局评审 | coverage matrix、runtime、regression、Test Trust | full feature diff | 本期新增独立 Test Trust |
| `finish` | 收尾沉淀 | final-review gate、finish audit、memory/spec/delta candidates | final-review artifact | 本期细化 delta labels |

### 3.5 新增/调整功能说明

本期新增或调整的是 skill contract，不是 runtime feature。

1. `spec`：补充 contract block 类型说明，尤其是 `Workflow Contract`。每个 implementation-relevant contract 继续通过 `D-*` 索引落地。[D-001]
2. `plan-to-exec`：明确计划中的 AC/D/TC/T/verification/review focus 是执行和评审的共享 contract，不只给计划阅读者看。[D-002]
3. `exec` / `subagent-exec`：统一要求任务完成证据记录 task anchor、commands、exit/result、evidence summary、remaining risk。[D-003]
4. `review`：明确消费来自执行阶段的 task evidence，并继续在 findings/coverage notes 中保留 AC/D/T。[D-004]
5. `final-review`：新增独立 `Test Trust`，对测试证据可信度给出 High/Medium/Low 和原因。[D-005]
6. `finish`：把 spec delta candidates 表达为 `ADDED` / `MODIFIED` / `REMOVED` / `RENAMED` 候选结构，同时保留 accepted/rejected candidate gate。[D-006]
7. governance tests：增加主链路 contract 测试，覆盖新 artifact chain 和 out-of-scope 边界。[D-007]
8. article status：实现完成后回标文章中相关 skill 的完成状态。[D-008]

### 3.6 专项设计检查

| 辅助 skill | 触发原因 | 检查内容 | 设计结论 |
|---|---|---|---|
| `architecture-designer` | 多个 workflow skill 的边界和下游消费关系调整 | 系统边界、迁移、失败模式、长期维护成本 | 使用新 artifact contract，不迁移旧 artifact，不引入通用 runtime 平台 |

## 四、详细设计

### 4.1 主链路 contract 详细设计

#### 4.1.1 需求内容

- 入口：`.loopx/intake/2026-06-30-main-chain-workflow-completion/`
- 操作人/调用方：`spec`、后续 `plan-to-exec`、执行和 review skills。
- 前置条件：requirements/test-cases/clarification 已完成，无开放问题。
- 输出结果：一个可由 `plan-to-exec` 消费的详细设计。

#### 4.1.2 方案设计

- 核心逻辑：将主链路定义为新 artifact contract，不要求历史 artifact 补齐字段。[D-009]
- 状态流转：`ready_for_spec -> design complete -> plan ready -> execution evidence -> review -> final-review -> finish`。
- 数据变更：无数据库变更；只涉及 Markdown artifact 和治理测试。
- 计算公式：不涉及。
- 幂等设计：重复设计或计划时，应保留既有 anchor 语义；新增任务追加 anchor，不重排旧 anchor。
- 权限/越权控制：不涉及外部权限。
- 异常处理：发现 AC/TC/D/T 缺失或冲突时，回到 owning skill，而不是下游自行发明。
- 补偿/重试：文档错误通过修改文档和测试修复；无数据补偿。
- 日志与审计：依赖 git diff、test output、finish audit。

#### 4.1.3 流程步骤

1. `clarify` 输出或更新 intake package。
2. `spec` 读取 `requirements.md` 和 `test-cases.md`，生成 `D-*`。
3. `plan-to-exec` 生成 `T-*`，绑定 AC/D/TC/verification/review focus。
4. `exec` 或 `subagent-exec` 执行任务并记录 verification evidence。
5. `review` 使用 AC/D/T 和执行证据做 spec compliance。
6. `final-review` 汇总 requirements coverage、runtime/regression 和 Test Trust。
7. `finish` 读取 final-review gate，处理 memory/spec/delta candidates。

#### 4.1.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| 正常新流程 | 按 AC/TC/D/T/evidence/review/final-review/finish 顺序传递 | 下游能看到来源和证据 | 测试通过 |
| intake 缺 `test-cases.md` | `spec` 或 `plan-to-exec` 回到 clarify | 不能继续设计或计划 | governance/test failure |
| `D-*` 缺失但存在实现相关设计 | `plan-to-exec` 回到 spec | 不允许凭空规划 | plan self-review |
| 新 plan 缺 `T-*` | 视为新 artifact contract 失败 | 不能执行 | skill-governance |
| 执行报告缺 verification evidence | 任务不能声明 verified | 需要补证据 | review finding |
| final-review 缺 Test Trust | final-review artifact 不完整 | 不应进入 finish | skill-governance |
| finish candidate 未处理 | `finish-record --status done` 不应通过 | 要接受或拒绝 candidate | finish runtime |
| 历史 artifact 缺字段 | 不迁移、不执行、不强兼容 | 不影响本期 | 无 |
| 并发修改 skill 文档 | 通过 git diff 和测试暴露冲突 | 需要人工合并 | tests |
| 权限失败 | 不涉及 | 不涉及 | 不涉及 |
| 依赖超时 | 不涉及外部依赖 | 不涉及 | test timeout |
| 回滚 | git revert | 回到旧 skill contract | test rerun |

#### 4.1.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `plan-to-exec` multi-plan 语义 | 用户明确不修改 | skill governance / grep |
| 旧 workflow artifact | 用户明确旧文件不再修改或执行 | 不加入迁移任务 |
| CLI command surface | 本期不是 runtime/CLI 改造 | `npm test` |
| install/package surface | 不新增 skill 或 scripts | `node scripts/verify-skills.mjs` |

### 4.2 `spec` contract blocks 详细设计

#### 4.2.1 需求内容

- 入口：`skills/spec/SKILL.md`
- 操作人/调用方：使用 `spec` 生成设计文档的 agent。
- 前置条件：clarify intake 或其他 source 已澄清。
- 输出结果：设计文档包含适用的 contract block 和 `D-*` index。

#### 4.2.2 方案设计

- 核心逻辑：在现有 `D-*` anchor 规则之上补充分类型 contract block 指南。[D-001]
- 状态流转：不涉及 runtime 状态。
- 数据变更：skill 文档增加说明。
- 异常处理：不适用的 contract 类型应写“不涉及”，不要制造空壳。

Contract block 类型：

| 类型 | 使用场景 | 下游要求 |
|---|---|---|
| Behavior Contract | 用户可见行为、工作流行为 | plan/review 检查行为覆盖 |
| API Contract | API/命令/函数签名 | plan/review 检查输入输出和错误 |
| Data Contract | schema、文件格式、迁移 | plan/review 检查兼容和回滚 |
| Permission Contract | 权限/鉴权 | plan/review 检查拒绝路径 |
| State Contract | 状态机、幂等、并发 | plan/review 检查非法转移 |
| CLI Contract | 命令、flags、stdout/stderr | plan/review 检查 CLI 兼容 |
| Operational Contract | 配置、发布、告警、回滚 | final-review/finish 检查运行风险 |
| Workflow Contract | skill artifact 交接 | plan/review 检查 AC/D/T/evidence 链路 |

#### 4.2.3 流程步骤

1. `spec` 判断哪些 contract types 适用。
2. `spec` 在正文相关决策处写 inline `D-*`。
3. `spec` 在最终索引中列出所有 `D-*`。
4. `plan-to-exec` 读取 `D-*` 和 contract type。

#### 4.2.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| 纯文档解释无实现决策 | `Design anchors: not applicable` | 不生成伪 D anchor | plan self-review |
| 多个 contract type 适用 | 同一 `D-*` 可概括一个决策，类型选主导类型 | 下游无需合并多个权威文件 | review |
| support lens 触发 | 结论并入统一设计，不生成第二权威 contract | 单一设计来源 | spec docs |

#### 4.2.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| 详细设计模板章节顺序 | spec skill 已要求保持 | docs review |
| inline `D-*` + index table | 已落地规则 | governance test |

### 4.3 执行证据链详细设计

#### 4.3.1 需求内容

- 入口：`docs/loopx/plans/YYYY-MM-DD-<slug>.md`
- 操作人/调用方：`exec`、`subagent-exec`、`review`。
- 前置条件：plan 已包含 `T-*`、AC/D/TC、verification、review focus。
- 输出结果：任务完成证据可供 review 和 final-review 使用。

#### 4.3.2 方案设计

- 核心逻辑：`plan-to-exec` 的 `T-*` 和 verification requirements 必须同时进入 `exec` 和 `subagent-exec`。[D-002][D-003]
- `exec` 记录 checkpoint 和 task completion evidence。
- `subagent-exec` 通过 task brief、implementer report、review package 保留 anchor context。
- `review` 消费这些证据，不只看代码 diff。[D-004]

统一证据字段：

```yaml
task_anchor: T-001
source_ac:
  - AC-001
design_anchors:
  - D-001
test_cases:
  - TC-001
commands_run:
  - node --test test/skill-governance.test.mjs
evidence_summary:
  - exit code 0
  - relevant assertions passed
remaining_risk: none
```

#### 4.3.3 流程步骤

1. `plan-to-exec` 写任务 traceability。
2. `exec` 或 `subagent-exec` 执行任务。
3. 实现报告或 checkpoint 记录统一证据字段。
4. `review` 的 Stage 1 检查证据与 AC/D/T 是否一致。

#### 4.3.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| task 无直接 AC | 标 `not_applicable` 并说明 docs-only/test-only/infrastructure | reviewer 可判断合理性 | review finding |
| verification 无法自动化 | 写 manual/deferred rationale | final-review Test Trust 降级或说明 | final-review |
| subagent report 缺 anchor | task review 不应批准 | 需要补 report 或 rerun | task reviewer |
| exec checkpoint 中断 | checkpoint 保留 task anchor 和证据 | 可恢复 | checkpoint |

#### 4.3.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `subagent-exec` fresh subagent per task | 已有设计 | skill docs |
| `exec` sequential checkpoint | 已有设计 | skill docs |

### 4.4 final-review 与 finish 详细设计

#### 4.4.1 需求内容

- 入口：完成后的 feature diff、verification evidence、per-task reviews。
- 操作人/调用方：`final-review`、`finish`。
- 前置条件：执行与任务级 review 完成。
- 输出结果：final-review artifact、finish audit、memory/spec/delta candidates。

#### 4.4.2 方案设计

- `final-review` 新增独立 `Test Trust` 小节。[D-005]
- `Test Trust` 判断测试证据可信度，不替代 requirements coverage。
- `finish` 继续读取 final-review gate，不生成 final-review。
- `finish` 的 spec delta candidates 增加分类命名。[D-006]

`Test Trust` 结构：

```text
Test Trust: High | Medium | Low
Reason:
- ACs covered by behavior tests:
- ACs covered only by smoke/manual checks:
- Weak assertions or missing negative paths:
- Runtime validation effect on trust:
- Required follow-up, if any:
```

`Spec Delta Candidates` 结构：

```text
Spec Delta Candidates
- ADDED:
  - <new durable rule>
- MODIFIED:
  - <changed durable rule>
- REMOVED:
  - <removed durable rule>
- RENAMED:
  - <renamed term or artifact>
```

#### 4.4.3 流程步骤

1. `final-review` 建 coverage matrix。
2. `final-review` 做 support lens scan、runtime validation、regression checklist。
3. `final-review` 写 `Test Trust`。
4. `finish` 读取 final-review readiness。
5. `finish-audit` 生成或检查 extraction candidates。
6. `finish` 接受/拒绝 candidates，并在 summary 报告 memory/spec/delta changes。

#### 4.4.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| tests 全 pass 但断言弱 | Test Trust Medium/Low | 不能把测试视作充分证明 | final-review finding |
| runtime validation 不可执行 | 明确原因，提高测试质量审查 | Ready 可能仍为 Yes/With fixes | final-review |
| final-review `Ready for finish? No` | finish 停止并路由 fix-review | 不允许完成 | finish gate |
| delta candidate 未分类 | finish summary 不完整 | 需要补分类 | governance test |
| 没有 durable learning | 记录具体 no_candidates_reason | summary 显示 none | finish audit |

#### 4.4.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `finish` 不生成 final-review | 防止职责重复 | skill governance |
| `finish` candidates 不自动写入 specs | 保持人工确认 | finish docs |

### 4.5 治理测试与文章回标详细设计

#### 4.5.1 需求内容

- 入口：skill docs 和文章。
- 操作人/调用方：maintainer、CI、`verify-skills`。
- 前置条件：skill docs 已更新。
- 输出结果：治理测试通过，文章完成状态准确。

#### 4.5.2 方案设计

- 在 `test/skill-governance.test.mjs` 增加覆盖主链路 contract 的测试。[D-007]
- 保持 `scripts/verify-skills.mjs` 负责 bundled skill metadata、package surface 和 markdown structure。
- 不新增通用 artifact validator。
- 更新 `docs/articles/harness-engineering-loopx-takeaways.md`，只回标本期完成项。[D-008]

治理测试应覆盖：

- `spec` 包含 contract block 类型和 `Workflow Contract`。
- `plan-to-exec` 要求 verification/review focus 进入执行证据。
- `exec` 和 `subagent-exec` 都保留 task anchor 与 verification evidence。
- `review` 消费 AC/D/T 和执行证据。
- `final-review` 包含 `Test Trust`。
- `finish` 包含 `ADDED/MODIFIED/REMOVED/RENAMED` delta candidate 结构。
- active docs 不引入 local metrics 或 generic artifact validator 作为本期主链路完成条件。

#### 4.5.3 流程步骤

1. 更新 skill docs。
2. 更新 prompt/template，如 final-review report template 需要显示 Test Trust。
3. 增加或调整治理测试。
4. 运行 `node scripts/verify-skills.mjs`。
5. 运行 `npm test`。
6. 回标文章状态。

#### 4.5.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| 测试只匹配关键词 | 应尽量检查上下游组合语义 | 降低假阳性 | review |
| 文章项只部分完成 | 标“部分完成”，不要删除线误导 | 后续 roadmap 清晰 | docs review |
| verify-skills 失败 | 修复 skill metadata/markdown/package | 不进入完成 | command output |

#### 4.5.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `verify-skills` 不是 artifact validator | 用户已排除通用 validator | 不新增脚本职责 |
| 文章仍是 roadmap 文档 | 只回标状态，不改为规范源 | docs diff |
