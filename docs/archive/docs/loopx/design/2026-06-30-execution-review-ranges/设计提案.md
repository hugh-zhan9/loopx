# 用 start-anchored execution range 重构 final-review 与 finish 的范围契约

Author(s): loopx maintainers
Last updated: 2026-06-30
Status: Draft
Discussion: 不涉及
Source requirements: `.loopx/intake/2026-06-30-execution-review-ranges/`
Support lenses: `architecture-designer`, `cli-developer`

## Abstract / 摘要

我们把 loopx 的执行范围语义从“review 前必须冻结 end commit”改为“记录 requirement start commit，final-review 审查当前代码状态，finish 记录最终完整 committed evidence”。同时新增独立的 execution range state，保留现有 `finish-start` baseline 语义不变；将 final-review 报告收敛为“同一个设计方案只有一个 canonical report”，并把 multi-plan child review 从“必须落报告”改为“只保留最小通过状态”。

## Background / 背景与动机

当前行为有四个稳定缺口：

1. `finish-start` 只记录 baseline start commit，`finish-audit` 通过 `baseline..HEAD` 推导变更窗口，无法表达“这个 requirement 的独立执行范围状态”。证据见 [src/finish-runtime.mjs](/Users/zhangyukun/project/loopx/src/finish-runtime.mjs:1242) 和 [src/finish-runtime.mjs](/Users/zhangyukun/project/loopx/src/finish-runtime.mjs:628)。
2. multi-plan state 目前强制每个 child plan 都有 `plan_final_review` artifact path，finish gate 也依赖它；这和用户明确确认的“child plan 只需要 final-review 过程，不需要落文档”冲突。证据见 [src/finish-runtime.mjs](/Users/zhangyukun/project/loopx/src/finish-runtime.mjs:740) 附近和 [skills/subagent-exec/SKILL.md](/Users/zhangyukun/project/loopx/skills/subagent-exec/SKILL.md:33)。
3. `final-review` 目前要求 concrete git range，但没有 canonical report identity 规则，也没有要求复审迭代同一份 report；现有 `.loopx/final-review/` 目录里已经出现 `*-re-review.md` 形态。
4. 中文 final-review 模板保留了过多英文人类可读标签，且 requirements coverage gap 虽然在技能正文里被定义为 Critical/Important，但模板没有强制把它们提升到 findings 和 blocking issues，导致 `fix-review` 容易漏掉未实现部分。证据见 [skills/final-review/SKILL.md](/Users/zhangyukun/project/loopx/skills/final-review/SKILL.md:77), [skills/final-review/references/report-template.zh-CN.md](/Users/zhangyukun/project/loopx/skills/final-review/references/report-template.zh-CN.md:1), [skills/final-review/final-reviewer.md](/Users/zhangyukun/project/loopx/skills/final-review/final-reviewer.md:156)。

用户明确给出的约束是：

- `final-review` 和 `finish` 都要记录该需求涉及的起始 commit。
- 不强制 `final-review` 前记录 end commit。
- `fix-review` 后可能仍有 tracked uncommitted changes，所以 review 不能依赖“先 commit 再 review”的强假设。
- untracked files 视为 clean。
- 同一个设计方案只有一个 final-review report。
- partial requirement 也是阻塞项，只是 severity 降为 Important。

## Goals And Non-Goals / 目标与非目标

目标：

- 为 single-plan 和 multi-plan 都建立统一的 requirement-level execution range 起点语义。
- 让 final-review 和 finish 对“同一个需求”有稳定、可追溯的范围标识。
- 让 multi-plan child review 保留过程门禁，但不产生额外 review artifact 噪音。
- 让 final-review 报告适合 `fix-review` 消费，missing/partial 都能直接变成阻塞问题。
- 保持现有 `finish-start` / `finish-audit` 学习提取链路兼容。

非目标：

- 不改变 `subagent-exec` 的 subagent 启动能力或执行模型。
- 不引入 `execution-end` 一类冻结式命令。
- 不把 child plan review 变成 report-first workflow。
- 不让 final-review 变成纯 runtime parser gate。
- 不改变 direct-to-plan / legacy flows 的高层主链，只在需要时提供 fallback。

## Proposal / 设计方案

### 1. 新增 dedicated execution range state，保留 finish baseline 不变

我们新增 `.loopx/execution-ranges/<slug>.json` 作为 requirement-level runtime state。它只负责 requirement start identity 和 canonical review identity，不替代 finish baseline。[D-001]

建议状态字段：

```json
{
  "schema_version": 1,
  "slug": "2026-06-30-execution-review-ranges",
  "started_at": "2026-06-30T12:00:00Z",
  "worktree": "/abs/path",
  "branch": "feature-branch",
  "start_commit": "<40-char-sha>",
  "start_commit_short": "<7-char-sha>",
  "source_artifact": "docs/loopx/plans/2026-06-30-execution-review-ranges.md",
  "design_artifact": "docs/loopx/design/2026-06-30-execution-review-ranges/需求设计文档.md",
  "scope_kind": "single-plan | multi-plan-package",
  "canonical_final_review_report": ".loopx/final-review/2026-06-30-execution-review-ranges.md"
}
```

`finish-start` 继续写 `.loopx/finish/baselines/`，用于 `finish-audit` 的 committed change window 和 learning extraction。二者各司其职，避免 baseline 语义被污染。

### 2. 新增 `loopx execution-start`，不新增 `execution-end`

新增 CLI 命令：

```text
loopx execution-start <slug> --source <path> [--design <path>] [--json]
```

它的职责只有：

- 解析/记录 requirement start commit。
- 解析 source artifact 与 design artifact。
- 生成 canonical final-review report path。
- 以 idempotent 方式复用已有 state。

它不负责记录 end commit，也不负责写 final-review / finish 结果。[D-002]

`exec` 与 `subagent-exec` 在开工前同时调用：

1. `loopx execution-start ...`
2. `loopx finish-start ...`

这样新旧链路兼容：execution range 解决 requirement identity；finish baseline 解决 committed audit。

### 3. final-review 改为 start-anchored current-state model

`final-review` 的 required scope 改成：

- `start_commit`
- review 时的 current `HEAD`
- 如果存在 tracked uncommitted changes，则附带 `git diff` 与 `git diff --cached`

它不要求 stable end commit，也不把 report 视为 frozen end state。[D-003]

report 内只记录 lightweight scope metadata：

- `start_commit`
- `review_head`
- `tracked_diff_included: yes|no`
- `diff commands used`

它足够给人审计，但不引入重型 fingerprint 合约。

### 4. final-review report 的 identity 以设计方案为准

如果存在 `design_artifact`，canonical report path 固定为：

```text
.loopx/final-review/<design-date>-<design-slug>.md
```

同一个设计方案的复审必须更新同一个 report，而不是生成 `re-review` sibling 文件。[D-004]

为保留历史可审计性，report 内新增 `复审记录 / Review Iterations` 小节，记录每轮：

- reviewed_at
- reviewed_head
- previous verdict
- current verdict
- fixed findings summary

如果是 legacy/direct-to-plan 且没有 design artifact，则 fallback 到 source artifact slug 生成 canonical path，保持旧流程可用。

### 5. multi-plan child final-review 只保留过程状态，不落 report

child plan 仍然必须经过 plan-level `final-review`，但不生成 `.loopx/final-review/*.md`。它只更新 `.loopx/multi-plan/<feature-slug>/state.json` 中的最小状态：[D-005][D-009]

```json
{
  "path": "docs/loopx/plans/2026-06-30-feature/01-core.md",
  "status": "complete",
  "plan_review": {
    "status": "passed",
    "reviewed_at": "2026-06-30T12:00:00Z",
    "summary": "No blocking issues"
  },
  "ready_for_spec_review": true
}
```

明确不记录：

- child plan start commit
- child plan current `HEAD`
- child plan end commit
- child plan report path

spec-level final-review 才写 canonical report，finish 也只认这个 report。

### 6. final-review coverage gaps 必须提升为 findings 和 blocking issues

report 模板与 reviewer prompt 要求：

- `missing` requirement -> `Critical`
- `partial` requirement -> `Important`
- 二者都必须同步出现在 findings 与 blocking issues 中
- `Ready for finish?` 不能在存在任何 coverage gap 时为 `Yes`

这使 `fix-review` 可以直接消费 actionable findings，而不是再去读 coverage matrix 做二次推断。[D-006]

### 7. 中文报告只保留机器 gate token 英文

中文模板仅保留这些 exact token：

- `Ready for finish?`
- `Yes`
- `No`
- `With fixes`

其余人类可读标签全部本地化，例如：

- `Blocking issues` -> `阻塞问题`
- `Coverage` -> `覆盖情况`
- `Runtime` -> `运行时验证`
- `Regression` -> `回归评估`
- `Critical / Important / Minor` -> `严重 / 重要 / 次要`

这样既保留下游门禁稳定 token，又避免中英文夹杂体验。[D-007]

### 8. finish 记录最终完整 committed evidence，并更新 multi-plan gate

`finish` 不再以“reviewed end commit 等于 HEAD”为前提，而是：

- 从 execution range state 取 `start_commit`
- 从 git 当前状态取 final `HEAD`
- 记录 commit list、changed files、relevant tracked status
- 在 `done` 之前确保 tracked changes 已提交

同时 multi-plan gate 改为检查：

- `plans[]` 非空
- 每个 child `status: complete`
- 每个 child `plan_review.status: passed`
- 每个 child `ready_for_spec_review: true`
- `spec_final_review.path` 存在
- `spec_final_review.ready_for_finish === "Yes"`

不再检查 `plan_final_review` path。[D-008][D-009]

## Boundary Scenarios / 边界场景

- missing / invalid `execution-ranges/<slug>.json`：
  - 处理：legacy flow fallback 到 finish baseline；如果当前流程明确要求 execution state，则报错并提示 `execution-start`。
- same slug, different design artifact：
  - 处理：`execution-start` 拒绝覆盖并返回 conflict error。
- tracked staged/unstaged changes 存在：
  - 处理：允许 `final-review`，但必须附 `git diff` 和 `git diff --cached`；`finish` 前必须提交。
- 只有 untracked files：
  - 处理：视为 clean，不阻塞 review/finish。
- child plan 通过 plan-level review，但 spec-level final-review 未完成：
  - 处理：允许继续 sibling execution，不允许 `finish`。
- repeated final-review for same design:
  - 处理：更新同一 canonical report，并追加复审记录。
- direct-to-plan / no design artifact:
  - 处理：report identity fallback 到 source artifact slug。
- rollback:
  - 处理：删除 execution state、新 report sections 和 schema 变更可通过 code revert 回滚；finish baseline 兼容不受影响。
- unchanged behavior:
  - 保留 `finish-start` / `finish-audit` 现有 committed range 学习提取逻辑。
  - 保留 single-plan 没有 multi-plan state 时的 finish 行为。

## Rationale / 理由与取舍

选择的方向是“start-anchored + final committed evidence”，因为它最符合当前 `final-review -> fix-review -> final-review` 的实际循环。

被拒绝方案：

| Alternative | Why Not |
|---|---|
| 强制 `execution_end_commit`，finish 校验 reviewed end == current HEAD | 会强迫 `fix-review` 或每轮 review 后 commit，流程太硬，和用户实际工作流冲突 |
| 仅扩展 `finish-start` baseline，不新增 execution state | baseline 会从 immutable start record 变成 workflow state，职责混杂 |
| child plan 继续各自落 final-review report | token 成本高、审阅噪音大，且与“同一个设计方案一个 report”相冲突 |
| final-review 记录 workspace fingerprint | 代价高，且用户明确不希望把 final-review 设计成冻结点 |
| 所有 `partial` 仅保留在 coverage matrix，不进入 findings | `fix-review` 无法直接消费，需求缺失会漏修 |

## Compatibility / 兼容性

这是兼容优先的增量变更。

- 对现有 `finish-start` / `finish-audit`：
  - 保持命令与 state 格式不变。
- 对 single-plan workflow：
  - 新增 `execution-start`，但 `finish` 在 execution state 缺失时可 fallback 到 baseline/source artifact。
- 对 multi-plan state：
  - schema 从 `1` 升到 `2`。
  - `plan_final_review` 被 `plan_review` 替代。
- 对 final-review report：
  - path 仍位于 `.loopx/final-review/`，但 identity 从“每次 review 运行”改成“每个设计方案/源需求一个 canonical 文件”。
- 对 direct-to-plan / legacy clarify bundle：
  - 在缺 design artifact 时 fallback 到 source artifact identity。

## Operational And Security Impact / 运行与安全影响

- 运行影响：
  - 新增一个本地 runtime state 目录 `.loopx/execution-ranges/`。
  - finish/final-review 需要额外读取该状态。
- 可观测性：
  - finish report 和 final-review report 都增加 requirement start commit 与 scope metadata。
- 失败模式：
  - schema 冲突或 state 缺失时，finish/final-review 必须给出明确路径与字段错误。
- 安全性：
  - 无新权限边界；全部状态是本地文件。

## Implementation And Transition / 实现与过渡

高层落地顺序：

1. 新增 execution range runtime state 与 `execution-start` CLI。
2. 更新 `exec` / `subagent-exec` 在开工前调用 `execution-start`。
3. 更新 `final-review` skill、reviewer prompt、report templates。
4. 更新 `finish` skill 与 `src/finish-runtime.mjs` multi-plan gate 和 final evidence rendering。
5. 更新 `plan-to-exec` / `subagent-exec` multi-plan state examples。
6. 更新 workflow/runtime/governance tests。
