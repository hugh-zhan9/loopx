## 二、需求信息

### 2.1 需求背景

- 背景：当前 loopx workflow 已有 `finish-start` baseline 与 `finish-audit` change window，但它服务的是 committed diff 学习提取，不是 requirement-level execution identity。与此同时，multi-plan child review、final-review report identity、coverage gap 可修复性、中文模板本地化等语义已经和真实使用习惯偏离。
- 需求目的：建立统一的 requirement-level start-anchored execution range 语义，让 final-review 和 finish 的范围、报告、multi-plan gate 和 review/fix-review 循环协同一致。
- 目标用户/使用方：
  - loopx workflow 技能维护者
  - 使用 `exec` / `subagent-exec` / `final-review` / `finish` 的 agent
  - 依赖 `.loopx/final-review/`、`.loopx/multi-plan/` 和 `.loopx/finish/` 本地状态的维护者

### 2.2 需求范围

- 本期范围：
  - 新增 requirement-level execution range state 和 `execution-start` 命令。[D-001][D-002]
  - 让 `exec` / `subagent-exec` 在开工前初始化 execution range state，同时保留 `finish-start` baseline。[D-002][D-010]
  - 将 `final-review` 改为 start-anchored current-state model，并在报告内记录 lightweight scope metadata。[D-003]
  - 将 final-review report identity 改为“同一个设计方案一个 canonical report”，复审时迭代更新同一文件。[D-004]
  - 让 multi-plan child plan final-review 仅记录最小通过状态，不落 report artifact。[D-005][D-009]
  - 将 requirements coverage 的 missing/partial 强制提升到 findings 和 blocking issues。[D-006]
  - 本地化中文 final-review 模板，只保留 `Ready for finish?` / `Yes|No|With fixes` 机器 token。[D-007]
  - 更新 finish report 和 multi-plan gate，记录最终完整 committed evidence，并把 child review gate 从 `plan_final_review` 改为 `plan_review.status`。[D-008][D-009]
  - 更新 runtime tests、skill governance tests 和相关 skill contracts。[D-011]
- 非目标：
  - 不改变 `subagent-exec` 的 subagent 能力发现或启动机制。
  - 不新增 `execution-end` 或其他冻结式命令。
  - 不把 child plan final-review 改成 report-first。
  - 不把 final-review 的轻量 scope metadata 变成强 fingerprint。
  - 不迁移历史 `.loopx/final-review/` artifact。
- 决策边界：
  - requirement-level execution range state 只负责 start identity，不负责 final evidence。
  - finish baseline 继续服务 committed audit，不替代 execution range state。
  - child plan state 只记录 plan-level review pass status，不记录 commit metadata。
  - spec-level final-review report 是 multi-plan package 唯一持久 review artifact。

### 2.3 可行性分析

- 业务可行性：requirements、non-goals、boundary 和 blocking semantics 已经在 intake 中全部确认，AC/TC 无冲突。
- 技术可行性：仓库已具备 `finish-start` baseline、multi-plan local state 和 final-review artifact 基础；新增 execution range state 与 report identity 规则属于增量重构。
- 团队接受能力：主要改动集中在 markdown skill contract、runtime helper 和 Node tests，符合现有维护方式。
- 时间成本：中等偏高。需要同时改 runtime schema、CLI、skill docs、模板和测试。
- 资源成本：低。无新依赖、无服务端、无数据库。
- 替代方案：
  - 继续使用 end-commit freeze model：已拒绝。
  - baseline 扩展为 execution state：已拒绝。
  - child plan 继续落 report：已拒绝。
  - 只修模板不改 runtime/state：不足以解决 finish gate 与 review identity。
- 关键风险：
  - legacy / direct-to-plan source 无 design artifact 时 canonical report key 推导出错。
  - tracked uncommitted diff 纳入 final-review 后，report 与 finish 的人工理解成本上升。
  - multi-plan state schema 升级需要兼容旧 state 文件。

## 三、概要设计

### 3.1 方案总述

- 设计目标：让 loopx 对“这个需求从哪里开始、review 看到了什么、finish 最终完成了什么”有一致且轻量的契约表达。
- 总体思路：
  - 以 `execution-start` 写 requirement-level start identity。[D-001][D-002]
  - 以 final-review report 记录 scope metadata、coverage findings 和 canonical verdict。[D-003][D-004][D-006][D-007]
  - 以 finish report 记录最终 committed evidence，并用 multi-plan state gate 控制 package completion。[D-008][D-009]
- 核心模块：
  - execution range runtime state helper
  - `execution-start` CLI surface
  - final-review canonical report and template contract
  - finish multi-plan gate / final evidence rendering
  - multi-plan state schema v2
  - governance/runtime tests
- 主要难点：
  - 同时兼容旧 baseline 链路和新的 execution identity。
  - 不新增 child review report 的前提下，仍要让 spec-level final-review 和 finish 明确知道 child 已通过 plan-level gate。
  - 在允许 tracked uncommitted review 的同时，避免 finish 漏掉未提交 tracked changes。
- 技术指标：
  - `execution-start` 重复调用同一 slug/source 时幂等返回已有 state。
  - final-review report 对同一 design/source 复用同一路径。
  - finish report 明确写出 requirement `start_commit` 和 final `HEAD`。
  - multi-plan child gate 不再依赖 `plan_final_review` path。
  - `TC-1` 至 `TC-15` 均能在设计层面得到映射。

### 3.2 整体架构设计

- 业务模式：
  - source requirement / design -> execution-start -> implementation -> final-review (可多轮) -> finish
  - multi-plan child 只做 plan-level review process；spec-level final-review 和 finish 属于 package/design 级。
- 系统边界：
  - `execution-range` state：记录 requirement start identity 与 canonical report key。
  - `finish baseline`：记录 committed audit baseline。
  - `final-review` report：记录设计方案级 review 结论和轻量 scope metadata。
  - `finish` report：记录最终 committed evidence 和 choice outcome。
- 上下游系统：
  - 上游：`clarify` intake、`spec` / `plan-to-exec` source 头信息。
  - 当前：`exec` / `subagent-exec` / `final-review` / `finish`。
  - 下游：`fix-review`、memory/spec extraction、人工审阅。
- 应用架构：
  - `src/finish-runtime.mjs` 内新增 execution range helpers，或抽为同域 helper 模块。
  - `src/cli.mjs` 暴露 `execution-start`。
  - skills / templates / tests 同步更新。
- 技术架构：
  - Node.js ESM + JSON local state。
  - markdown skill contract + report template。
  - Node built-in test governance。
- 数据流转：

```text
source design or source plan
  -> loopx execution-start
  -> .loopx/execution-ranges/<slug>.json

implementation / review loop
  -> loopx:final-review
  -> .loopx/final-review/<design-date>-<slug>.md   (single/spec-level only)

finish
  -> loopx finish-start
  -> .loopx/finish/baselines/<slug>.json
  -> loopx finish-audit / finish-record
  -> .loopx/finish/<audit-id>/*
```

### 3.3 核心流程设计

| 流程 | 触发条件 | 参与系统/模块 | 主流程 | 异常/补偿 | 输出 |
|---|---|---|---|---|---|
| execution identity 初始化 | `exec` / `subagent-exec` 开始执行 | `src/cli.mjs`, execution range helper | `execution-start` 记录 start commit 与 canonical report key | slug/source 冲突则报错 | execution state |
| single-plan final-review | 全部 task 完成、进入最终评审 | `skills/final-review`, report template | 读取 start commit + current HEAD + tracked diff inputs，更新 canonical report | coverage gap / runtime risk 则报告 `No` / `With fixes` | single final-review report |
| multi-plan child review | child plan task review 全部 clean | `skills/subagent-exec`, `skills/final-review` | 执行 plan-level review 过程，只回写 `.loopx/multi-plan/<slug>/state.json` | review 不 clean 则不置 ready | child `plan_review.status` |
| multi-plan spec-level final-review | 所有 child ready | `skills/final-review` | 写 package/design 级 canonical report | `ready_for_finish != Yes` 则 finish 不可进入 | spec-level report |
| finish 完成 | user/agent 选择完成路径 | `skills/finish`, `src/finish-runtime.mjs` | 校验 multi-plan gate、确保 tracked changes 已 commit、写 final committed evidence | state 缺失/invalid/incomplete 则拒绝 done | finish report / choice record |

### 3.5 新增/调整功能说明

#### 3.5.1 新增 execution-start

新增命令：

```text
loopx execution-start <slug> --source <path> [--design <path>] [--json]
```

职责：

- 记录 `start_commit`。
- 记录 `source_artifact` 与 `design_artifact`。
- 生成 canonical report path。
- 幂等返回已有 state。

边界：

- 不记录 end commit。
- 不写 final-review 或 finish 结果。
- 不替代 `finish-start`。

#### 3.5.2 调整 final-review report 语义

- single-plan / spec-level final-review 才写 report。
- report path 由 design/source identity 决定，复审更新同一文件。
- 报告新增 lightweight scope metadata 和 `复审记录 / Review Iterations`。
- Chinese template 只保留 `Ready for finish?` / `Yes|No|With fixes` 英文 token。

#### 3.5.3 调整 multi-plan state

child row 从：

```json
{
  "plan_final_review": ".loopx/final-review/..."
}
```

迁移为：

```json
{
  "plan_review": {
    "status": "passed",
    "reviewed_at": "...",
    "summary": "..."
  }
}
```

不记录 child commit metadata。

#### 3.5.4 调整 finish gate 与 finish report

- finish gate 改查 `plan_review.status === "passed"`。
- finish report 显式记录 requirement `start_commit`、final `HEAD`、commit list、changed files、tracked status summary。
- tracked changes 若存在，必须在 `done` 前被 commit 进 final `HEAD`。

### 3.6 专项设计检查

| 辅助 skill | 触发原因 | 检查内容 | 设计结论 |
|---|---|---|---|
| `architecture-designer` | workflow state ownership、report identity、multi-plan gate | 边界、兼容、失败模式、迁移、回滚 | 选择“execution state + baseline 并存”的最小扰动方案；state 升级仅限 `.loopx/` 本地文件 |

## 四、详细设计

### 4.1 execution range state 详细设计

#### 4.1.1 需求内容

- 入口：`loopx execution-start <slug> --source <path> [--design <path>]`
- 操作人/调用方：`exec`、`subagent-exec`、手动 workflow controller
- 前置条件：当前目录处于有效 git worktree，且 `HEAD` 可解析
- 输出结果：`.loopx/execution-ranges/<slug>.json` 被创建或幂等复用。[D-001][D-002]

#### 4.1.2 方案设计

- 核心逻辑：
  - 规范化 `slug`。
  - 解析当前 `HEAD` 为 `start_commit`。
  - 记录 `source_artifact`。
  - 若未显式传入 `--design`，尝试从 plan header `Source:` 或 multi-plan `00-overview.md` / state 中解析 design/source requirement。
  - 根据 design/source identity 计算 canonical final-review report path。[D-001][D-002]
- 状态流转：
  - `created`：首次建立 state。
  - `reused`：重复调用同一 slug/source/design，直接返回现有 state。
  - `conflict`：同一 slug 指向不同 source/design 或不同 worktree boundary，拒绝覆盖。
- 数据变更：
  - 新增 `.loopx/execution-ranges/<slug>.json`。
  - 不修改 `.loopx/finish/baselines/`。
- 计算公式：
  - `canonical_report_slug = <design-date>-<design-slug>`；若无 design，则 fallback `<source-slug>`。
- 幂等设计：
  - same slug + same source/design + same worktree -> 返回原 state。
  - same slug + different source/design -> 抛 `execution_start_slug_conflict`。
- 权限/越权控制：仅本地文件；无额外权限。
- 异常处理：
  - 无有效 `HEAD` -> `execution_start_no_valid_head`
  - 无法解析 source/design -> 允许使用 fallback source identity，但在 human output 说明。
  - state invalid JSON -> `execution_start_invalid_state`
- 补偿/重试：
  - 删除冲突 state 或显式更换 slug 后重试。
- 日志与审计：
  - JSON 模式输出完整 state。
  - human 模式输出 `slug/path/start/source/design` 简要信息。

#### 4.1.3 流程步骤

1. `exec` / `subagent-exec` 在开工前读取 plan/source。
2. 调用 `loopx execution-start ...`。
3. helper 校验 git worktree 与 `HEAD`。
4. helper 解析 source/design identity。
5. helper 创建或复用 state。
6. 继续现有 `loopx finish-start ...`。

#### 4.1.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| `HEAD` 不可解析 | 直接失败 | 明确 `no_valid_head` | stderr/JSON error |
| slug 冲突 | 直接失败 | 看到 conflict 及 source/design | stderr/JSON error |
| 无 design artifact | fallback 到 source artifact | human output 说明 fallback | 不涉及 |
| 重复调用 | 幂等复用 | 可见 `reused` 或同一路径输出 | 不涉及 |
| 非 git worktree | 直接失败 | 明确错误 | stderr/JSON error |
| untracked files 存在 | 不影响 clean 判定 | 不阻止 execution-start | 不涉及 |

#### 4.1.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `finish-start` baseline 文件结构 | 兼容现有 finish-audit | existing workflow tests |
| `finish-audit` committed change window 计算方式 | 不破坏学习提取 | runtime tests |
| 无 design/source 时仍允许 legacy flow | 避免阻塞 direct-to-plan | compatibility tests |

### 4.2 final-review 详细设计

#### 4.2.1 需求内容

- 入口：`loopx:final-review`
- 操作人/调用方：`exec`、`subagent-exec`、手动 workflow controller
- 前置条件：execution state 已存在或可从 source artifact fallback
- 输出结果：
  - single-plan/spec-level：canonical final-review report
  - multi-plan child plan-level：仅更新 `.loopx/multi-plan/<slug>/state.json`

#### 4.2.2 方案设计

- 核心逻辑：
  - 从 execution state 或 source artifact 解析 requirement start identity。[D-003]
  - 组装 review scope：`start_commit`, current `HEAD`, optional tracked diff inputs。
  - 生成/更新 canonical report；如果同一 design/source 已有 report，则覆盖主内容并在 `复审记录` 追加一轮。[D-004]
  - 对 coverage matrix 的 `missing/partial` 强制提升到 findings 与 blocking issues。[D-006]
  - 对中文模板做人类可读标签本地化，仅保留 gate token。[D-007]
  - 如果是 multi-plan child plan-level review，只更新 `plan_review.status/reviewed_at/summary` 和 `ready_for_spec_review`，不写 report。[D-005][D-009]
- 状态流转：
  - child plan-level：`pending -> passed/blocked`
  - single/spec-level report：`No / With fixes / Yes`
- 数据变更：
  - 更新 `.loopx/final-review/<canonical>.md`
  - 或更新 `.loopx/multi-plan/<slug>/state.json`
- 计算公式：
  - `tracked_diff_included = tracked_worktree_has_changes ? true : false`
  - `Ready for finish? = Yes` 仅当不存在 unresolved Critical/Important findings，尤其包括 requirement coverage gaps。
- 幂等设计：
  - 同一 design/source 重复 review -> 同一路径、追加一轮 iteration、更新当前 verdict。
  - 同一 child plan 重复 review -> 覆盖 `plan_review.summary` 和 `reviewed_at`。
- 权限/越权控制：不涉及额外权限。
- 异常处理：
  - `requirements.md` / source AC 无法解析 -> 停止 review。
  - tracked changes 存在但未提供 `git diff` / `git diff --cached` -> 视为 review input 不完整。
  - child plan-level review 被误要求写 report -> 不创建 artifact。
- 补偿/重试：
  - `fix-review` 后再次运行 final-review，更新同一 canonical report。
- 日志与审计：
  - report 内保留 `复审记录 / Review Iterations`。

#### 4.2.3 流程步骤

1. 收集 execution state / source identity。
2. 读取 current `HEAD`。
3. 检查 tracked staged/unstaged changes。
4. 如存在 tracked diff，收集 `git diff` 和 `git diff --cached`。
5. 构建 coverage matrix、support lens risk scan、runtime validation、test trust。
6. 生成 findings，强制把 coverage gap 提升到 blocking issues。
7. single/spec-level：更新 canonical report。
8. child plan-level：只更新 multi-plan state。

#### 4.2.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| tracked unstaged/staged changes 存在 | 必须附 `git diff` / `git diff --cached` | report scope metadata 显示 tracked diff included | 不涉及 |
| 只有 untracked files | 视为 clean | 不阻止 final-review | 不涉及 |
| same design, repeated final-review | 更新同一 report | 无新文件，看到 iteration history | 不涉及 |
| child plan review | 不写 report | state 中可见 `plan_review` | 不涉及 |
| missing requirement | 记为 Critical blocking finding | `Ready for finish?` 不能为 Yes | report/blocking issues |
| partial requirement | 记为 Important blocking finding | `Ready for finish?` 不能为 Yes | report/blocking issues |
| 中文用户 | 本地化人类标签 | 仅保留 gate token 英文 | template assertions |

#### 4.2.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `Ready for finish?` / `Yes|No|With fixes` exact token | finish 依赖稳定门禁文义 | governance tests |
| six-phase final-review structure | 维持现有 review discipline | governance tests |
| `fix-review` 仍然处理 final-review 返回的问题 | 主链不变 | skill contract review |

### 4.3 multi-plan state v2 详细设计

#### 4.3.1 需求内容

- 入口：`plan-to-exec`、`subagent-exec`、`final-review`、`finish`
- 操作人/调用方：multi-plan workflow controller
- 前置条件：存在 `docs/loopx/plans/YYYY-MM-DD-<feature-slug>/`
- 输出结果：`.loopx/multi-plan/<feature-slug>/state.json` schema v2

#### 4.3.2 方案设计

- 核心逻辑：
  - schema_version 从 `1` 升到 `2`。[D-009]
  - `plans[]` 中移除 `plan_final_review`。
  - 改为 `plan_review.status/reviewed_at/summary`。
  - 保留 `spec_final_review.path` 和 `ready_for_finish`，因为 spec-level report 仍是唯一 canonical artifact。
- 状态流转：
  - child row: `in_progress -> complete + plan_review.passed + ready_for_spec_review`
  - package: `in_progress -> ready_for_spec_review -> ready_for_finish`
- 数据变更：
  - v1 -> v2 迁移可采用“读取时兼容、写入时统一落 v2”。
- 计算公式：
  - `child_ready = status == "complete" && plan_review.status == "passed" && ready_for_spec_review == true`
  - `package_ready = all(child_ready) && spec_final_review.ready_for_finish == "Yes"`
- 幂等设计：
  - 重复 child review 可以覆盖 `reviewed_at/summary`。
  - `finish` gate 只读。
- 权限/越权控制：本地 state；不涉及身份。
- 异常处理：
  - v1 文件读取：兼容读，优先迁移到 v2。
  - invalid JSON：finish 阻止完成。
- 补偿/重试：修 state 后重试 finish。
- 日志与审计：finish error 明确指出缺失 child 或 review gate。

#### 4.3.3 流程步骤

1. 读取现有 state。
2. 若 schema v1，迁移/规范化为 v2 内存结构。
3. child plan-level review 更新 `plan_review`。
4. spec-level final-review 更新 `spec_final_review`。
5. finish gate 校验 v2 结构。

#### 4.3.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| v1 state 仍有 `plan_final_review` | 读兼容，写回 v2 | 无需手动迁移 | test coverage |
| child review 通过但未置 `ready_for_spec_review` | finish 仍阻止 | 提示 ready_for_spec_review 缺失 | error summary |
| `spec_final_review.path` 缺失 | finish 阻止 | 明确 spec review gate 缺失 | error summary |
| child plan 并行写 state | 第一版不加锁；最后写覆盖 | 依赖 review/controller 重试 | 不涉及 |
| child plan state 记录 commit metadata | 明确不允许 | validation failure | validation error |

#### 4.3.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `source_spec`, `feature_slug`, `plan_package` 顶层字段 | 仍是 package identity 的关键 | workflow tests |
| spec-level `spec_final_review.path` | finish 仍需唯一 artifact | workflow tests |
| single-plan 不读取 multi-plan state | 范围边界 | workflow tests |

### 4.4 finish 详细设计

#### 4.4.1 需求内容

- 入口：`loopx:finish` / `loopx finish-audit` / `loopx finish-record --status done`
- 操作人/调用方：workflow controller
- 前置条件：已有 baseline；若走新流程，已有 execution state
- 输出结果：finish audit/report 和最终 choice record 带完整 requirement committed evidence。[D-008]

#### 4.4.2 方案设计

- 核心逻辑：
  - `finish-audit` 仍按 baseline 计算 committed change window。
  - 新增 `requirement_start_commit` 字段，优先来自 execution state；无 execution state 时 fallback baseline ref。[D-008][D-010]
  - `finish-record --status done` 之前：
    - 若存在 tracked staged/unstaged changes，则要求先 commit；untracked 忽略。
    - 若 source 匹配 multi-plan package，则按 v2 gate 校验。
  - finish report 展示：
    - requirement start commit
    - final `HEAD`
    - commit list
    - changed files
    - tracked status summary / untracked summary
- 状态流转：
  - 维持现有 `needs-agent-audit -> audited -> choice-recorded -> completed`。
  - tracked changes 未 commit 或 multi-plan gate 失败时，不进入 `completed`。
- 数据变更：
  - finish state 增加 requirement start metadata 与 tracked/untracked 分离统计。
- 计算公式：
  - `tracked_dirty = statusLines.filter(!startsWith("?? "))`
  - `workflow_clean = tracked_dirty.length === 0`
- 幂等设计：
  - gate 条件不变时，重复 `finish-record --status done` 结果稳定。
- 权限/越权控制：不涉及。
- 异常处理：
  - missing execution state：fallback baseline，不阻断 legacy flow。
  - tracked dirty 未提交：阻止 done。
  - multi-plan state invalid/incomplete：阻止 done。
- 补偿/重试：
  - commit tracked changes、补齐 state 或 rerun final-review 后可重试。
- 日志与审计：
  - finish report 始终可见 requirement start commit 与 final committed evidence。

#### 4.4.3 流程步骤

1. `finish-audit` 读取 baseline，构建 committed change window。
2. runtime 解析 execution state（如存在）。
3. report 渲染 requirement start commit 与 current/final head evidence。
4. `finish-record --status done` 时校验 tracked dirty 与 multi-plan gate。
5. 条件满足后写 choice / report。

#### 4.4.4 边界条件

| 场景 | 处理方式 | 用户/调用方感知 | 监控/告警 |
|---|---|---|---|
| 只有 untracked files | 不阻止 done | report 可显示 untracked summary | 不涉及 |
| tracked staged/unstaged changes 仍存在 | 阻止 done | 提示先 commit tracked changes | stderr/JSON error |
| execution state 不存在 | fallback baseline start | report 仍有 start commit，但标记为 baseline-derived | 不涉及 |
| multi-plan state 缺失 | 若 source 匹配 package，则阻止 done | 缺 state path | error summary |
| canonical final-review report 不存在 | `finish` 不生成 report，仍按现有规则要求先做 final-review | user sees missing report | finish skill gating |

#### 4.4.5 不变行为

| 行为/表面 | 保持不变的原因 | 验证方式 |
|---|---|---|
| `finish-audit` 生成 extraction candidates | memory/spec extraction 主链不变 | workflow tests |
| `finish` 不自行生成 final-review report | 职责边界不变 | governance tests |
| 正常 repo / worktree completion menu | CLI 交互主形态不变 | finish skill review |

## 七、接口设计

### 7.1 接口设计原则

- execution range 与 finish baseline 的职责分离必须清晰；不要在同一命令里隐式写两种状态。[D-001][D-002]
- human output 继续默认简洁；完整 state payload 仅在 `--json` 下暴露。[D-002]
- final-review report token `Ready for finish?` 与 `Yes|No|With fixes` 必须稳定；其它标签按语言本地化。[D-007]
- multi-plan child review state 是 workflow contract，不是最终用户 API；但字段名必须稳定可测。[D-005][D-009]

### 7.2 接口清单

| 接口 | 调用方 | 服务方 | 权限/认证 | 幂等 | 文档地址 | 备注 |
|---|---|---|---|---|---|---|
| `loopx execution-start <slug> --source <path> [--design <path>] [--json]` | `exec` / `subagent-exec` / human | CLI runtime | 本地文件系统 | 是 | 本设计文档 | [D-002] |
| `.loopx/execution-ranges/<slug>.json` | `final-review` / `finish` | local runtime state | 本地文件系统 | 是 | 本设计文档 | [D-001] |
| `.loopx/multi-plan/<slug>/state.json` schema v2 | `subagent-exec` / `final-review` / `finish` | local runtime state | 本地文件系统 | 是 | 本设计文档 | [D-009] |
| `.loopx/final-review/<canonical>.md` | `finish` / human | final-review skill | 本地文件系统 | 是，同源更新同一路径 | 本设计文档 | [D-004] |

### 7.3 接口明细

#### 7.3.1 `loopx execution-start`

- 路径/方法：CLI subcommand
- 请求头：不涉及
- 请求参数：
  - positional `slug`
  - required `--source <path>`
  - optional `--design <path>`
  - optional `--json`
- 响应参数：
  - human mode: `execution range: <slug>`, `path`, `start`, `source`, `design`
  - JSON mode:
    - `ok`
    - `command`
    - `path`
    - `state`
    - `reused`
- 错误码：
  - non-zero exit for invalid head / conflict / invalid state
- 业务校验：
  - slug conflict
  - git worktree valid
  - source non-empty
- 数据变更：
  - create/read `.loopx/execution-ranges/<slug>.json`
- 日志字段：
  - `slug`
  - `start_commit_short`
  - `source_artifact`
  - `design_artifact`

#### 7.3.2 final-review canonical report

- 路径/方法：local markdown artifact write
- 请求头：不涉及
- 请求参数：
  - source requirements / design
  - start commit
  - current head
  - optional tracked diffs
- 响应参数：
  - markdown report body
  - `Ready for finish?`
  - `阻塞问题`
- 错误码：无 CLI code 约束，依赖 skill runtime
- 业务校验：
  - coverage gaps promoted to findings
  - canonical path stable
- 数据变更：
  - overwrite/update same file
- 日志字段：
  - `start_commit`
  - `review_head`
  - `tracked_diff_included`

  - execution state 造成 legacy flow 大面积失败

  - 保持 baseline fallback
  - 临时允许 final-review 继续读取 latest report 逻辑
- 用户影响：可能回退到旧 report identity 语义
- 恢复方式：revert runtime/schema/template 改动

### 8.3 关联系统/功能影响

| 系统/功能 | 影响 | 依赖动作 | 负责人 | 验证方式 |

| `finish` | multi-plan gate 和 report evidence 改动 | 更新 runtime/skill/tests | loopx maintainers | workflow tests |

### 8.4 回滚方案

- 回滚条件：
  - `execution-start` 设计证明与主链不兼容
  - multi-plan v2 state 读取/写入导致现有流程不可恢复
- 回滚步骤：
  1. revert execution state helper 与 CLI
  2. revert final-review template / skill 改动
  3. revert multi-plan state schema gate 改动
  4. 保留 baseline fallback
- 数据回滚：
  - `.loopx/execution-ranges/` 可直接删除
  - `.loopx/multi-plan/` 可从 v2 回写为 v1 或重新生成
- 配置回滚：不涉及
- 风险：已生成的 canonical report 和旧 `re-review` 文件并存，需要人工识别
