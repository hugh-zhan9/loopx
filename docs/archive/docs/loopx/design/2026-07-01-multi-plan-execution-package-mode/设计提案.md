# 将 multi-plan package mode 收进 exec/subagent-exec

Author(s): zhangyukun, Codex
Last updated: 2026-07-01
Status: Draft
Discussion: 不涉及
Source requirements: `.loopx/intake/2026-07-01-multi-plan-execution-package-mode/`
Support lenses: architecture-designer

## Abstract / 摘要

我们把 multi-plan package orchestration 收进现有 `exec` 和 `subagent-exec` 两个执行入口，而不是新增 `multi-plan-exec` skill。新的 package mode 接受 `docs/loopx/plans/YYYY-MM-DD-feature/` 或 `00-overview.md`，按 `00-overview.md` 的 child plan 顺序逐个执行；`subagent-exec` 在每个 child plan 内继续使用 fresh implementer/reviewer subagents，`exec` 在同一上下文内顺序执行。全部 child plans ready 后，package mode 自动进入 spec-level `final-review`，review clean 后进入 `finish`。

核心承诺是：用户只需要记住已有执行入口，multi-plan 仍保留 plan-level/spec-level review 和 finish gate，不引入自动并行调度，也不新增 public CLI。

## Background / 背景与动机

当前 repo 已经具备 multi-plan 的下游门禁，但执行入口仍不自然：

- `plan-to-exec` 能产出 `00-overview.md` + 多个 numbered child plans，但现在的 handoff 明确要求“per child plan”执行。
- `subagent-exec` 已支持 numbered child plan，但当前 contract 写明只执行当前 child plan，不执行 sibling child plans。
- `exec` 当前只描述“读一个 plan 文件并顺序执行”，没有 package mode。
- `final-review` 已经有 plan-level 和 spec-level 两层 review。
- `finish` runtime 已经校验 `.loopx/multi-plan/<feature-slug>/state.json`，且当前 schema v2 使用 `plan_review.status/reviewed_at/summary` 和 `ready_for_spec_review`。

用户的明确诉求是：不想新增一个 skill 扩充流程，希望 `subagent-exec` 支持 multi-plan package；同时 `exec` 作为无 subagent lane，也应支持同样 package scope。

这会反转历史设计 `docs/loopx/design/2026-06-29-multi-plan-execution-review-scope/需求设计文档.md` 中的旧边界：“不自动执行 multi-plan 目录”和“`subagent-exec` 的执行单位仍是单 plan 文件”。本提案接受这个反转，但把范围限定为顺序 package orchestration，而不是并行 scheduler。

## Goals And Non-Goals / 目标与非目标

目标：

- `subagent-exec <00-overview.md|plan-dir>` 执行整个 multi-plan package。
- `exec <00-overview.md|plan-dir>` 以同样 package scope 顺序执行，不使用 subagents。
- `subagent-exec <01-child.md>` 和 `exec <01-child.md>` 保持 targeted child-plan mode。
- package mode 顺序执行 child plans，不自动并行。
- package mode 缺失 `.loopx/multi-plan/<feature-slug>/state.json` 时从 `00-overview.md` 初始化。
- package mode 在所有 child plans ready 后自动跑 spec-level `final-review`，clean 后进入 `finish`。
- `plan-to-exec` 对 multi-plan package 默认推荐 package mode，并保留 child plan direct execution 作为 targeted/resume/manual-control 用法。

非目标：

- 不新增 `multi-plan-exec` skill。
- 不新增 public `loopx multi-plan` CLI。
- 不自动并行调度 child plans。
- 不改变 numbered child plan direct execution 的 targeted 语义。
- 不把 mutable state 写进 repo-tracked `docs/loopx/plans/.../`。
- 不重新设计 final-review 或 finish runtime 的核心 gate；package mode 复用已有 plan-level/spec-level review 和 finish gate。

## Proposal / 设计方案

### 统一输入分类

`exec` 和 `subagent-exec` 增加相同的 input scope classifier：

| 输入 | Scope | 行为 |
|---|---|---|
| `docs/loopx/plans/YYYY-MM-DD-feature.md` | single plan | 保持现有 single-plan 执行，最终 `final-review` + `finish` |
| `docs/loopx/plans/YYYY-MM-DD-feature/00-overview.md` | package | 顺序执行所有 child plans，spec-level `final-review` clean 后进入 `finish` |
| `docs/loopx/plans/YYYY-MM-DD-feature/` | package | 等同于该目录下 `00-overview.md` |
| `docs/loopx/plans/YYYY-MM-DD-feature/01-child.md` | child plan | 只执行该 child plan，plan-level `final-review` 后更新 state 并停止 |

非法路径、缺失 `00-overview.md`、无法解析 child plan list、重复 child plan path、state 与 overview 不匹配都应阻塞并报告具体缺陷。

### package mode 是外层控制器，不改变 child plan 内部执行纪律

package mode 做四件事：

1. 解析 `00-overview.md` 的 source spec、package slug、state path、child plan list 和 execution order。
2. 缺失 state 时初始化 `.loopx/multi-plan/<feature-slug>/state.json`，已有 state 时验证它与 overview 一致。
3. 按顺序把每个未完成 child plan 送入对应执行 lane。
4. 全部 child plans ready 后运行 spec-level `final-review`，clean 后进入 `finish`。

`subagent-exec` 内部仍是“每个 task 一个 fresh implementer subagent + 每个 task 一个 reviewer subagent”。package mode 不把“整个 child plan”交给一个大 subagent，也不并发运行多个 child plans。

`exec` 内部仍是 same-context sequential execution + checkpoint review。它与 `subagent-exec` 共享 package orchestration 语义，但不使用 subagents。

### state 初始化使用当前 schema v2

package mode 初始化缺失 state 时写入 schema v2：

```json
{
  "schema_version": 2,
  "feature_slug": "2026-07-01-feature",
  "plan_package": "docs/loopx/plans/2026-07-01-feature",
  "source_spec": "docs/loopx/design/2026-07-01-feature/需求设计文档.md",
  "status": "in_progress",
  "plans": [
    {
      "path": "docs/loopx/plans/2026-07-01-feature/01-core.md",
      "status": "pending",
      "plan_review": null,
      "ready_for_spec_review": false
    }
  ],
  "spec_final_review": null
}
```

child plan 完成后写：

```json
{
  "path": "docs/loopx/plans/2026-07-01-feature/01-core.md",
  "status": "complete",
  "plan_review": {
    "status": "passed",
    "reviewed_at": "2026-07-01T00:00:00.000Z",
    "summary": "No blocking issues"
  },
  "ready_for_spec_review": true
}
```

新设计不得重新引入 `plan_final_review` 作为新写入字段；现有 runtime 对旧 v1 state 的兼容读取仍保持。

## Support Lens Checks / 专项设计检查

| Support lens | Trigger | Design checks applied | Result |
|---|---|---|---|
| `architecture-designer` | workflow ownership、state model、package orchestration、failure modes | 明确系统边界、状态所有权、失败阻塞、兼容和回滚 | 选择“现有执行 skill 内增加 package mode + 本地 state 初始化”的最小边界，拒绝新 skill 和并行 scheduler |

`cli-developer` 未触发：本设计不新增或修改 public `loopx` CLI 命令、flag、stdout/stderr 或 `--json` 语义。`$exec` / `$subagent-exec` 是 agent skill invocation contract，不是 Node CLI surface。

## Boundary Scenarios / 边界场景

| 场景 | 设计处理 |
|---|---|
| 输入是 package dir | 查找同目录 `00-overview.md`，按 package mode 执行 |
| 输入是 `00-overview.md` | package mode |
| 输入是 `01-child.md` | targeted child-plan mode，只执行该 child |
| 输入是普通 single-plan `.md` | 保持现有 single-plan mode |
| package dir 缺 `00-overview.md` | 阻塞，报告 missing overview |
| `00-overview.md` 缺 source spec、state path 或 child plan list | 阻塞，要求修正 plan package |
| state 缺失 | 从 overview 初始化 schema v2 state |
| state JSON 非法 | 阻塞，不覆盖 |
| state 与 overview 的 feature slug、package path、source spec 或 child plan paths 不一致 | 阻塞，不猜测修复 |
| child plan 已 `complete` 且 `plan_review.status: passed` | package mode 跳过该 child plan，用于 resume |
| child plan review 不通过 | 不标 ready，进入现有 fix-review/修复路径，package mode 不继续 sibling |
| spec-level final-review 为 `Ready for finish? No` 或有 Critical/Important | 不进入 finish，走 fix-review/修复后复审 |
| 并发启动两个 package mode | 第一版不加锁；不支持并发运行。state 或 git 冲突出现时阻塞 |
| `00-overview.md` 标记 child plans 可并行 | 仅作为人工信息；package mode 仍顺序执行 |
| 文件权限或写 state 失败 | 阻塞并报告路径和操作 |
| 旧 v1 state 存在 | runtime 继续兼容读取；新 package mode 写 schema v2 |
| 单 plan workflow | 不变 |

## Rationale / 理由与取舍

| Alternative | Why Not |
|---|---|
| 新增 `multi-plan-exec` skill | 用户明确不想扩充流程；新增 skill 会增加心智负担，且其职责会和 `exec/subagent-exec/final-review/finish` 重叠 |
| 继续只允许 per-child execution | 与“一次完成所有 plan”的使用目标冲突；`plan-to-exec` 产出 multi-plan 后仍需要用户手工串联 |
| 把 package mode 只加到 `subagent-exec` | `exec` 是 no-subagent fallback，不支持同 scope 会让 multi-plan package execution 不对称 |
| 让 `subagent-exec` 并行执行 parallel-capable child plans | 需要额外解决共享文件冲突、state 并发写、review 顺序、git merge 和失败补偿；第一版成本过高 |
| 让 state 缺失直接阻塞 | 会让用户仍需手工准备 `.loopx/multi-plan`，违背一个入口跑完整个 package 的体验 |
| 自动修复已有矛盾 state | 风险太高；已有 state 可能代表真实执行进度，矛盾时应人工判断 |

## Compatibility / 兼容性

本提案是 additive workflow change，但会替换当前 skill 文案中的一个旧约束。

保持不变：

- single-plan `exec` / `subagent-exec` 行为。
- numbered child plan direct execution 行为。
- plan-level final-review 不授权 package finish。
- spec-level final-review 是 package finish 的唯一 review gate。
- `.loopx/multi-plan/<feature-slug>/state.json` 仍是本地 mutable state，不进 repo-tracked plan 目录。
- public `loopx` CLI 不新增命令。

变化：

- `exec/subagent-exec` 接受 package dir 或 `00-overview.md` 作为 whole-package scope。
- `plan-to-exec` multi-plan handoff 从“只按 child plan 执行”改为“默认 package execution，child execution 用于 targeted/resume/manual control”。
- 当前 `skills/subagent-exec/SKILL.md`、`skills/plan-to-exec/SKILL.md`、历史治理断言中关于“不执行 sibling plans / 不执行目录”的 wording 需要更新到新的 scope-specific contract。

## Operational And Security Impact / 运行与安全影响

运行影响：

- package mode 会更长时间占用当前 agent session，因为它串行执行多个 child plans。
- state 写入次数增加，但仍是本地文件写入，无服务端和数据库。
- 没有自动并行，因此不会新增并发 merge 负担。

安全影响：

- 不新增网络、权限、认证或 secret handling。
- 不新增 public CLI 或外部 API。
- state 初始化只读取 repo 内 `00-overview.md` 和 child plan paths，写入 `.loopx/multi-plan/.../state.json`。

可维护性：

- `exec` 与 `subagent-exec` 必须共享同一套 package mode wording 和治理测试，否则容易发生 scope divergence。
- 设计应要求 `plan-to-exec` 产出的 `00-overview.md` 保持可解析字段，减少 brittle parsing。

## Implementation And Transition / 实现与过渡

实现过渡应优先更新 contract，再补治理测试和 helper 行为：

1. 更新 `plan-to-exec` 的 multi-plan handoff 与 `00-overview.md` required fields。
2. 更新 `subagent-exec` 的 input classifier、package mode loop 和 child mode 边界。
3. 更新 `exec` 的 input classifier、package mode loop、child mode final-review/state update 和 single-plan finish 边界。
4. 更新 `finish` skill wording，确保只描述 schema v2 `plan_review` gate。
5. 增加 governance/runtime tests，覆盖 package input、child targeted input、state init、invalid state blocking、sequential execution wording、spec-level review + finish handoff。

这不是实现任务拆分；具体文件顺序由 `plan-to-exec` 决定。

## Detailed Design Handoff / 详细设计交接

应立即写详细设计。详细设计必须把以下决策作为固定约束：

- 不新增 workflow skill。
- `exec` 和 `subagent-exec` 都支持 package mode。
- package mode 顺序执行 child plans。
- package mode 缺 state 自动初始化，矛盾 state 阻塞。
