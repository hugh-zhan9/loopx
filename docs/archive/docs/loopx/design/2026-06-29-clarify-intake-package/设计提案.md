# 将 clarify 输出升级为 intake package

Author(s): loopx maintainers
Last updated: 2026-06-29
Status: Draft
Discussion: 当前对话
Source requirements: 当前对话、[Harness Engineering 对 loopx 的可吸收点](../../../articles/harness-engineering-loopx-takeaways.md)
Support lenses: cli-developer, architecture-designer

## Abstract / 摘要

我们将 `clarify` 的输出从单个 `.loopx/intake/clarify-<slug>-YYYY-MM-DD.md` 文件升级为目录式 intake package：

```text
.loopx/intake/YYYY-MM-DD-<slug>/
  clarification.md
  requirements.md
  test-cases.md
```

`requirements.md` 成为确认后的需求契约，`test-cases.md` 成为需求阶段的黑盒验收/集成测试场景，`clarification.md` 保留问答过程和 resume state。`spec` 与 `plan-to-exec` 后续应接受 intake package 目录作为输入，并至少读取 `requirements.md` 与 `test-cases.md`。

第一版不新增 `acceptance-testcase-generator` skill。由 `clarify` 直接生成三件套，等格式稳定后再评估是否拆出 support skill。

## Background / 背景与动机

当前 `clarify` 的 canonical 输出是单文件：

```text
.loopx/intake/clarify-<slug>-YYYY-MM-DD.md
```

`spec` 读取“用户 PRD / 外部需求文档 / approved clarify output”作为 source of truth；`plan-to-exec` 也明确接受 `.loopx/intake/clarify-<slug>-YYYY-MM-DD.md`。这说明当前没有正式的 `requirements.md` 或 `test-cases.md` artifact，需求契约、澄清过程、验证口径被混在同一个文件里。

Harness Engineering 文章里有一个值得吸收的 P1 设计：`requirements.md` 给 P2 设计使用，`test-cases.md` 给 P4 测试使用，两者共用同一组 AC。这个做法解决的是“下游不要重新理解一遍需求再写测试”。在 loopx 里，这对应一个更清晰的 P1 intake package。

当前代码证据：

- `skills/clarify/SKILL.md` 要求写 `.loopx/intake/clarify-<slug>-YYYY-MM-DD.md`。
- `skills/spec/SKILL.md` 使用 approved `clarify` output 作为 source of truth。
- `skills/plan-to-exec/SKILL.md` 接受 `.loopx/intake/clarify-<slug>-YYYY-MM-DD.md` 作为 source。
- `src/workflow.mjs` 生成 `spec_artifact_path`，但实际指向 intake/clarify 单文件。
- `src/cli.mjs` human output 中 `intake:` 展示 `state.spec_artifact_path`。

## Goals And Non-Goals / 目标与非目标

目标：

- 将 `clarify` 的产物从单文件改为目录式 intake package。
- 明确 `clarification.md`、`requirements.md`、`test-cases.md` 的职责边界。
- 让 `requirements.md` 与 `test-cases.md` 共用同一组 `AC-*`。
- 让 `spec` 和 `plan-to-exec` 能以 intake package 目录作为输入。
- 保留短期兼容字段，降低 CLI 和测试迁移风险。
- 把需求阶段的测试场景提前固定为黑盒验收/集成测试，不提前绑定内部实现。

非目标：

- 不在第一版新增 `acceptance-testcase-generator` skill。
- 不让 `test-cases.md` 生成可执行测试脚本。
- 不把 `test-cases.md` 用作单元测试设计文档。
- 不改变 loopx 的主流程：`clarify -> spec? -> plan-to-exec -> ...`。
- 不新增 mandatory CLI state machine。
- 不迁移历史 `.loopx/intake/clarify-*.md` 文件。

## Proposal / 设计方案

### 1. `clarify` 输出 intake package 目录

新建 workflow 时，`clarify` 生成：

```text
.loopx/intake/YYYY-MM-DD-<slug>/
  clarification.md
  requirements.md
  test-cases.md
```

如果同一天同 slug 的目录已经存在，实现可追加短时间戳或序号，避免覆盖已有 intake package。目录名必须使用 terminal-friendly kebab-case slug，不使用中文原文。

### 2. 三个文件各自承担不同职责

`clarification.md` 是过程记录：

- source inputs
- Q&A rounds
- user wording
- assumptions challenged
- rejected alternatives
- brownfield evidence
- resume state

`requirements.md` 是需求契约：

- intent and outcome
- scope
- non-goals
- decisions
- constraints
- acceptance criteria
- open questions
- handoff recommendation

`test-cases.md` 是需求阶段测试场景：

- coverage summary
- `TC-*` cases
- each case maps to one or more `AC-*`
- case type: integration, e2e, api, cli, manual
- preconditions, steps, expected result, automation target

### 3. `requirements.md` 与 `test-cases.md` 共用 `AC-*`

`requirements.md` 中的 acceptance criteria 使用稳定 ID：

```markdown
### AC-001

WHEN <condition or user action>
THEN <observable system behavior>
AND <additional constraint>

Evidence target: integration | e2e | api | cli | unit | manual
Risk: high | medium | low
```

`test-cases.md` 中每个测试用例必须引用来源 AC：

```markdown
### TC-001

Source AC: AC-001
Type: integration
Priority: P0
Preconditions:
- ...
Steps:
1. ...
Expected:
- ...
Automation target: TBD
```

规则：

- 每个 `TC-*` 必须引用至少一个 `AC-*`。
- 每个高风险 `AC-*` 至少需要一个失败或边界 case。
- 无法自动化的 case 必须写 `Type: manual` 和原因。
- `test-cases.md` 不写内部函数级单元测试。
- `requirements.md` 与 `test-cases.md` 冲突时，回到 `clarify`，下游不能自行调和。

### 4. `spec` 与 `plan-to-exec` 接受 intake package 目录

`clarify` 的 handoff 改为传目录：

```text
$spec .loopx/intake/YYYY-MM-DD-<slug>/
$plan-to-exec .loopx/intake/YYYY-MM-DD-<slug>/
```

`spec` 接收目录时：

- 必读 `requirements.md`。
- 必读 `test-cases.md`。
- 按需读 `clarification.md`。
- 如果设计需要修改 AC 或测试前提，必须返回 `clarify`。

`plan-to-exec` 接收目录时：

- 必读 `requirements.md`。
- 必读 `test-cases.md`。
- 按需读 `clarification.md`。
- 计划任务必须覆盖 `AC-*`。
- 验证计划必须覆盖 `TC-*`。

### 5. CLI 和状态短期保留兼容字段

新增状态字段：

```json
{
  "intake_package_path": ".loopx/intake/YYYY-MM-DD-<slug>/",
  "clarification_path": ".loopx/intake/YYYY-MM-DD-<slug>/clarification.md",
  "requirements_path": ".loopx/intake/YYYY-MM-DD-<slug>/requirements.md",
  "test_cases_path": ".loopx/intake/YYYY-MM-DD-<slug>/test-cases.md"
}
```

短期保留：

```json
{
  "spec_artifact_path": ".loopx/intake/YYYY-MM-DD-<slug>/requirements.md"
}
```

`spec_artifact_path` 保留是兼容措施，不再代表新概念。CLI human output 应逐步显示：

```text
intake: .loopx/intake/YYYY-MM-DD-<slug>/
requirements: .loopx/intake/YYYY-MM-DD-<slug>/requirements.md
test cases: .loopx/intake/YYYY-MM-DD-<slug>/test-cases.md
```

JSON mode 应返回完整字段，保持自动化可读。

## Support Lens Checks / 专项设计检查

| Support lens | Trigger | Design checks applied | Result |
|---|---|---|---|
| `cli-developer` | `loopx clarify/status/next --json` 和 human output 会展示新 artifact 路径 | 保留现有命令签名；JSON 增加结构化字段；human output 简洁显示 intake/package 子路径；不把完整运行状态混入默认 stdout | 采用目录输入但不新增命令；保留兼容字段 |
| `architecture-designer` | intake package 是跨 skill 的长期 artifact contract | 明确边界、迁移、兼容、失败模式、下游依赖；避免新增 mandatory CLI state machine | 采用 skill-first artifact contract，CLI 只生成和展示 runtime state |

## Boundary Scenarios / 边界场景

| 场景 | 处理 |
|---|---|
| 新 slug 首次运行 clarify | 创建 `.loopx/intake/YYYY-MM-DD-<slug>/` 和三份文件。 |
| 同一天同 slug 重复运行 clarify | 不覆盖已有 package；追加短时间戳或序号创建新目录，state 指向最新 package。 |
| 老 workflow 仍有 `.loopx/intake/clarify-*.md` | 不迁移历史文件；`spec`/`plan-to-exec` 保持读取旧单文件能力。 |
| `requirements.md` 缺少可测 AC | `clarify` 不能 handoff 为 `direct_to_plan`；必须继续澄清或 blocked。 |
| `test-cases.md` 没有覆盖某个高风险 AC | `clarify` 不能 handoff 为 ready；必须补 case 或明确 manual/blocked 原因。 |
| `requirements.md` 与 `test-cases.md` 的 AC 不一致 | 下游停止，回到 `clarify`。 |
| `spec` 设计发现 AC 需要变化 | 不在 `spec` 中悄悄改需求；返回 `clarify` 或要求更新 intake package。 |
| `plan-to-exec` 发现测试场景无法执行 | 不自行删改测试场景；将阻塞项写明并返回 `clarify` 或 `spec`。 |
| `loopx status --json` 被脚本使用 | 保留 `spec_artifact_path`，新增 package 字段；不删除旧字段。 |
| `loopx status` human output | 增加 `intake:`、`requirements:`、`test cases:`，保持简洁。 |

## Rationale / 理由与取舍

| Alternative | Why Not |
|---|---|
| 继续使用单文件 clarify bundle | 需求契约、澄清过程、测试场景混在一起，下游仍要重新解释哪些内容是权威需求。 |
| 只在单文件中增加 `Test Case Seeds` section | 成本最低，但 `test-cases.md` 无法成为独立测试输入，也不符合“需求阶段测试场景一等产物”的目标。 |
| 第一版新增 `acceptance-testcase-generator` skill | 会同时扩大 bundled skill surface、resolver、安装治理和文档范围；在 artifact contract 稳定前成本偏高。 |
| 让 `spec` 生成 `test-cases.md` | 测试场景会晚于需求澄清阶段，容易重新解释需求；文章中的价值点是 P1 同源生成。 |
| 只让 `plan-to-exec` 读取 `requirements.md` | plan 会丢失需求阶段确定的验收/集成场景，测试仍然后置。 |

选择目录式 intake package，是因为它用最小结构改变换来清晰职责边界，同时保留现有 workflow 和 skill-first 定位。

## Compatibility / 兼容性

这是对新 `clarify` 输出格式的 breaking change，但应对现有使用保持读兼容：

- 新 workflow 使用目录式 intake package。
- 历史 `.loopx/intake/clarify-*.md` 不迁移、不删除。
- `spec` 和 `plan-to-exec` 继续接受旧单文件 source。
- `spec_artifact_path` 短期保留，指向新 `requirements.md`。
- 当前 public commands 不变：`loopx clarify`、`loopx status`、`loopx next` 保持命令签名。
- JSON payload 只新增字段，不删除旧字段。
- docs 和 skill handoff 文案更新为目录路径。

## Operational And Security Impact / 运行与安全影响

运行影响较小：新增两个 markdown 文件和一个目录层级。主要风险在 artifact 命名、状态字段和测试治理。

安全影响：无新的外部调用、权限、网络或秘密管理。`requirements.md` 和 `test-cases.md` 可能包含用户需求和测试账号描述，仍位于 `.loopx/` runtime state，不应被默认提交。

可观测性：`loopx status --json` 返回 intake package 子路径后，后续工具可以明确判断 P1 产物是否完整。

## Implementation And Transition / 实现与过渡

建议分两步：

1. 先更新 skill 合约和 runtime 生成目录式 intake package，并保留旧单文件读兼容。
2. 再让 `spec`、`plan-to-exec`、`final-review` 更强地消费 `test-cases.md`，必要时新增 artifact validator。

第一版不新增 support skill，不改变主流程，不迁移历史文件。
