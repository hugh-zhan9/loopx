# 需求、task 与 plan 分层协作

2026-11-11。用户已批准本会话讨论的方向并授权实现验证，未授权提交、推送、发版或覆盖本机已安装技能。基线 aa8e679（含用户已有本地提交）；分支 feature/task-scoped-workflows。详情见[需求设计文档](需求设计文档.md)。

## 已批准目标

- AC-1：大需求可先做整体理解再拆 task，无需一次穷尽所有细节；task 是交付和上下文边界，plan 是其内部实施方法，串行与并行均可。
- AC-2：人拆或 agent 拆使用同一合同，保留有效既有拆分；小任务继续 prompt-first，不强制 task 文档或持久 plan。
- AC-3：澄清只解决当前范围的必要决定；跨任务决定仍须在依赖实现前解决，其他问题保留明确归属，不能消失或自动延期验收。
- AC-4：共享决定保留唯一来源；新会话读取必要原始需求、共同约束和依赖结果，而非全量会话历史；任务交接与未完成工作恢复分开。
- AC-5：任务局部验收与需求集成验收分开；复用内容未变化的review和验证，跨合同变化重新覆盖实际影响。
- AC-6：安装与公开文档一致，旧plan继续有效；不引入执行runtime、不扩大Git或外部写授权。

<a id="D-001"></a>
## D-001：文档职责

```text
需求原文 + 共同约束 → task-split → 任务索引 / task简报
                                     ↓ 当前task范围
                          clarify / spec / plan2exec（按需）
                                     ↓
                            直接执行或显式exec
                                     ↓
                    task交付结果 → 下游task / 需求集成验收
```

task-split选择与调整委托边界，不制定执行微步骤、不执行任务。shared/task-scope维护范围、上下文选择、问题归属和交接规则；现有skill按当前范围消费它。plan2exec仍拥有P-*切片，exec仍只接收一份ready plan，宿主负责会话和调度。没有固定流水线。

<a id="D-002"></a>
## D-002：兼容与验收

task文档是可选来源，不新增plan必填字段或新plan schema。没有task简报时现有直接需求输入不变。任务图记录交付依赖而不按状态自动执行；共同合同变更必须找出受影响任务，不因旧task完成而隐藏集成缺口。父层保留需求覆盖与最终验收责任，子层不能用缩小上下文删掉安全、数据和兼容约束。

实现复用skills/shared/evidence-contract、exec recovery及review coverage；新skill加入既有canonical安装清单和npm打包，不创建独立安装机制。测试使用隔离HOME，不修改个人技能。检查覆盖包内容、两宿主安装、保护用户自定义、文档引用及行为场景；独立审查公共工作流兼容和范围授权。真实模型效率提升需独立评估，不从文本测试宣称token或review次数下降。
